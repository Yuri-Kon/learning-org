* Portage 的整体模型

| 名称     | 职责                        | 本质                             |
|----------+-----------------------------+----------------------------------|
| Portage  | 整套包管理系统               | 依赖解析、构建、安装、数据库及工具 |
| ~emerge~ | 用户主要操作入口             | 高层包管理命令                    |
| ~ebuild~ | 描述软件包的元数据和构建过程 | 在特定环境下执行的Bash脚本        |

[[file:image/poratge.arch.svg][Portage 安装软件包各组件协作过程]]

Portage 的默认布局:

- ~/etr/portage/~: Portage 的主要目录
  - ~make.conf~: 主要配置
  - ~package.use~: 按软件包设置 USE
  - ~repos.conf~: 仓库注册信息
  - ~make.profile~: 当前 Profile 链接
- ~/var/db/repos/~:
  - ~gentoo/~: 官方的 ebuild 仓库
  - ~local/~: 个人仓库
- ~/var/cache/disfiles/~: 下载的源码归档缓存
- ~/var/tmp/portage~: 解包、编译、临时安装等构建工作目录
- ~/var/db/pkg/~: 已安装软件包数据库(VDB)

* ebuild 是什么

** ebuild 是一段 Bash 程序

官方开发手册将 ebuild 定义为：在特定环境中执行的 bash 脚本。

我们可以写一个简化的 ebuild:

#+begin_src shell
  EAPI=8

  DESCRIPTION="A simple application"
  HOMEPAGE="https://example.org"
  SRC_URI="https://example.org/foo.${PV}.tar.gz"

  LICENSE="MIT"
  SLOT="0"
  KEYWORDS="~amd64"

  IUSE="debug"

  src_configure() {
      econf $(use_enable debug)
  }

  src_compile() {
      emake
  }

  src_install() {
      emake DESTDIR="${D}" install
  }
#+end_src

这份 ebuild 文件包括两种性质不同的内容:

- 软件包元数据: 描述软件包的属性，供 portage 选择软件包和计算依赖等
  #+begin_src shell
    EAPI=8
    DESCRIPTION="A simple application"
    SLOT="0"
    KEYWORDS="~amd64"
    IUSE="debug"
  #+end_src
- 构建阶段函数: 定义软件包在某个构建阶段应该如何执行
  #+begin_src shell
    src_compile() {
        emake
    }
  #+end_src


这就引出一个问题:

**既然 ebuild 是 bash 脚本，为什么 python 编写的 portage 能够读取其中的变量和函数?**

** Portage 如何获取 ebuild 中的信息

当需要从 ebuild 中生成元数据时， Portage 可以启动 bash 执行环境，在特殊的 ~depend~ 阶段加载 ebuild 和相关 eclass, 然后收集元数据变量。

在 Portage 的 [[https://github.com/gentoo/portage/blob/master/bin/ebuild.sh][bin/ebuild.sh]] 源码中，可以找到:

#+begin_src shell
  if [[ ${EBUILD_PHASE} = depend ]] ; then
      set -f

      metadata_keys={
          DEPEND RDEPEND SLOT SRC_URI RESTRICT HOMEPAGE LICENSE DESCRIPTION
          KEYWORDS INHERITED IUSE REQUIRED_USE PDEPEND BDEPEND EAPI PROPERTIES
          DEFINED_PHASES IDEPEND INHERIT
      }
#+end_src

这段代码列举了需要收集的元数据键，然后通过专用管道将其传递给包管理器。

这里有个性能问题：如果每次 ~emerge -pv~ 都需要执行大量的 ebuild 来读取元数据，开销就会很大。所以 Portage 支持 **元数据缓存(metadata cache)**, 官方仓库一般包含预生成的 ~metadata/md5-cache/~, Portage 可以直接读取有效的缓存，而不必每次都加载 ebuild.

接下来我们观察真实的元数据缓存:

#+begin_src shell :results output
  repo=$(portageq get_repo_path / gentoo)

  ebuild_file=$(
      # 选择Portage中除了mask之外的版本号最高的ebuild文件
      fd -d 1 '[^(9999)].ebuild$' "$repo/sys-apps/portage" |
          sort -V |
          tail -n 1
             )

  echo "$ebuild_file"
  echo

  cache="$repo/metadata/md5-cache/sys-apps/$(basename "$ebuild_file" .ebuild)"

  if [[ -f "$cache" ]]; then
      rg -n '^(EAPI|DESCRIPTION|SLOT|KEYWORD|IUSE|DEFINED_PHASES)=' "$cache"
  else
      echo "No md5-cache file"
  fi
#+end_src

- ~.ebuild~ 是 Bash 程序
- ~md5-cache~ 是提取后的元数据，方便包管理器查询
- ~DEFINED_PHASE~ 表示 ebuild 或继承的 eclass 定义了哪些阶段函数


那么我们来到这个假设:

#+begin_src shell
  EAPI=8

  DESCRIPTION="Example"
  SLOT="0"

  src_compile() {
      RDEPEND="dev-libs/openssl"
      emake
  }
#+end_src

那么 Portage能否通过正常的元数据提取过程，发现这个程序依赖 ~dev-libs/openssl~ 呢？

答案是不能。 Portage 在提取这个ebuild的元数据时，会加载并求值顶层Bash代码，但并不会自动执行 ~src_compile~. 这里要理解 Portage 的实现机制:

- 加载 ebuild: 求值顶层代码，包括变量赋值、函数定义和 inherit 调用
- 执行构建阶段: 在相应阶段调用 ~src_unpack()~, ~src_compile()~ 和 ~src_install()~ 等函数
- 依赖解析: 使用以获取的元数据，而不是实际编译软件来发现依赖


*** Bash 的求值顺序

考虑一段普通的 Bash 脚本:

#+begin_src shell
  RDEPEND=""

  src_compile() {
      RDEPEND="dev-libs/openssh"
  }

  DESCRIPTION="Example"
#+end_src

假设这个文件叫 ~demo.sh~, 那么通过:

#+begin_src shell
  source demo.sh
#+end_src

可以把它加载到当前的Shell.

Bash 会依次处理三个顶层结构:

| 结构                   | 加载时的行为           |
|------------------------+------------------------|
| ~RDEPEND=""~           | 立即执行赋值           |
| ~src_compile() {...}~  | 定义函数，不执行函数体 |
| ~DESCRIPTION="Example" | 立即执行赋值           |


因此，在加载完毕后， ~RDEPEND~ 仍然是空字符串；而 ~src_compile~ 已经成为一个可以调用的函数。只有在执行 ~src_compile~ 之后，才会修改 ~RDEPNED~.

*** Portage 的真实调用路径

1. Python: 首先查找元数据缓存
   源码入口: [[https://github.com/gentoo/portage/blob/master/lib/portage/dbapi/porttree.py]]

   #+begin_src python
     mydata, ebuild_hash = self._pull_valid_cache(
         mycpv, myebuild, mylocation
     )
   #+end_src

   接着会检查:

   #+begin_src python
     if mydata is None:
         # 运行元数据生成过程
         ...
   #+end_src

   这说明 Portage 并不需要每次查询都加载 ebuild. 首先会尝试复用缓存，只有缓存不存在或不能通过验证时才需要生成元数据。

2. Python: 启用元数据生成阶段
   继续进入: [[https://github.com/gentoo/portage/blob/master/lib/_emerge/EbuildMetadataPhase.py#L53]]

   找到 ~EbuildMetadataPhase._async_start()~, 它会调用:

   #+begin_src python
     retval = doebuild(
         ebuild_path,
         "depend",
         settings=settings,
         # 其他参数略
     )
   #+end_src

   注意这里的 ~"depend"~, 它是 Portage 内部提取元数据的阶段，不等于 ~DEPEND~ 依赖变量。

   随后 Python 会通过构建执行逻辑准备环境，启动对应的 Bash 处理流程。

3. Bash: 真正加载 ebuild

   进入: [[https://github.com/gentoo/portage/blob/master/bin/ebuild.sh]]

   这里会 ~source "${EBUILD}"~ ，这个调用将 ebuild 加载进 bash 环境，之后 Portage 检查已定义的阶段函数，并在 ~depend~ 阶段收集变量，例如:

   #+begin_src shell
     DEPEND
     RDEPEND
     SLOT
     SRC_URI
     LICENSE
     KEYWORDS
     IUSE
     DEFINED_PHASES
   #+end_src

   收集到的元数据通过专门的文件描述符传回 Python 进程，而不是依赖解析器直接解析 Bash 语法。当 Python 收到 ~RDEPEND~ 时， Bash 中的 ~src_compile()~ 根本没有作为构建阶段被执行。

4. Python: 重新接收 Bash 的结果

   回到 ~EbuildMetadataPhase.py~, 会发现 Python 读取管道中的文本，并按照 ~key=value~ 的格式转换为字典。

   其核心逻辑可以概括为:

   #+begin_src python
     metadata = {}
     for line in metadata_lines:
         key, value = line.split("=", 1)
         metadata[key] = value
   #+end_src

   这样，Bash 中的 ~RDEPEND="dev-libs/openssl"~ 最终就能成为 Python 可以处理的元数据:
   #+begin_src python
     {
         "RDEPEND": "dev-libs/openssl"
     }
   #+end_src

   之后由依赖解析器进一步解释这个字符串，而不是将它当作普通 Python 代码执行。

** Portage 依赖模型

考虑下面这个 ~ebuild~:

#+begin_src shell
  EAPI=B
  IUSE="ssl"

  if [[ ${USE} == *ssl* ]]; then
      RDEPEND="dev-libs/openssl"
  fi
#+end_src

这段代码不符合 ebuild 规范。它试图在加载 ebuild 时，根据当前环境中的 ~USE~ 变量决定元数据的内容。但问题在于， **生成 ebuild 元数据时，最终启用的 USE flags** 尚未确定。因此，这种在全局作用域生成 ~RDEPEND~ 的写法并不符合规范。

但是 Gentoo 的 Package manager Specification(PSM) 要求 ebuild 元数据应当独立于具体系统、 profile 和构建阶段。元数据缓存甚至可以在另一台机器上生成。

因此，正确的写法应该是:

#+begin_src shell
  EAPI=8
  IUSE="ssl"

  RDEPEND="ssl ? ( dev-libs/openssl )"
#+end_src

Bash 在加载 ebuild 时，只负责保存字符串。此时 ~RDEPEND~ 始终是 ~ssl ? ( dev-libs/openssl )~, Portage 后续进行依赖解析时，才根据 USE flags 来判断这项依赖是否生效。
这是 portage 自己的解析语法，具体是:

#+begin_export ascii
ssl? ( dev-libs/openssl )
│      └─────────────┘
│            │
│         依赖包
│
└── USE 条件
#+end_export

这样，就可以在解析依赖关系时就确定元数据。

两种写法主要有下面的差别:

|                    | Bash条件判断    | Portage 条件依赖 |
|--------------------+---------------+----------------|
| 何时判断题条件        | 加载 ebuild 时 | 解释依赖关系时    |
| 元数据是否随USE改变   | 是            | 否             |
| 能否安全地缓存元数据   | 不符合规范要求   | 可以            |
| 是否属于规范支持的写法 | 否            | 是             |


*** USE flags 的完整模型

假设我们开发一个名为 ~app-misc/hello~ 的软件，拥有两个可选功能:

#+begin_src shell
  IUSE="ssl debug"
#+end_src

~IUSE~ 表示这个 ebuild 支持这两个选项，并不意味着它们已经启用。

决定软件包有效 USE 状态的因素包括:

- ebuild 中的 ~IUSE~ 及其默认键位
- Profile 提供的默认选项、强制或屏蔽设置
- ~/etc/portage/make.conf~ 中的全局 USE 配置
- ~/etc/portage/package.use~ 中针对软件包的设置


Portage 需要把它们组合起来，确定当前软件包的有效USE集合。 Profile 的强制与屏蔽限制也必须得到满足。

条件依赖是一种声明式表达式。假设 ebuild 写了:

#+begin_src shell
  RDEPEND="
    sys-libs/zlib
    ssl ? ( dev-libs/openssl )
    !ssl ? ( app-arch/xz-utils )
  "
#+end_src

语法理解为:

- ~sys-libs/zlib~: 无条件依赖
- ~ssl ? (...)~: 当 ssl 启用时纳入内部依赖
- ~!ssl ? (...)~: 当 ssl 禁用时纳入内部依赖


同一个 ebuild 文件，同一份元数据，可以对应不同的 USE 配置。 Portage 不需要重新执行 ebuild 来重新生成一份依赖声明。这就是 **声明与求值分离** 的意义。

下面开始理解 Portage 的依赖分类

*** 5种依赖变量

| 变量       | 用途                      | 典型例子               |
|-----------+--------------------------+----------------------|
| ~BDEPEND~ | 构建机器需要执行的工具       | pkg-config, 代码生成器 |
| ~DEPEND~  | 构建目标程序需要的库与头文件  | OpenSSL 开发库        |
| ~RDEPEND~ | 程序运行期间需要的依赖       | 动态链接库、运行时解释器  |
| ~PDEPEND~ | 可以在主包之后安装的运行时依赖 | 用于处理特定依赖循环     |
| ~IDEPEND~ | 按抓功能和卸载阶段执行的工具  | 更新桌面数据库的工具     |


~BDEPEND~ 和 ~DEPEND~ 都和构建有关系，但它们区分的是 **CBUILD(执行构建的系统)** 与 **CHOST(目标软件运行的系统)** 。

在本机原生编译时，这两个系统通常相同，但在交叉编译时，它们可能完全不同。

例如下面这个 ebuild:

#+begin_src shell
  EAPI=8

  IUSE="ssl"

  BDEPEND="virtual/pkgconfig"

  DEPEND="
    sys-libs/zlib
    ssl ? ( dev-libs/openssl )
  "

  RDEPEND="${DEPEND}"
#+end_src

- 需要 pkg-config 这个构建工具
- 编译时需要 zlib, 启用 ssl 时还需要 openssl
- 运行时同样需要对应的库
** 依赖表达式

Portage 的依赖表达式有自己的语法，可以看成一门小型的声明式语言。
*** Package Atom: 描述软件包的候选集合

比如:

#+begin_export ascii
dev-libs/openssl
>=dev-libs/openssl-3.0
dev-libs/openssl:0
dev-libs/openssl[asm]
#+end_export

这些被称为 package Atom, 分别约束软件包名称、版本、SLOT、和USE状态。

注意: ~dev-libs/openssl[asm]~ 中的 ~asm~ 是对 OpenSSL 这个被依赖包的 USE flag 提出的要求，和 ~RDEPEND="ssl? ( dev-libs/openssl )"~ 的写法要区分开。后者的 ~ssl~ 是对当前 **ebuild** 自己的 USE 状态进行条件判断。
*** 组合逻辑

Portage 支持把多个 Atom 组合成逻辑表达式。

- ~A B~: A 和 B 都要满足
- ~foo? ( A )~: 当前包启用 ~foo~ 的时候需要依赖 ~A~
- ~!foo? ( A )~: 当前包禁用 ~foo~ 的时候需要依赖 ~A~
- ~|| ( A B )~: ~A~, ~B~ 至少满足一个
- ~!A~: 弱阻止依赖 ~A~ 的匹配包
- ~!!A~: 强组织依赖 ~A~ 的匹配包

** ~use_reduce()~

我们可以阅读 portage 的一个具体函数:

[[https://github.com/gentoo/portage/blob/master/lib/portage/dep/__init__.py][portage/dep/__init__.py]] 观察这里面的 ~use_reduce~ 函数。

这个函数的函数签名是:

#+begin_src python
  def use_reduce(
      depstr: str,
      uselist=(),
      masklist=(),
      matchall: bool=False,
      excludeall=(),
      is_src_uri: bool = False,
      eapi: Optional[str] = None,
      opconvert: bool = False,
      flat: bool = False,
      is_valid_flag=None,
      token_class=None,
      matchnone: bool = False,
      subset=None,
  ):
      """
      Takes a dep string and reduces the use? conditionals out, leaving an arry with
      subarrys. All redundant brackets are removed.
      """
#+end_src

这个函数主要的工作，就是根据指定的 USE 集合，对条件依赖表达式进行求值与规约。例如，是如:

#+begin_export ascii
sys-libs/zlib
ssl? ( dev-libs/openssl )
!ssl? ( app-arch/xz-utils )
#+end_export

以及有效的 USE 集合:

#+begin_src python
  {"ssl"}
#+end_src

那么条件规约之后，就会留下:
#+begin_export ascii
sys-libs/zlib
dev-libs/openssl
#+end_export

~use_reduce()~ 并没有执行安装，也没有决定安装 Openssl 的哪个具体版本。它只是完成了解析过程中的一部分工作。

我们可以直接调用 Portage 的 API:

#+begin_src shell :results output 
  python ./myuf.py
#+end_src

#+RESULTS:
: USE: {'ssl'}
: Dependencies: ['sys-libs/zlib', 'dev-libs/openssl']
: USE: set()
: Dependencies: ['sys-libs/zlib', 'app-arch/xz-utils']

~flat=True~ 用于将结果展平为列表。

我们继续阅读代码，看到 ~use_recuce()~ 的结果是通过 ~_use_reduce_cached()~ 实现的。其中，nested function ~is_active()~ 用于决定一个给定的 use conditional 是否 active:

#+begin_src python
  def is_active(conditional: str):
      """
      Decides if a given use conditional is active
      """
      if conditional.startwith("!"):
          flag = conditional[1:-1]
          is_negated = True
      else:
          flag = conditional[:-1]
          is_negated = False

      if is_valid_flag:
          if not is_valid_flag(flag):
              msg = f"USE flag '{flag}' referenced in conditional '{conditional}' is not in IUSE"
              e = InvalidData(msg, category="IUSE.missing")
              raise InvalidDependString(msg, errors=(e,))
      else:
          if useflag_re.match(flag) is None:
              raise InvalidDependString(f"invalid use flag '{flag}' in conditional '{conditional}' ")

      if is_negated and flag in excludeall:
          return False
      if flag in masklist:
          return is_negated
      if matchall:
          return True
      if matchnone:
          return False
      return (flag in uselist and not is_negated) or (
          flag not in uselist and is_negated
      )
#+end_src

这一段逻辑其实很直观。首先就是取得这个 flag, 然后判断是否是合法的 flag. 如果合法会依次检查是否 ~is_negated~, flag 是否在 ~masklist~ 中，是否已经 ~matchall~, 是否 ~matchnone~, 最后再返回一个 bool 值。核心判断就是 ~flag~ 在 ~uselist~ 且没有 ~negated~ 则返回 ~True~

** 从表达式到依赖图

依赖处理路径是:

1. 原始依赖表达式: 读取RDEPEND, DEPEND 元数据
2. ~use_reduce()~: 按 USE 条件解析、规约依赖表达式
3. Atom 匹配与依赖选择: 考察哪些候选包能满足依赖约束
4. ~depgraph~: 综合多个包的依赖、版本、冲突与安装顺序
