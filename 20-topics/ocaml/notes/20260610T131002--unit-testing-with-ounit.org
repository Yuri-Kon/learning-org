* 总述
本节的目标是把 OCaml 的学习方式从 *REPL* 观察推进到 *可重复验证* 。 CS3110 在 3.3 用 OUnit2 演示 ~open OUnit2~ 、测试用例、测试套件、 ~assert_equal~ 、 ~run_test_tt_main~ 等基本结构； OUnit 本身是 OCaml 的 xUnit 风格测试框架，用于命名、组织并自动运行测试。 ~let () = ...~ 用于表达副作用型入口、 ~dune~/~opam~ 是项目工程化工具，这正好是测试文件运行方式的基础。


* OUnit2 的基础
在 OCaml 中， ~OUnit2~ 是标准的单元测试框架，类似于 Python 的 ~unittest~ 或 Java 的 JUnit 。其核心目标是：
- 可自动运行测试，不依赖人工输入或观察结果
- 精确断言，能够验证函数输出、异常等
- 测试套件组织，方便管理大量测试
- 支持测试驱动开发 (TDD) ，即先写测试再写实现

* 单元测试的对象

单元测试不是运行整个应用，而是验证一个很小的功能。比如:

#+begin_src ocaml
  sum [] = 0
  sum [1; 2] = 3
  next_weekday Monday = Tuesday
#+end_src
这非常适合 OCaml ，因为 OCaml 中大量函数是纯函数：相同输入总是相同输出，没有隐藏状态。比如 ~sum~ 这个函数：

#+begin_src ocaml
  let rec sum = function
    | [] -> 0
    | x :: xs -> x + sum xs
#+end_src
它是一个典型列表递归函数。这类函数的测试非常自然:

#+begin_src ocaml
  assert_equal 0 (sum [])
  assert_equal 1 (sum [1])
  assert_equal 3 (sum [1; 2])
#+end_src
这里有一个重要顺序:
#+begin_src ocaml
  assert_equal expected actual
#+end_src
第一个参数是你期望得到的值，第二个参数是实际代码算出来的值。 CS3110 特别指出，失败输出里的 ~expected: ... but got: ...~ 就依赖这个顺序。


* OUnit2 的三个核心结构

OUnit2 的最小结构是:

#+begin_src ocaml
  open OUnit2

  let tests =
    "suite name" >::: [
        "case name" >:: (fun _ -> assert_equal expected actual);
      ]

  let () =
    run_test_tt_main tests
#+end_src
这里有三个东西需要记住。

~>::~ 把一个字符串名字和一个测试函数组合成测试用例:
#+begin_src ocaml
  "case name" >:: (fun _ -> assert_equal 0 (sum []))
#+end_src
测试函数的参数是 OUnit 提供的 text context 。多数初级测试不需要它，所以写成 ~_~ 。

~>:::~ 把一个字符串名字和测试用例列表组合成测试套件:
#+begin_src ocaml
  "test suite for sum" >::: [
      ...
    ]
#+end_src

~run_test_tt_main~ 执行整个测试套件，并把成功、失败、异常等结果打印出来。 CS3110 的示例中，失败时开头的 ~FFF~ 表示三个测试都 failed:

#+begin_example
FFF
==============================================================================
Error: test suite for sum:2:two_elements.

File ".../_build/oUnit-test suite for sum-...#01.log", line 9, characters 1-1:
Error: test suite for sum:2:two_elements (in the log).

Raised at OUnitAssert.assert_failure in file "src/lib/ounit2/advanced/oUnitAssert.ml", line 45, characters 2-27
Called from OUnitRunner.run_one_test.(fun) in file "src/lib/ounit2/advanced/oUnitRunner.ml", line 83, characters 13-26

not equal
------------------------------------------------------------------------------
#+end_example
第一行 ~FFF~ 的告诉我们三个测试都失败；

第二行 ~Error: test suite for sum:two_elements~ 告诉我们这里的测试套件名称是: ~test suite for sum~ ， ~index~ 的名称是 ~two_elements~ 。

* 优化 OUnit 的输出
我们使用 ~~printer~ 添加给 ~assert_equal~ 。它是一个把结果转化为字符串的函数

在我们的示例中，如果 ~sum~ 有bug的话，会下面的输出：

#+begin_example
==============================================================================
Error: test suite for sum:2:two_elements.
...
not equal
------------------------------------------------------------------------------
#+end_example
这里， ~not equal~ 在 OUnit 中意味着 ~assert_equal~ 发现传递给它的两个值在当前的测试用例中不相等。如果我们还想要进一步知道为什么他们不相等，以及想要知道 ~sum~ 的实际输出到底是什么，那么我们需要传递一个额外的参数 ~~printer~ 给 ~assert_equal~ :
#+begin_src ocaml
  let tests = "test suite for sum" >:::
  let tests = "test suite for sum" >::: [
        "empty" >:: (fun _ -> assert_equal 0 (sum []) ~printer:string_of_int);
        "singleton" >:: (fun _ -> assert_equal 1 (sum [1]) ~printer:string_of_int);
        "two_elements" >:: (fun _ -> assert_equal 3 (sum [1; 2])~printer:string_of_int);
      ]

  let _ = run_test_tt_main tests
#+end_src

我们就得到了更详细的提示:
#+begin_example
==============================================================================
Error: test suite for sum:2:two_elements.
...
expected: 3 but got: 4
------------------------------------------------------------------------------
#+end_example
这个输出意味着名为 ~two_elements~ 的测试断言了3和4相等。期望输出是 ~3~ ，实际输出是 ~4~ 。

注意到我们上面的测试套件含有很多重复的代码。尤其是我们需要为每一行都写 ~printer~ 。我们可以改进为下面的结构：

#+begin_src ocaml
  let make_sum_test name expected_output input =
    name >:: (fun _ -> assert_equal expected_output (sum input) ~printer:string_of_int)

  let tests = "test suite for sum" >::: [
        make_sum_test "empty" 0 [];
        make_sum_test "singleton" 1 [1];
        make_sum_test "two_elements" 3 [1; 2];
      ]
#+end_src
而对于比整数更复杂的输出类型，我们最终会需要自己编写传递给 ~printer~ 的函数。这有点类似 Java 中的 ~toString()~: 对于自己定义的复杂类型，语言并不知道如何将他们转化为字符串。因此必须有我们提供转化函数。

* 测试驱动开发 (Test-Driven Develop)

测试并不仅仅发生在编写代码之后。在 /test-driven development (TDD)/ 中，测试先行。它强调代码的 /增量 (incremental)/ 开发：总有需要被测试的内容。测试并不是在实现之后才进行的；相反， /持续的测试 (continuous testing)/ 需要尽早发现错误。因此，当写代码的时候就应该立即书写测试单元测试。自动化测试套件很重要，因为这样持续的测试就不再需要很多的精力。

下面是一个 TDD 的例子。我们特意选择了一个十分简单的函数去实现，因为其过程很清晰。假设我们在处理:

#+begin_src ocaml
  type day = Sunday | Monday | Tuesday | Wednesday | Thursday | Friday | Saturday
#+end_src
同时我们希望写一个函数: ~next_weekend : day -> day~ ，返回给定天的下一个工作日。我们可以从一个未实现的函数开始:
#+begin_src ocaml
  let next_weekday d = failwith "Unimplemented"
#+end_src
如果这时候我们就进行编译 ~dune build~ 的话，编译器对这个函数就会报错:

#+begin_example
File "weekday.ml", line 3, characters 17-18:
3 | let next_weekday d = failwith "Unimplemented"
                     ^
Error (warning 27 [unused-var-strict]): unused variable d.
#+end_example
意思是，我们在函数中声明的参数并没有被使用。

然后我们可以写一个最简单的单元测试。比如:

#+begin_src ocaml
  let tests_for_weekday = "test suite for next_weekday" >::: [
      "tue_after_mon" >:: (fun _ -> assert_equal Tuesday (next_weekday Monday));
    ]
#+end_src
这个测试只用来测试，周一之后是周二。为了令这个测试通过，我们可以修改 ~next_weekday~:

#+begin_src ocaml
  let next_weekday d =
    match d with
    | Monday -> Tuesday
    | _ -> failwith "Unimplemented"
#+end_src

接着我们运行测试，可以看到通过了。

接下来，我们继续添加更多的测试用例。最简单的方案是只添加工作日的天数，所以我们修改测试为:

#+begin_src ocaml
  let tests_for_weekday = "test suite for next_weekday" >::: [
      "tue_after_mon" >:: (fun _ -> assert_equal Tuesday (next_weekday Monday));
      "wed_after_tue" >:: (fun _ -> assert_equal Wednesday (next_weekday Tuesday));
      "thu_after_wed" >:: (fun _ -> assert_equal Thursday (next_weekday Wednesday));
      "fri_after_thu" >:: (fun _ -> assert_equal Friday (next_weekday Thursday));
    ]
#+end_src

于是，我们需要添加新功能:
#+begin_src ocaml
  let next_weekday d =
    match d with
    | Monday -> Tuesday
    | Tuesday -> Wednesday
    | Wednesday -> Thursday
    | Thursday -> Friday
    | _ -> failwith "Unimplemented"
#+end_src
这一次，我们通过了测试用例。

我们的下一步应该是处理周日的情况，但是在此之前，我们注意到测试代码也包含了很多重复的部分。于是我们应该重构这一部分:

#+begin_src ocaml
  let make_next_weekday_test name expected_output input =
    name >:: (fun _ -> assert_equal expected_output (next_weekday input))

  let tests_for_weekday = "test suite for next_weekday" >::: [
        make_next_weekday_test "tue_after_mon" Tuesday Monday;
        make_next_weekday_test "wed_after_tue" Wednesday Tuesday;
        make_next_weekday_test "thu_after_wed" Thursday Wednesday;
        make_next_weekday_test "fri_after_thu" Friday Thursday;
      ]

#+end_src
现在我们可以继续补全周末的测试用例:

#+begin_src ocaml
  make_next_weekday_test "mon_after_fri" Monday Friday;
  make_next_weekday_test "mon_after_sat" Monday Saturday;
  make_next_weekday_test "mon_after_sun" Monday Sunday;
#+end_src

然后我们可以补全我们的函数：

#+begin_src ocaml
  let next_weekday d =
    match d with
    | Monday -> Tuesday
    | Tuesday -> Wednesday
    | Wednesday -> Thursday
    | Thursday -> Friday
    | Friday -> Monday
    | Saturday -> Monday
    | Sunday -> Monday
#+end_src


当然，对于这个函数，大多数人不用 TDD 也能完成。但是我们很少会写如此 简单的函数。

下面让我们回顾一下 TDD 的流程:
1. 编写一个会失败的测试用例。运行测试套件证明用例会失败。
2. 实现仅仅能够满足这个测试用例的功能。运行测试用例证明测试通过。
3. 按需改进代码。在上面的例子中我们重构的是功能，但是一般我们需要重构功能。
4. 重复上述步骤，知道你能确认测试套件能够证明你的实现是对的。
