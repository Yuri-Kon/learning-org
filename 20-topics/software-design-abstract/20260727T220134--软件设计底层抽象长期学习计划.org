* 这套计划要解决什么问题

这不是一套“学习设计模式、背诵架构名词”的计划，也不是一套单纯的语言进阶路线。

它要建立的是一套可以跨语言、跨项目迁移的软件设计认识框架：

1. 能从状态、数据、身份、时间、权限、效应和成本分析一个系统；
2. 能解释类、接口、继承、闭包、异常、协程、线程、事务等机制为什么存在；
3. 能区分语法便利、库约定、运行时保证、类型保证和数学保证；
4. 能把业务要求逐层转化为状态模型、数据表示、模块边界、协议和验证方法；
5. 能观察抽象在真实机器上的代价：内存、缓存、系统调用、调度、复制和同步；
6. 能针对变化、失败、并发、兼容性和可诊断性设计，而不只针对“正常运行”；
7. 能在 C++ 与 Python 中完成主要实践，并用 Rust、Go 对照不同语义选择；
8. 最终形成自己的设计判断，而不是依赖模式名称和框架惯例。

本计划的基本推导路径为：

#+begin_example
系统目标与约束
  -> 数据、状态、身份与时间
  -> 合法状态与合法转移
  -> 模块隐藏的知识
  -> 所有权、权限与副作用
  -> 控制流、接口契约与组合规律
  -> 运行时表示与成本
  -> 失败、并发、恢复与演化
  -> 测试、测量、模型与证据
#+end_example

* 对原计划的结构性修正

** 保留的部分

原计划中以下思想应继续保留：

- 从不变量、契约、表示独立和所有权切入，而不是从设计模式切入；
- 维护少量持续演化的项目，而不是不断创建无关玩具；
- 在 C++、Python、Rust、Go 之间做语义对照；
- 逐渐从示例测试升级到性质测试、状态机测试和模型检查；
- 每隔一段时间进行设计复盘并记录 ADR。

** 必须补上的部分

原计划对“领域建模、分布式系统、形式化验证”投入过早、过重，却缺少几层关键桥梁：

1. 机器与运行时：对象怎样落入内存，函数怎样调用，引用为何失效，系统调用、虚拟内存、缓存和调度如何影响设计；
2. 程序语言语义：名字绑定、环境与存储、求值顺序、闭包、异常、可变状态、模块和多态怎样组成语言机制；
3. 数据表示与复杂度：容器、布局、索引和算法成本怎样反过来限制抽象；
4. 控制流与事件系统：回调、Observer、事件循环、协程、取消、重入和线程亲和性；
5. 调试、性能与可观测性：如何根据证据认识程序，而不是只依靠设计时推理；
6. 演化与兼容性：接口、数据格式、数据库模式和模块边界如何随时间变化；
7. 与现实工作的连接：Qt/PySide、诊断工具、后台任务、UI 状态同步和可诊断性。

** 降低的部分

- Rust 不作为第二个完整主项目，而作为“所有权、和类型、trait、并发安全”的对照实验；
- Go 主要承担并发协议和服务边界实践，不泛化为完整应用主线；
- 分布式系统放到本地并发、持久化和故障模型之后；
- Alloy、TLA+ 和证明助手不再是固定 KPI，而是针对已经遇到的高风险问题使用；
- 每阶段不再同时阅读多本主教材。

* 统一知识地图：十二个底层概念

以后遇到 OOP、设计模式、框架或语言机制时，优先用以下概念解释。

** 状态与转移

- 系统此刻知道什么；
- 哪些状态合法；
- 哪些操作改变状态；
- 操作顺序、重复、失败和竞争会产生什么结果。

对应：类不变量、State 模式、事务、状态机、协议、typestate。

** 数据与表示

- 抽象值怎样由具体位、字段、节点、表和索引表示；
- 表示改变后，哪些客户端不应受影响；
- 表示选择带来什么时间和空间成本。

对应：ADT、封装、representation invariant、缓存局部性、序列化。

** 值、身份与时间

- 两个对象何时相等；
- 复制意味着什么；
- 同一实体在不同时刻如何表示；
- 快照、版本和历史怎样区分。

对应：值对象、实体、revision、event、snapshot、MVCC。

** 所有权、别名与权限

- 谁负责资源生命周期；
- 谁可以读、写、转移、共享或观察；
- 别名怎样制造局部推理困难。

对应：RAII、unique_ptr、borrow、const、capability、Qt parent-child。

** 抽象与信息隐藏

- 模块真正隐藏的是哪项可能变化的设计决策；
- 客户端可以观察什么；
- 哪些知识不应穿过边界。

对应：module、package、adapter、pImpl、facade、deep module。

** 替换、契约与精化

- 一个实现能否在所有允许的上下文中替换另一个；
- 输入、输出、错误、副作用、复杂度和时序承诺是什么；
- 子类型是否保留超类型可证明的性质。

对应：Protocol、interface、trait、concept、LSP、契约测试。

** 组合与代数结构

- 操作是否可结合、交换、重复、合并或增量执行；
- 组合是否保持性质；
- 顺序是否构成可观察语义。

对应：pipeline、monoid、idempotence、commutativity、monotonicity。

** 控制流与效应

- 谁决定下一步执行什么；
- 回调、异常、迭代器、协程和事件循环怎样改变控制权；
- 一个依赖向代码授予了什么外部能力。

对应：Command、Observer、Strategy、exception、async、dependency injection。

** 并发与协调

- 哪些状态被共享；
- 哪些动作需要原子性、互斥、顺序或通知；
- 取消、关闭、背压和公平性怎样进入协议。

对应：mutex、channel、actor、worker pool、structured concurrency。

** 失败与恢复

- 失败发生在哪个边界；
- 已经发生了多少副作用；
- 能否重试、补偿、回滚、降级或继续部分工作。

对应：异常安全、Result、retry、transaction、saga、circuit breaker。

** 成本与资源预算

- 抽象产生多少分配、复制、间接跳转、锁竞争、系统调用和 I/O；
- 延迟、吞吐、内存和响应性之间如何权衡；
- 是否已有测量证据。

对应：复杂度、cache、benchmark、profiling、zero-cost abstraction。

** 演化与证据

- 需求、接口、数据和实现怎样随时间改变；
- 如何知道设计正确、可维护、足够快、可诊断；
- 哪些结论来自测试、类型、模型、基准或生产观测。

对应：compatibility、migration、ADR、property test、sanitizer、trace、model checking。

* 学习方法：四层闭环

每个主题都必须经过以下四层，不能只阅读抽象，也不能只写代码。

** 概念模型

回答：

- 它解决什么不可避免的问题？
- 最小模型是什么？
- 关键不变量和反例是什么？
- 它与哪些相邻概念容易混淆？

** 语言机制

至少比较 C++ 与 Python；必要时加入 Rust 或 Go：

- 语法如何表达；
- 检查发生在编译期、运行时还是完全依赖纪律；
- 对象布局、生命周期和调用成本是什么；
- 哪些非法程序会被拒绝，哪些仍可运行。

** 项目决策

在现有项目中回答：

- 当前具体问题在哪里；
- 有哪些候选设计；
- 为什么选择某一方案；
- 这个决定在什么条件下失效。

** 运行证据

至少取得一种证据：

- 单元测试或契约测试；
- 性质测试；
- sanitizer 或静态分析；
- trace、日志或调试器观察；
- benchmark 或 profiler；
- Alloy/TLA+ 反例。

* 阶段 2：机器模型、数据表示、内存与生命周期

时间：10 周。

这是原计划最重要的新增阶段。

** 核心问题

- 源代码中的对象、引用、函数调用如何落到机器上；
- 栈、堆、静态存储、虚拟内存和页是什么；
- cache locality 为什么影响数据结构设计；
- C++ 未定义行为、悬空引用和失效从何而来；
- Python 对象、引用、容器和垃圾回收隐藏了哪些成本；
- RAII 与 Rust ownership 分别替程序员承担什么责任。

** 主材料

- Computer Systems: A Programmer's Perspective：机器级程序、优化、存储器层次、异常控制流、虚拟内存、系统级 I/O；
- Operating Systems: Three Easy Pieces：Virtualization、Concurrency、Persistence 中的基础章节；
- Rust Book：第 4、15 章；
- C++ Core Guidelines：Resource Management、Memory Management。

** 实验

- 用 C 实现动态数组、链表、arena、简单引用计数；
- 制造 use-after-free、double free、越界和引用失效；
- 使用 ASan、UBSan、Valgrind 观察错误；
- 使用 objdump、nm、readelf、gdb 观察函数、符号、栈帧和对象布局；
- 比较 AoS 与 SoA、连续容器与节点容器的缓存行为；
- 用 Python 的 sys.getsizeof、tracemalloc、dis 观察对象和字节码，但不把这些实现细节误当语言规格。

** 项目实践

- C++ Pipeline 增加大数据量 benchmark；
- 比较 vector、deque、list 或不同 map 表示；
- 分析 string、string_view、自引用 append 和扩容失效；
- 在 Rust 中重写 Repository 或 Snapshot 核心。

** 退出标准

- 能从接口推断主要生命周期风险；
- 能解释一个抽象为什么快或慢，而不是只说“零成本”；
- 能使用运行工具证明一次内存或布局判断。

* 阶段 3：模块、类型、接口、替换与设计模式解构

时间：10 周。

** 核心问题

- 模块应该按执行步骤还是按隐藏的设计决策划分；
- 类型怎样约束合法程序；
- 名义子类型、结构子类型和泛型约束有什么差异；
- 方法签名兼容为什么不等于行为可替换；
- OOP 模式背后究竟在管理哪种变化、权限或控制流。

** 主材料

- Parnas：On the Criteria To Be Used in Decomposing Systems into Modules；
- A Philosophy of Software Design：复杂性、深模块、信息泄漏、通用接口；
- Liskov/Wing：A Behavioral Notion of Subtyping；
- Domain Modeling Made Functional：类型驱动工作流与错误建模；
- MIT 6.005 的接口、相等、函数式编程部分。

** 设计模式解构表

每两周研究一个模式，不以背 UML 为目标：

*** Strategy

底层问题：把可替换决策作为值或能力传入。

比较：虚基类、Protocol、Callable、模板参数、Rust closure。

*** Observer

底层问题：一对多通知、时间耦合、重入、生命周期和错误传播。

比较：Qt signal/slot、callback list、event bus、reactive stream。

*** State

底层问题：状态相关行为和合法转移。

比较：if/Enum、状态表、对象多态、sum type、typestate。

*** Iterator

底层问题：将遍历控制权与容器表示分离。

比较：外部迭代器、内部迭代器、generator、range/view、visitor。

*** Adapter / Facade

底层问题：隔离外部表示和变化，压缩接口表面积。

*** Command

底层问题：把未来执行、排队、撤销、重试和审计所需的信息对象化。

** 项目实践

- 对 MergeStrategy 同时实现 Protocol 版本和 Callable 版本；

- 能不用模式名称解释模式；
- 能在对象、函数、泛型、和类型与表驱动之间选择；
- 能发现表示泄漏、时序耦合和行为不兼容。

* 阶段 4：程序语言语义、控制流、效应与错误

时间：10 周。

这是第二个关键新增阶段。

** 核心问题

- 表达式如何求值；
- 环境、存储和对象状态有什么区别；
- 词法作用域、闭包和动态分派如何工作；
- 异常、回调、迭代器、协程如何转移控制权；
- 纯函数和效应ful 操作怎样组合；
- 错误是值、异常、状态还是事件。

** 主材料

- Programming Languages: Application and Interpretation（PLAI）：解释器、作用域、函数、状态、对象相关章节；
- Crafting Interpreters：树遍历解释器、闭包、类、字节码虚拟机和 GC 的选读；
- Cornell CS 3110 材料：代数数据类型、模块、求值模型和类型系统；
- Python Language Reference：data model、execution model；
- C++ 关于异常、lambda、coroutine 的权威文档和标准库资料。

** 实验

实现一个小解释器，只需支持：

- 数字和布尔值；
- let 绑定；
- 函数与闭包；
- 可变 cell；
- 一个错误机制。

然后观察加入可变状态前后，环境模型怎样变化。

** 项目实践

- 将 PDF 项目分成 pure core 与 effectful shell；
- 为文件、网络、时钟、日志、随机数和调度建立明确边界；
- 比较异常、Result、部分结果和 Failed 状态；
- 记录每种错误是否可重试、是否已产生副作用、是否需要用户介入。

** 退出标准

- 能解释闭包、对象和模块的共同点与差异；
- 能画出复杂回调/异常路径的控制流；
- 能说明一个依赖授予了哪些能力和副作用。

* 阶段 5：事件驱动 GUI、Qt 对象模型与诊断工具设计

* 阶段复盘问题

每次整合周回答：

1. 当前系统的抽象值是什么，具体表示是什么？
2. 哪些状态非法，谁阻止它们出现？
3. 哪些约束只写在注释中？
4. 哪些模块泄漏了本应隐藏的知识？
5. 谁拥有资源，谁只是借用，借用多久？
6. 控制权如何转移，是否存在隐藏回调或重入？
7. 哪些副作用已经发生，失败后能否恢复？
8. 哪些操作依赖顺序，哪些可重复或交换？
9. 当前性能判断有何测量证据？
10. 出错后是否能重建事件链？
11. 接口或数据变化时，哪些客户端会破坏？
12. 测试验证的是样例、性质、协议还是实现细节？
13. Rust 或 Go 的对照是否真正揭示了语义差异？
14. 哪个抽象应该删除，而不是继续包装？

* 计划成功的判断标准

这套计划成功，不是因为读完了多少书，而是因为逐渐形成以下能力：

- 看见一个类时，先问它维护什么状态、身份和不变量；
- 看见继承时，先问替换契约，而不是代码复用；
- 看见设计模式时，能还原它管理的变化、权限和控制流；
- 看见智能指针时，能画出真实所有权和别名关系；
- 看见异步代码时，先写终止、取消、背压和竞争规则；
- 看见高可靠要求时，能拆成故障模型、恢复策略和证据；
- 看见高性能要求时，能提出成本模型并用工具测量；
- 看见跨语言差异时，能区分语法差异、语义差异和实现差异；
- 面对新项目时，能从目标与约束推导模型、边界、协议和验证，而不是先选模式或框架。
