* Part3 概述
本部分回答: *一个类到底应该像什么东西一样被使用、复制、移动、销毁、比较、调用、继承、泛化* 。本章被组织成 copy control, operator, overloading, inheritance, templates, 并强调这些是 class authors 的高级工具。同时，类不仅控制初始化，还控制复制、赋值、移动和销毁，这正是C++与很多语言的根本插一之一。

这里有一个非常重要的抽象:

#+begin_quote
类设计不是“把数据和函数放进class”，类设计是定义一种新类型的语义。
#+end_quote
一个类至少要回答这些问题:
#+begin_src cpp
  T a;
  T b = a; // 可以复制吗？复制后共享资源还是独立资源
  a = b; // 赋值后 a 原来的资源如何处理
  T c = std::move(a); // 可以移动吗？移动后a处于什么状态
  a == b; // 什么叫相等
  a < b; // 是否存在自然顺序
  std::cout << a; // 是否适合输出
  a[i]; // 是否像容器
  a(); // 是否像函数
  Base *p = new Derived;
  delete p; // 通过基类指针销毁是否安全
  template<class T> ... // 对 T 的最小要求是什么
#+end_src
* Copy Control -- 生命周期与所有权
类通过五个特殊成员函数控制对象被 copied, assigned, moved, destoryed 分别发生什么。这五个成员函数分别是:

- copy constructor
- copy-assignment operator
- move constructor
- move-assign operator
- destructor
#+begin_src cpp
  class T {
  public:
    T(const T&); // copy constructor
    T& operator=(const T&); // copy-assignment operator

    T(T&&)noexcept; // move constructor
    T& operator=(const T&&) noexcept; // move-assignment operator

    ~T(); // destructor
  };
#+end_src
** 为什么C++需要 copy control
因为C++的对象通常可以直接拥有资源:
#+begin_src cpp
  class Buffer {
  private:
    char* data_;
    std::size_t size_;
  };
#+end_src
如果编译器默认逐成员复制，结果是:
#+begin_src cpp
  Buffer a;
  Buffer b = a; // b.data_ 和 a.data_ 指向同一块内存
#+end_src
这叫 *shallow copy* . 如果两个对象析构时都发生 ~delete[] data_~, 就会 double delete. 这个问题在 Java, Python 中不常以同样的形式出现，因为它们的对象通常是引用语义并由运行时管理内存；但C++的对象默认是值语义，生命周期和资源释放是语言的一部分。

所以本章的真正问题是:
#+begin_quote
这个类是“值”吗？是“资源句柄”吗？是“共享对象”吗？是“不可复制对象”吗？
#+end_quote
不同的答案决定不同的 copy control 策略。
** 三种典型语义
*** 第一种: 纯值类型, Rule of Zero
例如:
#+begin_src cpp
  class Student {
  public:
    Student(std::string name, std::vector<int> scores)
    : name_{std::move(name)}, scores_{std::move(scores)} {}

  private:
    std::string name_;
    std::vector<int> scores_;
  };
#+end_src
这个类不直接管理裸资源。 ~std::string~ 和 ~std::vector~ 都是封装好的类，它们自己负责资源管理。所以 ~Student~ 不需要写 destructor, copy constructor, move constructor.

这就是现代C++最推荐的 *Rule of Zero*: _能不写特殊成员函数，就不要写。让成员对象自己管理资源_ 。

能避免定义默认操作，就避免定义。如果定义或删除了任何 copy, move, destructor, 就应该定义或删除全部相关操作，以保持语义一致。当类管理裸资源句柄时，不能依赖隐式生成的特殊成员函数，因为默认浅拷贝通常不符合资源所有权语义。

现代C++类设计的第一原则是:
#+begin_src cpp
  // 优先这样
  std::string;
  std::vector<T>;
  std::unique_ptr<T>;
  std::shared_ptr<T>;
  std::fstream;
  std::mutex;
  std::optional<T>;

  // 尽量避免这样:
  T*;
  FILE*;
  int fd;
  new / delete;
  malloc / free;
#+end_src
不是说不能直接用裸资源，而是: *裸资源应该被封装进很小的 RAII 类型中* 。
*** 第二种: 独占资源, move-only
例如文件句柄、socket, mutex, terminal raw mode guard. 这类对象不应被复制，但可以移动:
#+begin_src cpp
  #include <cstdio>
  #include <stdexcept>
  #include <string>
  #include <utility>

  class File {
  public:
    explicit File(const std::string &path)
    : fp_{std::fopen(path.c_str(), "r")} {
      if (!fp_)  {
        throw std::runtime_error{"fail to open file"};
      }
    }

    ~File() {
      if (fp_) {
        std::fclose(fp_);
      }
    }

    File(const File&) = delete;
    File& operator=(const File&) = delete;

    File(File&& other) noexcept
    : fp_{std::exchange(other, fp_, nullptr)} {}

    File& operator=(File&& other) noexcept {
      if (this != &other) {
        if (fp_) {
  	std::fclose(fp_);
        }
        fp_ = std::exchange(other.fp_, nullptr);
      }
      return *this;
    }

  private:
    std::FILE* fp_{nullptr};
  }
#+end_src
这个类的语义是:
#+begin_src cpp
  File f1{"a.txt"};
  File f2 = f1; // error: 不允许复制
  File f3 = std::move(f1); // ok: 资源所有权转移
#+end_src
这也体现了 *move semantics* 的核心: 转移资源所有权。 ~std::move~ 并不会移动任何东西，只是把表达式转化成 xvalue，从而让移动构造或移动赋值有机会被选择。真正“偷资源”的代码发生在 ~File(File&&)~ 和 ~File& operator=(File&&)~ 里。
*** 第三种: 共享资源, shared ownership
比如之前 ~TextQuery~ 的程序中， ~QueryResult~ 和 ~TextQuery~ 都可能共享同一份文本数据，因此会使用 ~std::shared_ptr~, 这种语义并不是 “深拷贝”，而是 “多个对象共同指向同一资源”。
#+begin_src cpp
  class QueryResult {
  public:
    // 多个 QueryResult 可能共享同一份文本
  private:
    std::shared_ptr<std::vector<std::string>> file_;
    std::shared_ptr<std::set<std::size_t>> lines_;
  };
#+end_src
这里默认 copy control 就是合理的: 复制 ~shared_ptr~ 会增加引用计数，不会复制整个文件。

所以 copy control 的关键不是“写不写五个函数”，而是判断:
#+begin_quote
复制这个对象时，用户直觉上是期待独立副本、共享同一套资源、还是禁止复制？
#+end_quote
** Copy, Move 与异常安全
移动操作一般应该标记为 ~noexcept~:
#+begin_src cpp
  T(T&&) noexcept;
  T& operator=(T&&) noexcept;
#+end_src
原因是标准容器在扩容、重排元素时，会根据移动构造是否 ~noexcept~ 来决定是否移动元素；如果移动可能抛出异常，容器为了维持异常安全，可能要回退到复制。这也是现代C++中 ~noexcept~ 与性能直接相关的典型例子。
* Operator Overloading -- 让类型拥有自然接口
本章讨论 overload operators and conversions. 运算符重载允许我们定义类类型作为内置运算符操作数的意义；合理使用可以让程序更易写、更可读。

但 operator overloading 非常容易滥用。它的本质应该是:

#+begin_quote
当某种操作对于用户来说已经有清晰、稳定、无歧义的数学或语言习惯时，才重载运算符。
#+end_quote
例如 ~Money + Money~ 合理， ~Matrix * Matrix~ 合理， ~std::cout << obj~ 合理；但用 ~operator!~ 表示保存文件，用 ~operator+~ 保存发送网络请求，就是坏设计。
** 运算符重载本质上是函数
#+begin_src cpp
  a + b;
#+end_src
本质上可能是:
#+begin_src cpp
  operator+(a, b); // non-member
  a.operator+(b); // member
#+end_src
成员运算符的左操作数绑定到隐式 ~this~, 所以成员运算符显式运算符数量比操作数少一个。

例如:
#+begin_src cpp
  class Money {
  public:
    explicit Money(long long cents):  cents_{cents} {}
    Money& operator+(const Money &rhs) noexcept {
      cents_ += rhs.cents_;
      return *this;
    }
    friend Money operator+(Money lhs, const Money& rhs) noexcept {
      lhs += rhs;
      return lhs;
    }

  private:
    long long cents_{};
  };
#+end_src
为什么 ~operator+~ 常写成非成员? 

因为 ~+~ 是对称操作，用户可能会期待:
#+begin_src cpp
  Money m{100};
  m + Money{50};
  Money{50} + m;
#+end_src
如果涉及隐式转换，非成员函数更容易让左右两边都参与转换。书中也给出类似原则：赋值、下标、调用、箭头必须是成员；复合赋值通常是成员；对称运算符通常是普通非成员函数。
** 哪些运算符应该谨慎或避免
~,~, ~&~, ~&&~, ~||~ 通常不应该重载。因为重载后的 ~&&~ 和 ~||~ 不保留内置版本的 short-circuit evaluation, 即不会短路。

例如内置 ~&&~:
#+begin_src cpp
  p != nullptr && p->valid();
#+end_src
如果 ~p == nullptr~, 右侧不会求值。

但重载 ~operator&&~ 后，它只是一个函数调用，两个参数通常都会先求值。这会破坏用户对语言的基本预期。

因此记住:
#+begin_quote
运算符重载必须服从用户对该运算符的既有直觉。 
#+end_quote
** C++20的现代补充: ~operator<=>~
C++20 引入 three-way comparison, 也就是 spaceship operator:
#+begin_src cpp
  #include <compare>

  class Point {
  public:
    int x{};
    int y{};

    auto operator<=>(const Point&) const = default;
  };
#+end_src
默认生成的 ~<=>~ 可以同时支持一组比较操作。类类型可以 default ~operator<=>~.

不过，是否定义顺序要看语义。 ~Point~ 的相等很自然，但“哪个Point更小”不一定总有业务意义。如果只是为了放进 ~std::set~, 可以定义排序；如果业务上没有自然顺序，也可以只定义 ~==~, 再给容器提供 comparator.
** Conversion Operators: 隐式转换
转换函数可以让类对象隐式转换到其他类型。
#+begin_src cpp
  class Size{
  public:
    explicit Size(int n) : value_{n}{}
    explicit operator int() const { return value_; }

  private:
    int value_{};
  };
#+end_src
现代C++中应该默认使用 ~explicit~, 因为隐式转换很容易发生意外:
#+begin_src cpp
  void resize(Size);

  resize(10); // 如果 Size(int) 不是 explicit, int 会隐式构造 size
#+end_src
* Resources Handle -- 资源句柄
资源句柄是C++资源管理中非常重要的一个概念。
** 什么是 resources(资源)
在程序里，资源不仅仅是内存。

资源指的是:
#+begin_quote
由操作系统、运行库或者外部系统管理，需要申请(acquire)和释放(release)的有限对象。
#+end_quote
通常需要从某个运行环境中获取，使用完后通常需要显式归还的东西。

常见资源包括:
| 资源                    | 获取操作       | 释放操作        |
|-------------------------+-----------------+------------------|
| 动态内存               | ~new~, ~malloc~ | ~delete~, ~free~ |
| C 文件流               | ~std::fopen~    | ~std::fclose~    |
| POSIX 文件描述符       | ~open~          | ~close~          |
| 网络套接字             | ~socket~        | ~close~          |
| 互斥量锁定状态        | ~lock~          | ~unlock~         |
| 操作系统线程           | 创建线程       | ~join~ / 关闭    |
| GPU, 窗口, 数据库连接 | 对应 API 创建  | 对应 API 销毁   |

例如打开文件后，即便只使用了很少的内存，也仍然占用了操作系统的文件表项、缓冲区等资源。因此需要在结束后进行清理以归还。
** 什么是 Handle
句柄是程序用来代表、定位或操作某型资源的一个值。

可以粗略理解为:
#+begin_quote
资源是 “真正的东西”，句柄是程序手里持有的“凭证”或“访问入口”。
#+end_quote

例如:
#+begin_src cpp
  std::FILE *file = std::fopen("data.txt", "r");
#+end_src

这里可以这样划分:

- data.txt 对应已经打开的文件状态、缓冲器等
- 真正的资源 resource
- file, 也就是 std::FILE*
- 程序用于访问该资源的句柄 handle

不能直接在C++代码中操作操作系统内部的文件对象，只能通过 ~file~ 这个值调用:
#+begin_src cpp
  std::fread(..., file);
  std::fprintf(file, ...);
  std::fclose(file);
#+end_src
所以 ~file~ 是程序操作这个资源的入口。
** 句柄不一定是指针
*handle 是一种角色或语义，不是一种固定的C++类型* 。

句柄可能是指针，也可能是整数，甚至可能是某种特殊结构体。

~std::FILE* file~  是指针形式的句柄。

下面的 ~fd~ 是一个整数，但它代表操作系统中的打开文件，所以也是句柄。
#+begin_src cpp
  int fd = ::open("data.txt", O_RDONLY);

  ::read(fd, buffer, size);
  ::close(fd);
#+end_src

Windows ~HANDLE~:
#+begin_src cpp
  HANDLE hFile;
#+end_src

Windows API 直接将很多资源命名为 ~HANDLE~.
** 句柄和资源不是一个东西
例如:
#+begin_src cpp
  std::FILE *p1 = std::fopen("data.txt", "r");
  std::FILE *p2 = p1;
#+end_src
这里复制的是 ~std::FILE*~ 的值:
#+begin_example
p1 ─┐
    ├──> 同一个文件流资源
p2 ─┘
#+end_example

并没有创建第二个文件流 _资源_ 。

所以上述的copy-assignment operator 的意思是：复制了句柄值，但没有复制底层资源。

这与复制普通指针的行为完全一样。现在有了一个新问题: 既然 ~p1~ 和 ~p2~ 都能访问同一个资源，那么到底谁能调用 ~fclose()~ 呢？

如果两者都关闭:
#+begin_src cpp
  std::fclose(p1);
  std::fclose(p2); // UB
#+end_src
第二次关闭会产生 UB.

而如果两者都以为对方关闭了文件，就会造成资源泄露。
** 什么是拥有资源句柄
考虑一个持有文件句柄的类:
#+begin_src cpp
  class UniqueFile {
  public:
      UniqueFile(const char* path, const char* mode);
      ~UniqueFile();

      UniqueFile(const UniqueFile&) = delete;
      UniqueFile& operator=(const UniqueFile&) = delete;

      UniqueFile(UniqueFile&&) noexcept;
      UniqueFile& operator=(UniqueFile&&) noexcept;

      std::FILE* get() const noexcept;

  private:
      std::FILE* file_{nullptr};
  };
#+end_src

这里的 ~private~ 对象 ~std::File* file_~ 是一个底层句柄(raw handle).

而 ~UniqueFile~ 的对象是资源持有者(resource owner):
#+begin_example
UniqueFile 对象
    │
    │ owns
    ▼
std::FILE* 句柄
    │
    ▼
打开的文件流资源
#+end_example

根据我们的析构函数其中负责释放该句柄，很容易看出，“拥有” 并不只能 “能够访问”，而是:
#+begin_quote
~UniqueFile~ 能够承担生命周期结束时释放资源的责任。
#+end_quote

这就是 *RAII*. 对象构造成功后，资源由对象管理；对象析构时，资源自动释放。
** 原始句柄与所有权包装器
可以区分两个层次:
*** 原始句柄(raw handle)
#+begin_src cpp
  std::FILE* ;
  int fd;
  SocketHandle;
#+end_src

这些值本身通常不会自动清理资源。

例如:
#+begin_src cpp
  std::FILE* file = std::fopen(...);
#+end_src
离开作用域时，指针变量 ~file~ 会消失，但是 _它指向的文件流不会自动执行 ~fclose~_ .
*** 拥有型包装器(owning wrapper)
#+begin_src cpp
  UniqueFile file{"data.txt", "r"};
#+end_src

包装器通过析构函数自动执行清理。

标准库中的典型例子是:
#+begin_src cpp
  std::unqiue_ptr<T>
#+end_src

可以理解为:
#+begin_example
裸指针 raw pointer
    +
独占所有权 exclusive ownership
    +
析构时自动 delete
#+end_example
** ~get()~ 返回的是什么
上面结构体中的接口:
#+begin_src cpp
  std::FILE *get() const noexcpet;
#+end_src
通常实现为:
#+begin_src cpp
  std::FILE *UniqueFile::get() const noexcept {
    return file;
  }
#+end_src
这里返回的是 :
#+begin_quote
句柄值的拷贝，而不是资源的拷贝，也不是所有权的转移。
#+end_quote
例如:
#+begin_src cpp
  UniqueFile file{"data.txt", "r"};
  std::FILE *raw = file.get();
#+end_src
此时:
#+begin_example
file.file_ ─┐
            ├──> 同一个文件流资源
raw ────────┘
#+end_example
~raw~ 只是另一个能够访问相同资源的指针值，而文件句柄的所有权仍然属于 ~file~ 。

所以 ~get()~ 的语义一般是:
#+begin_quote
借出底层句柄以供访问，但不转移所有权。
#+end_quote
** ~get~ 和 ~release~ 的语义区别
这两个名字在资源管理非常常见。
*** ~get()~: 观察，不转移所有权
#+begin_src cpp
  std::FILE *raw = file.get();
#+end_src
对象仍然拥有资源。
*** ~release()~: 交出句柄，转移释放责任
假设定义:
#+begin_src cpp
  std::FILE *UniqueFile::release() noexcept {
    return std::exchange(file_, nullptr);
  }
#+end_src

使用:
#+begin_src cpp
  std::FILE* raw = file.release();
#+end_src

结果是:
- ~file.file_ == nullptr~
- ~raw~ 持有原来的句柄

此时的 ~UniqueFile~ 不再负责关闭，调用者必须负责 ~std::fclose(raw)~.

因此:
- ~get()~: 借用句柄，不改变所有权
- ~release()~: 交出句柄，放弃所有权
** 无效句柄(Invalid handle)
句柄类型通常需要某个特殊值表示“当前没有资源”。对于 ~std::FILE*~, 无效值是 ~nullptr~, 所以类可以维护这样的不变量:
- ~file_ == nullptr~: 表示当前不拥有文件资源
- ~file_ != nullptr~: 表示当前拥有一个需要 ~fclose~ 的文件资源


对于 POSIX 文件描述符，常见无效值是: ~-1~. 例如:
#+begin_src cpp
  int fd_{-1};
#+end_src

因此句柄包装器通常需要知道三件事:
1. 句柄类型
2. 无效值
3. 释放操作

这三个信息共同决定了资源管理方式
** 资源句柄小结
#+begin_quote
程序用来标识、访问或操作某项资源的值；它可能是指针、整数或其他类型。句柄本身通常不是资源，复制句柄也不意味着复制资源。
#+end_quote

* OOP -- 运行期多态
OOP 的核心概念可以概括为 data abstraction, inheritance, dynamic binding. 继承可以定义相关类型，动态绑定可以写忽略派生类细节的代码。

C++ 的 OOP 和 Java 有一个非常重要的区别:
#+begin_src cpp
  Java 对象通常天然通过引用使用；C++对象默认是值对象。 \\
  因此C++里的多态必须通过 pointer 或 reference 发生.
#+end_src
C++中的动态绑定发生在通过基类 reference 或 pointer 调用 virtural function 时。
** public inheritance 表示 is-a
#+begin_src cpp
  class Quote {
  public:
    std::string isbn() const;
    virtual double net_price(std::size_t n) const;
    virtual ~Quote() = default;
  };

  class BulkQuote : public Quote {
  public:
    double net_price(std::size_t n) const override;
  }
#+end_src
~BulkQuote : public Quote~ 的意思不是 “复用 Quote的代码”，而是:
#+begin_quote
每个 ~BulkQuote~ 都可以被当作一个 ~Quote~ 使用
#+end_quote
这叫做 *substitutability* . 如果只是想复用函数实现的话，优先考虑 composition:
#+begin_src cpp
  class Window {
  private:
    Rectangle bounds_; // has-a
  }
#+end_src
继承的判断标准是:
#+begin_src cpp
  // 合理:
  class BulkQuote : public Quote {}; // BulkQuote is a Quote
  // 可疑:
  class Stack : public Vector {}; // Stack 不是一般意义上的 Vector
#+end_src
** virtual function 与 override
虚函数 (virtual function) 是基类中用 ~virtual~ 声明的成员函数；当通过基类指针或引用调用它时，程序会根据对象的实际动态类型，在运行时选择调用基类版本还是派生类重写版本。
#+begin_src cpp
  struct Base {
    vitrual void f();
  };

  struct Derived : Base {
    void f() override;
  };

  Base *p = new Derived;
  p->f(); // 调用 Derived::f, 而不是 Base::f
#+end_src
~override~ 是C++11 引入的 *虚函数重写检查标记* ，它的意思是:
#+begin_quote
我声明这个派生类是为了重写基类中的某个虚函数；如果它实际上没有成功重写，请编译器报错。
#+end_quote
它的主要价值是 *防止我们以为自己重写了虚函数，但其实没有重写* 。例如:
#+begin_src cpp
  struct Derive : Base {
    void f(int) override; // error: 少了 const, 不能重写 Base::f
  };
#+end_src
这里如果没有 ~override~, 代码可能仍然编译，但 ~Derived::f(int)~ 会变成一个新的函数，而不是重写 ~Base::f(int) const~. C++ Primer也强调， ~override~ 可以让派生类明确表达 “我要重写继承来的虚函数”，并让编译器帮我们发现参数列表不匹配、基类函数不是虚函数等错误。

虚函数覆盖要求函数名、参数、constness、返回类型、异常说明等都兼容，稍有不一致就可能不是 override.

~virtual~ 开启动态绑定， ~override~ 检查派生类是否真的重写了基类函数。
** virtual destructor
如果一个类要作为多态基类，析构函数通常应该是 virtual:
#+begin_src cpp
  class Shape {
  public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
  };
#+end_src
否则 :
#+begin_src cpp
  Shape *p = new Circle{};
  delete p; // 如果 ~Shape 非 virtual, 行为可能错误
#+end_src
作为继承层次根部的 base class 通常应该定义 virtual destructor, 即便他不做任何工作。基类析构函数要么应当是 public virtual, 要么 protected non-virtual; clang-tidy 的对应检查也说这是为了避免 undefined behavior.
** Object slicing 对象切片
#+begin_src cpp
  BulkQuote bulk;
  Quote q = bulk; // slicing
#+end_src
这里不是多态。 ~bulk~ 的派生部分会被切掉，只剩 ~Quote~ 子对象。这叫 *object slicing* .

所以多态对象不要按值存入容器:
#+begin_src cpp
  std::vector<Quote> basket; // 错: 放入 BulkQuote 会 slicing
#+end_src
应该使用指针，现代C++中通常使用智能指针:
#+begin_src cpp
  std::vector<std::unqiue_ptr<Quote>> basket;
  basket.push_back(std::make_unique<BulkQuote>(...));
#+end_src
上面的例子中， ~q~ 是一个真正的、独立的 ~Quote~ 的对象，初始化 ~q~ 时，会调用 ~Quote~ 的拷贝构造函数，只拷贝 ~bulk~ 里的 *Quote 基类子对象部分* ， ~BulkQuote~ 自己新增的成员，例如折扣、最低购买数量等，会被丢掉。这就是 object sliciing. 从派生类对象初始化或赋值给基类对象时，只有基类部分被复制、移动或赋值，派生类部分被忽略。

而智能指针版本:
#+begin_src cpp
  std::shared_ptr<Quote> p = std::make_shared<BulkQuote>();
#+end_src
这里发生的事两件完全不同的事情:
#+begin_src cpp
  std::make_shared<BulkQuote>();
#+end_src
这一步真的在动态内存里创建了一个完整的 ~BulkQuote~ 对象，然后:
#+begin_src cpp
  std::shared_ptr<BulkQuote> -> std::shared_ptr<Quote>
#+end_src
发生的是 _派生类到基类指针的转换_, 而不是对象拷贝。也就是说， ~p~ 的静态类型是: ~std::shared_ptr<Quote>~, 但它管理的实际对象仍然是: ~BulkQuote~.
所以如果 ~p->net_price(15)~ ，如果这里 ~net_price~ 是虚函数，则会根据指针所指对象的动态类型进行调用 ~BulkQuote::net_price~ . 存放继承体系对象时，通常应该存放基类指针，最好是智能指针。

对比一下:
#+begin_src cpp
  BulkQuote bulk;
  Quote q = bulk; // 复制对象本身，切掉派生类的部分
  Quote &r = bulk; // 绑定到原对象，不切
  Quote *p = *bulk; // 指针指向原对象，不切
#+end_src
智能指针本质上属于第三类。
*** Object Slicing 反例
#+begin_src cpp
  std::shared_ptr<Quote> p = std::make_shared<BulkQuote>();

  Quote q = *p; // 仍然切片!
#+end_src
因为 ~*p~ 得到的是一个 ~Quote&~ 静态视角下的对象，再用它初始化 ~Quote q~, 又回到了 “按值拷贝基类对象” 的问题。
* Tempaltes -- 编译期多态与泛型设计
本章讲解 templates and generic programming. OOp 和 generic programming 处理的都是 “写程序时还不知道的类型”；区别是 OOP 的类型到运行期才能确定，而 generic programming 的类型在编译期确定。

这是理解C++的关键:
#+begin_src cpp
  // runtime polymorphism
  void draw(const Shpae &s) {
    s.draw(); // 运行时根据动态类型选择
  }

  // compile-time polymorphism
  template <typename T>
  void draw(const T& x) {
    x.draw(); // 编译期为 T 生成代码
  }
#+end_src
** function template 函数模板
函数模板是书写一次，多次实例化。以 ~compare~ 举例: 多个类型的比较函数函数体几乎一样，于是可以写成 function template:

#+begin_src cpp
  template <typename T>
  int compare(const T& lsh, const T& rhs) {
    if (lhs < rhs) return -1;
    if (rhs < lhs) return 1;
    return 0;
  }
#+end_src
调用:
#+begin_src cpp
  compare(1, 2); // T = int
  compare(std::string{"a"}, std::string{"b"}); // T = std::string
#+end_src
这里的 ~T~ 不是运行期变量，而是编译期类型参数。编译器会给不同的 ~T~ 生成不同实例。
** 泛型代码的核心: 减少对类型的要求
这个例子有一个深层的思想:
#+begin_src cpp
  if (lhs < rhs) return -1;
  if (rhs < lhs) return 1;
#+end_src
它只要求 ~T~ 支持 ~<~, 不要求 ~>~, ~==~. 这就是 generic programming 的重要设计:
#+begin_quote
模板对类型的要求越少，可用范围越大。
#+end_quote
现代C++进一步用 *concepts* 显式表达这种要求。比如标准库有 ~std::semiregular~, 它要求类型 copyable 且 default initializable, 语义上类似内置类型但不要求支持 ~==~.
例如:
#+begin_src cpp
  #include <concepts>

  template <std::regular T>
  T clamp_value(T value, T low, T high) {
    if (value < low) return low;
    if (high < value) return high;
    return value;
  }
#+end_src
~concepts~ 的好处是：错误信息更清晰，接口约束更明确。没有 concepts 时，模板错误常常会在函数体深处爆炸；有 ~concepts~ 后，错误会更接近调用点.
** 模板 vs 继承: 两个多态模型
| 维度      | Templates                | Inheritance + virtual     |
|-----------+--------------------------+---------------------------|
| 决定时机 | 编译期                  | 运行期                   |
| 性能      | 通常可内联，无虚调用   | 有间接调用成本          |
| 代码体积 | 可能膨胀                | 一份虚函数代码          |
| 扩展方式 | 新类型只要满足接口即可 | 新类型必须继承基类      |
| 适合场景 | 容器/算法/数值/策略    | 插件/GUI/运行期对象集合 |

* Concepts
~concepts~ 是C++20正式进入标准的模板约束机制，用来把 “模板参数必须满足什么要求” 显式写出来。concepts(约束) 就是一组逻辑操作和操作数，用来规定 template arguments 必须满足的要求； ~requires-expression~ 则提供了一种简洁方式表达这些要求。

** concepts 解决什么问题
传统模板的问题是: *模板对类型的要求藏在函数体内*

例如:
#+begin_src cpp
  template <typename T>
  T min_value(const T& a, const T& b) {
    return b < a ? b : a;
  }
#+end_src
这段代码看似可以接受任意 ~T~, 但实际上要求:
- T 必须支持 ~operator<~
- T 必须可以复制或移动返回


如果你传入一个不支持 ~<~ 的类型，那么编译器会在模板实例化深处报一大串错误。

concepts 的目的就是把这种隐含要求写在接口上:
#+begin_src cpp
  #include <concepts>

  template <typename T>
  concept LessThanComparable =
  requires(const T& a, const T& b) {
  {a < b} -> std::convertible_to<bool>;
  };

  template <LessThanComparable>
  T min_value(const T& a, const  T& b) {
    return b < a ? b : a;
  }
#+end_src
现在接口直接告诉: ~min_value~ 只接受支持 ~<~ 且结果可转化为 ~bool~ 的类型。

这就是 concepts 的价值：让模板接口从 “只写 typename” 升级为 “写出类型契约”。

** 最小语法

*** 标准 concept
#+begin_src cpp
  #include <concept>
  #include <iostream>

  template <std::integral T>
  T add_one(T x) {
    return x + 1;
  }

  int main() {
    std::cout << add_one(41) << '\n';

    // add_one(3.14); // error: double 不满足 std::integral
  }
#+end_src
~template <std::integral T>~ 等价于说： T 必须是 ~integral~ type, 例如 ~int~, ~bool~, ~long~, ~char~ 等。

*** requires-clause
#+begin_src cpp
  #include <concepts>

  template <typename T>
  requires std::floating_point<T>
  T half(T x) {
    return x / 2;
  }
#+end_src
也可以写成:
#+begin_src cpp
  template <typename T>
  T half(T x) requires std::floating_point<T>{
    return x / 2;
  }
#+end_src
这两种都常见。

*** 自定义 concept
#+begin_src cpp
  #include <concepts>
  #include <string>

  template <typename T>
  concept Printable = requires(std::ostream& os, const T& value) {
  {os << value} -> std::same_as<std::ostream&>;
  };
#+end_src
意思是: 对于类型T,如果 ~os << value~ 这个表达式合法，并且结果类型正好是 ~std::ostream &~, 那么 T 就满足 ~Printable~.
