* Classes 总览
用 class 定义抽象数据结构，通过接口和实现分离来维护对象状态，并通过构造函数、访问控制、成员函数、静态成员等机制，把一个概念变成可靠的类型。
* class 的第一性原理: 把一组数据变成一个有语义的类型
class 先不要固定为 Java 里的 “对象模板”，而是:
#+begin_quote
class = representation + invariants + interface
#+end_quote
其中，
- representation: 对象内部如何存储数据
- invariants: 对象在整个生命周期中必须保持成立的条件
- interface: 外部代码允许的操作


例如，一个 ~Point~ 可能只是两个独立坐标:
#+begin_src cpp
  struct Point {
    int x{};
    int y{};
  }
#+end_src
没有太强的 invariant, ~x~ 和 ~y~ 都可以独立变化，所以公开成员很自然。

但一个 ~BoardSize~ 不一样:
#+begin_src cpp
  class BoardSize {
  public:
    BoardSize(int width, int height)
    : width_{width}, height_{height} {
      if (width_ <= 0 || height_ <= 0) {
        throw std::invalid_argument("board size must be positive");
      }
    }

    int width() const { return width_; }
    int height() const { return height_; }
    
  private:
    int width_;
    int height_;
  }
#+end_src

这里的 invariant: 宽高必须为正。外部代码不应该绕过检查随意修改成员，所以用 ~class + private~ . 如果类型具有 invariant, 就用 ~class~; 如果成员可以彼此独立变化，用 ~struct~. ~struct~ 和 ~class~ 的区别只在于默认可见性。
* 数据抽象与封装
C++ Primer 一开始就强调两个概念: *data abstraction* 与 *encapsulation* 。

abstraction 是把接口和抽象分离； interface 是用户能执行的操作， implemetation 是数据成员、成员函数函数体、以及不希望用户直接使用的辅助函数。encapsulation 则强调隐藏实现，让用户只能通过接口使用对象。

比如这个设计很脆弱:
#+begin_src cpp
  struct Snake {
    std::vector<Point> body;
    Direction dir;
  };
#+end_src
任何地方都能写:
#+begin_src cpp
  snake.body.clear();
  snake.dir = Direction::up;
#+end_src
于是你无法保证蛇至少有一个头，也无法保证方向变化合法。更好的设计是把 “蛇必须有身体、方向不能反向” 作为 invariants, 把 “移动时头尾如何变化” 集中起来。
* C++ class 与 Java / Python Class 的关键差异

*C++ class 默认是值类型， Java class 默认是引用类型* .

在 Java 中，类型分为 primitive type 和 reference type, class type 属于 reference types; 对象通常通过引用访问。 Oracle JLS 把类型分类明确把 class types, interface types, array types 归为 reference type。

Java 风格:
#+begin_src java 
  User a = new User("Alice");
  User b = a; // b  和 a 指向同一个对象
#+end_src

C++ 风格:
#+begin_src cpp
  User a{"Alice"};
  User b = a; // 默认是复制出另一个 User
#+end_src
这意味着 C++ class 天然要考虑                                              ``
- 对象如何初始化
- 对象如何复制
- 对象如何赋值
- 对象如何移动
- 对象如何销毁
- 对象是否拥有资源


C++ Primer 在本章最后已经提醒：如果不定义 copy, assignment, destruction, 编译器会合成版本，通常逐成员复制、赋值、销毁。这对 ~std::string~ , ~std::vector~ 这样的成员通常正确，但对手动管理动态资源的类通常不正确。

Python 又不同。Python 的 class 更动态。官方文档说， class 有一个由 dictionary 实现的 namespaces; class attribute reference 本质上会查找这个字典，实例对象主要操作也是 attribute references.

所以三者可以粗略对比:
| 维度           | C++                                              | Java                                      | Python                                       |
|----------------+--------------------------------------------------+-------------------------------------------+----------------------------------------------|
| class 核心角色 | 定义新类型，通常是值类型                        | 定义引用类型对象                         | 创建动态对象模型与命名空间                  |
| 对象存放       | 可栈上、堆上、静态区、容器中                   | 通常由 JVM 管理，通过引用访问            | 由解释器创建，通过引用访问控制             |
| 复制语义       | 默认逐成员访问，可自定义 copy/move              | 变量赋值复制引用，不复制对象            | 名字绑定到对象，赋值复制引用               |
| 析构/资源释放 | RAII, 析构确定发生                              | GC 管理内存，资源常用 try-with-resources | GC/引用计数等实现细节，常用 context manager |
| 动态派发       | 只有 ~virtual~ 才动态派发                       | 普通实例方法通常动态派发                 | 方法/属性查找动态                           |
| 成员访问       | ~public/private/protected~ 编译期约束           | 语言级控制访问                           | 主要靠约定， ~_name~/name mangling          |
| 设计重点       | value semantics, RAII, Invariants, zero-overhead | 引用对象，继承接口，GC                   | 动态性、duck typing, 运行时扩展             |

C++ class 不仅是面向对象的 class, 还是 内存生命周期、所有权、值语义的交汇点。
* 成员函数与 ~this~
成员函数是定义在 class 内部的函数:
#+begin_src cpp
  class Sales_data {
  public:
    std::string isbn() const {
      return bookNo;
    }
  private:
    std::string bookNo;
  };
#+end_src
调用:
#+begin_src cpp
  Sales_data item;
  item.isbn();
#+end_src

这个调用隐含了一个对象, C++ Primer 解释说，非 ~static~ 成员函数通过一个隐式参数 ~this~ 访问调用它的对象。 ~item.isbn()~ 可以理解成编译器隐式把 ~&item~ 传递给 ~isbn()~ 。

也就是说:
#+begin_src cpp
  return bookNo;
#+end_src
近似等价于:
#+begin_src cpp
  return this->bookNo;
#+end_src
cppreference 也说明，在非静态成员函数体内，对非静态成员的无限定访问会被转换成通过 ~(*this)~ 的成员访问。
** ~const~ 成员函数
#+begin_src cpp
  std::string isbn() const;
#+end_src
参数列表后面的 ~const~ 修饰的是隐式 ~this~, 普通成员函数中的 ~this~ 类似:
#+begin_src cpp
  Sales_data *const this
#+end_src
~const~ 成员函数 ~this~ 类似:
#+begin_src cpp
  const Sales_data *const this
#+end_src
所以 ~const~ 成员函数不能修改普通数据成员。

设计原则:
#+begin_quote
不修改对象可观察状态的成员和函数，一律加 ~const~
#+end_quote
例如:
#+begin_src cpp
  class Snake {
  public:
    Point head() const;
    std::size_t length() const;
    bool contains(Point p) const;
    void move_to(Point p, bool grow); // 会修改对象，所以不加 const
  }
#+end_src
* 成员函数 vs 非成员函数

不是所有“和类有关”的函数都应该是成员函数。

C++ Primer 的 ~Sales_data~ 例子中:
#+begin_src cpp
  Sales_data &combine(const Sales_data&);
#+end_src
是成员函数，因为它修改左操作数。

但是:
#+begin_src cpp
  Sales_data add(const Sales_data &, const Sales_data &);
  std::istream &read(std::istream &, Sales_data &);
  std::ostream &print(std::ostream &, const Sales_data &);
#+end_src
是非成员函数，因为它们虽然概念上属于接口，但不一定绑定到某个对象上。

现代C++的经验准则是:

- 如果函数必须直接访问或修改对象内部表示，把它当作成员
- 如果函数只是基于 public 接口组合操作，优先当作非成员、非 friend


只有当函数需要直接访问类的表示时，才把它做成成员；辅助函数应减少耦合。

例如:

#+begin_src cpp
  class Point {
  public:
    Point(int x, int y): x_{x}, y_{y} {}
    int x() const { return x_; }
    int y() const { return y_; }

  private:
    int x_;
    int y_;
  };

  int manhattan_distance(Point a, Point b) {
    return std::abs(a.x() - b.x()) + std::abs(a.y() - b.y());
  }
#+end_src
~manhattan_distance~ 不需要访问 private 成员，所以不必是成员函数。
* 构造函数: 建立对象不变量
构造函数的核心任务不是 “给成员变量赋值”，而是:
#+begin_quote
创建一个从一开始就合法可用的对象。
#+end_quote

construst 应该是 fully initialized object; 如果构造函数无法构造合法对象，应抛出异常。

例如:
#+begin_src cpp
  class Board {
  public:
    Board(int width, int height) : width_{width}, height_{height}, cells_(static_cast<std::size_t>(width * height), Cell::Empty)
    {
      if (width_ <= 0 || height_ <= 0) {
        throw std::invalid_argument("invalid board size");
      }
    }
    
  private:
    int width_;
    int height_;
    std::vector<Cell> cells_;
  }
#+end_src
但是上面写法有个潜在问题: 如果我们传入非法的 ~width~ 和 ~height~, 那么在检查前就会初始化成员变量，并用于初始化 ~cells_~ 。更稳妥的方法是先验证再构造，或者把验证逻辑抽象为 *静态函数*:

#+begin_src cpp
  class Board {
  public:
    Board(int width, int height) : width_{check_positive(width, "width")}, height_{check_positive(height, "height")}, cells(static_cast<std::size_t>(width_) * height_, Cell::Empty){}
    
  private:
    static int check_positive(int value, const char *name) {
      if (value <= 0) {
        throw std::invalid_argument(std::string{name} + "must be positive");
      }
      return value;
    }
    
    int width_;
    int height_;
    std::vector<Cell> cells_;
  }
#+end_src
构造函数是 C++ class 设计的中心，因为C++没有统一的GC后置初始化模型。对象一旦构造完成，其他成员函数都可以假设 invariant 已经成立。
* 构造函数初始化列表: 初始化，不是赋值
C++ Primer 特别强调:  *构造函数体执行之前，成员已经初始化完成* 。如果我们在构造函数体里写赋值:
#+begin_src cpp
  class User {
  public:
    User(const std::string &name) {
      name_ = name;
    }
  private:
    std::string name_;
  }
#+end_src
实际过程是:
#+begin_quote
- 先默认初始化 ~name_~
- 再在构造函数体里赋值 ~name_~
#+end_quote
更好的写法是:
#+begin_src cpp
  class User {
  public:
    User(std::string name) : name_{std::move(name)}
    {}
    
  private:
    std::string name_;
  };
#+end_src
有些成员必须在初始化列表中初始化:
#+begin_src cpp
  class Example {
  public:
    Example(int x, int &ref) : x_{x}, ref_{ref}, fixed_{x}
    {}

  private:
    int x_;
    int &ref_;
    const int fixed_;
  }
#+end_src
必须通过构造函数初始化列表初始化的成员:
- 引用成员
- ~const~ 成员
- 没有默认构造函数的成员

还有一个容易错的点: *成员初始化顺序不是初始化列表顺序，而是成员声明顺序*

比如:

#+begin_src cpp
  class X {

  public:
    X(int value) : j_{value}, i_{j_} // 看起来先 j_ 后 i_, 实际不是
    {}
  private:
    int i_;
    int j_;
  }
#+end_src
实际上是按照在 ~private~ 声明顺序初始化的。即，先初始化 ~i_~, 再初始化 ~j_~ , 所以 ~i_{j_}~ 会读取尚未初始化的 ~j_~ 。初始化列表只指定初始值，不决定初始化顺序； *成员按类中声明顺序初始化* 。

- 成员初始化顺序 = 成员声明顺序
- *初始化列表最好按声明顺序书写*
- 尽量用构造函数参数初始化成员， *不要用一个成员初始化另一个成员*
* ~= defalut~, 默认构造函数与聚合
如果类没有定义任何构造函数，编译器会合成默认构造函数。它会使用类内初始化器；没有类内初始化器的成员则默认初始化。对于内置类型成员，这可能留下未定义值。 _有内置类型成员的类通常应该给这些成员类内初始化器，或者自己定义默认构造函数_ 。

#+begin_src cpp
  class Sales_data {
  public:
    Sales_data() = defalut;
  private:
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };
#+end_src
~= defalut~ 的意思是：我知道需要这个特殊成员函数，请编译器按照默认规则生成。

现代C++中，建议尽量写类内初始化器:
#+begin_src cpp
  class Snake {
  private:
    std::vector<Point> body_;
    Direction dir_{Direction::right};
    bool alive_{true};
  };
#+end_src
这样每个构造函数都能获得一致的默认状态。
* ~explicit~: 阻止危险的隐式类型转换
C++里，一个能用单个实参调用的构造函数，默认会定义从参数类型到类类型。这被称为 converting constructor 。

例如:

#+begin_src cpp
  class BoardSize {
  public:
    BoardSize(int n) : width_{n}, height_{n} {}
    
  private:
    int width_;
    int height_;
  }

  void create_board(BoardSize size);

  create_board(40); // 如果构造函数不是 explicit, 这会隐式构造 BoardSize{40}
#+end_src
** 不写 ~explicit~ 会导致的问题
如果 ~BoardSize(int)~ 不是 ~explicit~, 那么它是一个 *converting constructor*, 也就是允许从 ~int~ 隐式构造出 ~BoardSize~ 的构造函数。 cppreference 对 convertin constructor 的定义就是: 非 ~explicit~ 构造函数可以指定从参数类型到类类型的隐式转换；而 ~explicit~ 构造函数不能用于隐式转换和 copy-initialization.
*** 这段代码发生了什么
~create_board(40);~ 等价的，可以理解为编译器替我们做了:

#+begin_src cpp
  create_board(BoardSize{40});
#+end_src
更准确地说，函数实参 ~40~ 被用于初始化形参 ~BoardSize size~. 因为 ~BoardSize~ 有一个可用的非 ~explicit~ 构造函数 ~BoardSize(int n)~ 。所以编译器允许 ~int -> BoardSize~ 的转换，而且这属于一次 *用户自定义转换* 。

如果写成:
#+begin_src cpp
  explicit BoardSize(int n) : width_{n}, height_{n} {}
#+end_src
那么:
#+begin_src cpp
  create_board(40); // error
  create_board(BoardSize{40}); // ok
  create_board(BoardSize(40)); // ok
#+end_src
也就是说， ~explicit~ 禁止编译器在 “不显眼的地方” 自动替我们构造对象。
*** 可能产生的问题
**** 主要问题: 调用点语义模糊
比如 ~create_board(40)~ 乍看像是 ~create_board(int)~ ，但实际上是 ~void create_board(BoardSize size)~ 。这会让调用点隐藏掉一个重要事实：传入的不是普通整数，而是一个 “棋盘尺寸对象”。

在例子中， ~BoardSize(int n)~ 的语义是创建一个正方形棋盘尺寸。但从调用点的传参看不出来 ~40~ 是宽度、高度、边长、格子数、还是某种容量。
**** 更严重的问题: 错误类型也能通过
因为 ~BoardSize(int)~ 接受 ~int~, 所以很多能先转换为 ~int~ 的东西，也可能继续转换为 ~BoardSize~:
#+begin_src cpp
  create_board(true); // true -> 1 -> BoardSize{1}
  create_board('A'); // 'A' -> 65 -> BoardSize{65}
  create_board(40.8); // 40.8 -> 40 -> BoardSize{40}
#+end_src
这些调用从业务语义上大概率是错的，但如果构造函数不是 ~explicit~, 它们可能会通过编译。

但如果显式用 ~create_board(BoardSize{40.8});~ ，由于花括号初始化会禁止窄化转换，编译器会更容易报错。 /Effective Modern C++/ 也强调，花括号初始化的一个重要好处是防止内置类型之间的 narrowing coversion, 同时也提醒构造函数重载和初始化语法会影响实际调用结果。
**** 污染重载决议，制造意外匹配
假设以后增加了重载:
#+begin_src cpp
  viod create_board(BoardSize size);
  void create_board(int cell_count);
#+end_src
那么 ~create_board(40)~ 会优先选择 ~int~ 版本，因为精确匹配优于用户自定义转换。

这看起来没问题，但问题是：如果后来某个重载被删除、改名、模板化，原本不该成立的调用可能有因为隐式构造而成立，导致行为改变。
** 添加 ~explicit~
因此 现代C++ 的常见原则是:
#+begin_quote
单参数构造函数默认写 explicit, 除非你想明确提供隐式转换。
#+end_quote
cppreference 对 ~explicit~ 的说明是: 它指定构造函数或转换函数不能用于隐式转换或 copy-initializatin; C++20 起还支持条件 ~explicit~ 。

推荐写成:
#+begin_src cpp
  class BoardSize {
  public:
    explicit BoardSize(int n) : width_{n}, height_{n} {}
    
  private:
    int width_;
    int height_;
  }
#+end_src
这样如果调用函数必须写:
#+begin_src cpp
  create_board(BoardSize{40});
#+end_src
*  ~friend~: 受控破坏封装
~friend~ 允许某个非成员函数或另一个类访问 ~private~ 成员. 比如下面的这些 ~read~, ~print~ 函数:

#+begin_src cpp
  class Sales_data {
      friend std::istream& read(std::istream&, Sales_data&);
      friend std::ostream& print(std::ostream&, const Sales_data&);

  public:
      // ...

  private:
      std::string bookNo;
      unsigned units_sold = 0;
      double revenue = 0.0;
  };
#+end_src
这些函数属于 ~Sales_data~ 的接口，但是不是成员函数；一旦数据成员 private, 它们如果想要访问内部表示，就必须成为 ~friend~ 。

但是不要把 ~friend~ 理解成 “破坏封装”。更准确地说，
#+begin_quote
~friend~ 是把某个函数纳入实现可信边界
#+end_quote
它不是类成员，但是它被类授权访问内部表示。

使用原则是:

- 能用 ~public~ 接口完成，就不要使用 ~friend~
- 如果确实是类接口的一部分，但语法上不适合作为成员，可以使用 ~friend~
- ~operator<<~, ~operator>>~, 以及对称二元运算符成员非常适合非成员 ~friend~
* 返回 ~*this~: 链式调用与左值语义
C++ Primer 的 ~Screen::move~, ~Screen::set~, ~Screen&~ 可以这样链式调用:
#+begin_src cpp
  myScreen.move(4, 0).set('#').display(std::cout);
#+end_src
关键是返回引用:
#+begin_src cpp
  class Screen {
  public:
    Screen &move(pos r, pos c) {
      cursor_ = r * width_ + c;
      return *this;
    }
    Screen &set(char ch) {
      contents_[cursor_] = ch;
      return *this;
    }
  private:
    using pos = std::string::size_type;
    pos cursor_ = 0;
    pos width_ = 0;
    std::string contents_;
  };
#+end_src
如果返回的是 ~Screen~ 而不是 ~Screen&~, 就会返回副本，后续操作可能作用在临时对象上，不再修改原对象。

~const~ 成员函数如果返回 ~*this~, 应该返回 ~const T&~
#+begin_src cpp
  const Screen &display(std::ostream &os) const {
    os << contents_;
    return *this;
  }
#+end_src
* ~mutable~: 逻辑 ~const~ 与物理 ~const~
有时一个成员函数逻辑上不改变对象，但是需要更新缓存或统计计数:
#+begin_src cpp
  class Text {
  public:
    std::size_t length() const {
      ++access_count_;
      return text_.size();
    }

  private:
    std::string text_;
    mutable std::size_t access_count_ = 0;
  };
#+end_src
~mutable~ 成员即使在 ~const~ 里也可以被修改 。使用原则是:

#+begin_quote
~mutable~ 只用于不影响对象外部语义的缓存、统计、惰性计算。 \\
不要用 ~mutable~ 绕过 const-correctness
#+end_quote
* ~static~ 成员: 属于类，不属于单个对象
普通数据成员属于单个对象。例如:
#+begin_src cpp
  class Account {
  private:
    std::string owner_;
    double amount_;
  };
#+end_src
每个 ~Account~ 类对象都有自己的 ~owner_~ 和 ~amount_~ 。

~static~ 成员属于类整体:
#+begin_src cpp
  class Amount {
  public:
    static double rate() { return interest_rate_; }
    static void rate(double r) { interest_rate_ = r; }
  private:
    std::string owner_;
    double amount_{};
    static double interest_rate_;
  };
#+end_src
类外定义:
#+begin_src cpp
  double Amount::interest_rate_ = 0.03;
#+end_src
C++ Primer 指出， ~static~ 成员存在于任何成员之外。所有对象共享一个 ~static~ 数据成员； *~static~ 成员函数没有 ~this~ 指针*, 因此不能直接访问静态函数，也不能声明为 ~const~. cppreference 也说明，static member functions 不关联任何对象，调用时没有 ~this~ pointer.

C++17 后， ~inline static~ 数据成员也很常见:
#+begin_src cpp
  class GameConfig {
  public:
    inline static constexpr int default_width = 40;
    inline static constexpr int default_height = 20;
  };
#+end_src
* 现代C++ class 设计原则
** 原则1: 判断这是 “数据聚合” 还是 “有不变量的类型”
#+begin_src cpp
  struct Point {
    int x{};
    int y{};
  };
#+end_src
这是数据聚合，公开成员没有问题。

#+begin_src cpp
  class DirectionController {
  public:
    bool turn(Direction next);
    
  private:
    Direction current_{Direction::Right};
  };
#+end_src
这是有规则的类型，外部不能随便改 ~current_~, 否则可能产生意外。

#+begin_quote
- ~struct~ 表示 “这些数据都是什么”
- ~class~ 表示 “这些对象能做什么，并保证自己始终合法”
#+end_quote
** 构造完对象后应该立即可用
下面这种设计:
#+begin_src cpp
  class BadGame {
  public:
    Game() = default;

    bool init(int w, int h);
    void run();

  private:
    bool initialized_ = false;
  };
#+end_src
会让每个成员函数都不得不检查 ~initialized_~ 。更好的设计是:
#+begin_src cpp
  class Game {
  public:
    Game(int width, int height) : board{width, height}, snake_{Point{width / 2, height / 2}}
    {}

  private:
    Board board_;
    Sanke snake_;
  }
#+end_src
如果构造失败，就抛出异常；如果构造成功，就直接可用。这就是 RAII 思想的基础。
** 优先 Rule of Zero
普通业务类最好不要手写析构、复制构造、移动构造、赋值运算符。让 ~std::string~, ~std::vector~, ~std::unique_ptr~ 等自己管理资源。

比如:
#+begin_src cpp
  class Snake {
  public:
    explicit Snake(Point start) : body_{start} {}
  private:
    std::vector<Point> body_;
    Direction dir_{Direction::Right};
  };
#+end_src
这个类不需要写析构函数，不需要写 copy/move. cppreference 对 Rule of Zero 的表述是：有自定义析构、复制/移动构造、复制/移动赋值语句的类应专门处理 ownership; 其他类不应该自定义这些特殊成员函数。即，能避免定义默认操作就避免。

使用 ~vector~ 和 ~string~ 构造的类，通常可以依赖合成的复制、赋值、销毁，手动管理动态内存的类才容易出问题。
** 成员变量表达状态，成员函数维护状态
坏设计:
#+begin_src cpp
  snake.body.push_back(...);
  snake.body.erase(...);
  snake.direction = ...;
#+end_src
外部代码直接操作内部结构，规则分散。

更好的方向是:
#+begin_src cpp
  snake.change_direction(input_dir);
  snake.advance(next_food_position);
#+end_src
也就是， class 的 public 接口应该接近问题领域语言，而不是暴露底层容器操作。
** 原则5: 接口尽量稳定，实现可以变化
比如，如果把 ~Snake~ 的身体暴露为 ~std::vector<Point>~, 之后如果想改 ~std::deque<Point>~, 所有用户代码都可能受到影响。

而如果只暴露:
#+begin_src cpp
  Point head() const;
  std::span<const Point> body() const;
  void advance(Point next, bool grow);
#+end_src
内部从 ~vector~ 换成 ~deque~ 的影响会小很多。
* C++ class 的几种常见角色
** Plain Data: 纯数据结构
#+begin_src cpp
  struct Point {
    int x{};
    int y{};
  };
#+end_src
适合简单组合，没有不变量。
** Value Type: 值类型
#+begin_src cpp
  class BoardSize {
  public:
    BoardSize(int w, int h);
    int width() const;
    int height() const;
  private:
    int width_;
    int height_;
  };
#+end_src
它像 ~int~, ~std::string~ 一样可以复制、放进容器、作为函数返回值。
** RAII Resources Handle: 资源管理器
#+begin_src cpp
  class TerminalMode {
  public:
    TerminalMode();
    ~TerminalMode();

    TerminalMode(const TerminalMode &) = delete;
    TerminalMode &operator=(const TerminalMode &) = delete;
  private:
    // old terminal state
  };
#+end_src
这种类表示 “拥有一个资源”。构造时获取资源，析构是是释放资源。这类之后会进入 Rule of Five/Zero 的核心。
** Manager / Controller: 管理对象协作
#+begin_src cpp
  class Game {
  public:
    void run();
  private:
    Board board_;
    Snake snake_;
    Renderer renderer_;
  };
#+end_src
它不一定代表数学意义上的值，而是组织多个对象的行为。
** Polymorphic Interface: 多态接口
#+begin_src cpp
  class Renderer {
  public:
    virtural ~Renderer() = default;
    virtural void draw(const GameState &) = 0;
  };
#+end_src
注意: C++ 不要求所有 class 都是多态对象。只有写了 ~virtual~ 才走动态派发。
* Class 总结
Class = 用户自定义类型。核心不是 “把变量和函数放在一起”，而是用接口维护对象不变量。

1. data abstraction: 用户关注对象能做什么，不关注内部怎么存
2. encapsulation: private 隐藏表示，public 暴露接口
3. struct/class: 唯一区别是默认访问权限；实践中 struct 用于纯数据， class 用于有不变量的类型
4. 非 static 成员函数有隐式 this 指针；成员访问默认通过 this
5. const 成员函数表示不会修改对象的可观察状态；const 对象只能调用 const 成员函数
6. 构造函数负责初始化对象并建立 invariant, 构造函数默认没有返回类型，不能是 const
7. 优先使用构造函数初始化列表； const, reference, 无默认构造的成员必须在初始化列表中初始化
8. 单参数构造函数默认考虑 explicit, 避免意外隐式转换
9. 成员初始化顺序由声明顺序决定，不由初始化列表中的顺序决定
10. 成员函数 vs 非成员函数: 需要访问的表示做成员，辅助操作的优先非成员
11. friend 是授权非成员/其他类访问 private, 实现受控扩展
12. 返回 ~*this~ 且要链式调用时返回 ~T&~, ~const~ 成员返回 ~*this~ 应返回 ~const T &~
13. ~mutable~ 用于缓存/统计等不改变逻辑状态的成员
14. ~static~ 成员属于类，不属于对象； ~static~ 成员函数没有 ~this~
15. 现代C++优先 Rule of Zero: 用标准库成员管理资源，避免手写析构/copy/move
