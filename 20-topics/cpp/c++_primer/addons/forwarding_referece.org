#+title: 转发引用 forwarding reference
#+author: yurikon
#+language: zh-cn
* 转发引用
转发引用是一种位于类型推导语境中的 ~T&&~, 它既能绑定左值，也能绑定右值，并记录实参原本的值类别，以便通过 ~std::forward~ 继续传递。
* 为什么需要转发引用
考虑一个中间函数 ~relay~, 它接受参数，再把参数交给另一个函数:
#+begin_src cpp
  void consume(const std::string &);
  void consume(std::string &&);
#+end_src
我们希望:
#+begin_src cpp
  std::string s{"hello"};

  relay(s); // 最终调用 const std::strnig&
  relay(std::string{"hello"}); // 最终调用 std::string&&
#+end_src
也就是说， ~relay~ 不应擅自决定复制还是移动，而应该忠实保留调用者传进来的状态:

- 左值：继续作为左值传递
- const 左值：继续作为 const 左值传递
- 右值：继续作为右值传递


这类函数在标准委员会的表述中属于 *neutral passthrough code*, 即 “中立的中间层”：它自身并不真正消费参数，而是把参数的类型、 ~const~ 属性和值类别交给下游代码处理。转发引用正是为这种用途设计的。
* 并非所有的 ~T&&~ 都是转发引用
这是最重要的判断。
** 典型转发引用
#+begin_src cpp
  template <typename T>
  void f(T&& value);
#+end_src
这里 ~T~:
1. 是函数模板参数
2. 从调用实参中推导
3. ~T&&~ 没有额外的 ~const~
4. 参数类型直接是 ~T&&~


因此它是转发引用。

当前标准草案的定义是：转发引用是“指向一个未加cv限定的模板参数的右值引用”，并且在相关函数调用中执行模板实参推导；当传入左值时，推导过程会把实参类型当作其左值引用类型处理。
** 普通左值引用
#+begin_src cpp
  void f(std::string&& value);
#+end_src
这里没有类型推导， ~value~ 只能绑定到右值:
#+begin_src cpp
  std::string s;
  f(s); // 错误: 左值不能绑定到 std::string&&
  f(std::move(s)); // 正确, xvalue
  f(std::string{}); // 正确, prvalue
#+end_src
这就是普通的右值引用，而不是转发引用。
** ~const T&&~ 不是转发引用
#+begin_src cpp
  template <typename T>
  void f(const T&& value);
#+end_src
它不是转发引用，因为 ~T~ 前面有 ~const~ ，被视为是常量右值引用。

#+begin_src cpp
  int n = 10;

  f(n);  // 错误：const T&& 仍不能绑定普通左值
  f(10); // 正确
#+end_src
** ~std::vector<T>&&~ 不是转发引用
#+begin_src cpp
  template <typename T>
  void f(std::vector<T>&& value);
#+end_src
这里整个参数的类型不是 ~T&&~, 而是 ~std::vector<T>&&~ , 这里 ~T~ 只负责推导元素类型，所以该参数是一个普通的 “指向  ~std::vector<T>~ 类型的右值引用”。

#+begin_src cpp
  std::vector<int> values;

  f(values);            // 错误
  f(std::move(values)); // 正确
#+end_src
** 类模板成员中的 ~T&&~
#+begin_src cpp
  template <typename T>
  class Box {
  public:
      void set(T&& value);  // 通常不是转发引用
  };
#+end_src
因为当我们创建这个类时: ~Box<std::string> box~ ，类模板参数 ~T~ 已经确定为了是 ~std::string~, 而这个成员函数实际上相当于:
#+begin_src cpp
  void set(std::string&& value);
#+end_src
类型是 ~std::string&&~, 没有在调用 ~set~ 时推导 ~T~, 因此是普通右值引用。

但如果成员函数自己引入一个模板参数:
#+begin_src cpp
  template <typename T>
  class Box {
  public:
      template <typename U>
      void set(U&& value);  // U&& 是转发引用
  };
#+end_src
调用 ~set~ 时才推导 ~U~, 所以 ~U&&~ 是转发引用。
* 左值会把 ~T~ 推导成引用
这是转发引用最特殊的地方。
比如:
#+begin_src cpp
  template <typename T>
  void relay(T&& value);
#+end_src
有以下对象:
#+begin_src cpp
  std::string s{"hello"};
  const std::string cs{"const hello"};
#+end_src
调用结果如下:
| 调用                  | 实参类型                  | 推导出的 ~T~        | 参数最终类型        |
|-----------------------+----------------------------+----------------------+----------------------|
| ~relay(s)~            | ~std::string~ lvalue       | ~std::string&~       | ~std::string&~       |
| ~relay(cs)~           | ~const std::string~ lvalue | ~const std::string&~ | ~const std::string&~ |
| ~relay(std::move(s))~ | ~std::string~ xvalue       | ~std::string~        | ~std::string&&~      |
| ~relay(std::move{})~  | ~std::string~ prvalue      | ~std::string~        | ~std::string&&~      |

最反常的一行是:
#+begin_src cpp
  relay(s);
#+end_src

此时模板参数不是推导为 ~T = std::string~, 而是 ~T = std::string&~ .

这是模板推导中专门为转发引用设置的规则。标准明确规定：如果参数模式是转发引用，而实参是左值，类型推导时使用“实参类型的左值引用”代替原实参类型。
* 底层机制：引用折叠(reference collapsing)
当左值 ~s~ 传给:

#+begin_src cpp
  template <typename T>
  void relay(T&& value);
#+end_src
推导会得到:
#+begin_src cpp
  T = std::string&
#+end_src
代回参数类型 ~T&&~ 会得到一个概念上的“引用的引用”: ~std::string& &&~.

C++不允许最终类型中存在“引用中的引用”，因此会执行 *reference collapsing(引用折叠)* .

引用折叠规则如下:
- ~T& &~ -> ~T&~
- ~T& &&~ -> ~T&~
- ~T&& &~ -> ~T&~
- ~T&& &&~ -> ~T&&~

可以压缩成一句话:
#+begin_quote
只要组合中出现了一个 ~&~, 折叠结果就是 ~&~ ；只有两个都是 ~&&~ 时，结果才是 ~&&~ .
#+end_quote

当前标准在 ~[dcl.ref]~ 中正式将这一规则成为 reference collasping.

因此:

#+begin_src cpp
  T = std::string&;
  T&& = std::string& &&;
#+end_src

折叠为: ~std::string&~. 而右值调用 ~relay(std::string{})~, 得到:
#+begin_src cpp
  T = std::string
    T&& = std::string&&
#+end_src
没有引用的引用，因此保持右值引用。

完整过程是:
#+begin_example
左值实参
  ↓
T 推导为 U&
  ↓
参数类型成为 U& &&
  ↓
引用折叠
  ↓
U&

右值实参
  ↓
T 推导为 U
  ↓
参数类型成为 U&&
  ↓
U&&
#+end_example
* 有名字的右值引用变量仍然是左值表达式
看下面的代码:
#+begin_src cpp
  template <typename T>
  void relay(T&& value) {
    consume(value);
  }
#+end_src
即便这样调用:
#+begin_src cpp
  relay(std::string{"temporary"});
#+end_src
~value~ 的声明类型可能是 ~std::string&&~, 但表达式 ~value~ 仍然是一个左值表达式。原因是:

#+begin_quote
只要一个对象通过名字被访问，这个名字表达式通常就是左值。
#+end_quote

因此， ~consume(value)~, 始终把 ~value~ 当作左值传递。

这也是为什么下面的代码不能完美转发:

#+begin_src cpp
  template <typename T>
  void relay_bad(T&& value) {
    consume(value); // value 永远是lvalue
  }
#+end_src
需要写成:
#+begin_src cpp
  template <typename T>
  void relay(T &&value) {
    consume(std::forward<T>(value));
  }
#+end_src
* ~std::forward~ 做了什么
~std::forward~ 不是移动操作，也不会自己搬运任何资源。

它本质上只是一个有条件的类型转换：
#+begin_src cpp
  static_cast<T&&>(value)
#+end_src
其主要声明形式是:
#+begin_src cpp
  template <class T>
  constexpr T&& forward(std::remove_reference_t<T>& value) noexcept;
#+end_src
标准库还提供一个接收右值的重载。

删除 libc++ 内部宏后，其实现结构可以近似写成:
#+begin_src cpp
  template <class T>
  constexpr T&& forward(std::remove_reference_t<T>& value) noexcept {
    return static_cast<T&&>(value);
  }
#+end_src
libc++ 的真实实现也是返回 ~static_vast<_Tp&&>(_t)~; 第二个重载还通过断言防止把右值错误地转发为左值。
** 原实参是左值
#+begin_src cpp
  std::string s;
  relay(s);
#+end_src
推导结果是: ~T = std::string &~, 于是 ~std::forward<std::string&>(value)~, 在其内部转换为 ~static_cast<std::string& &&>(value)~, 发生引用折叠后为 :

#+begin_src cpp
  static_cast<std::string &>(value);
#+end_src
因此其结果仍然是左值。
** 原实参为右值
#+begin_src cpp
  relay(std::string{});
#+end_src
推导结果是 ~T = std::string~, 于是 ~std::forward<std::string>(value)~ 内部转化为 ~static_cast<std::string &&>(value)~, 结果是右值。
** 小结
因此，我们可以把 ~std::forward<T>~ 理解为:
- 如果 ~T~ 记录了 “原来是左值”，就返回左值
- 如果 ~T~ 记录了 “原来是右值”，就返回右值
* 例子
#+begin_src cpp
  #include <iostream>
  #include <string>
  #include <utility>

  void consume(std::string &) {
    std::cout << "mutable lvalue\n";
  }

  void consume(const std::string &) {
    std::cout << "const lvalue\n";
  }

  void consume(std::string&&) {
    std::cout << "rvalue\n";
  }

  template <typename T> void relay_bad(T &&value) { consume(value); }
  template<typename T> void relay(T &&value) {
    consume(std::forward<T>(value));
  }

  int main() {
    std::string s{"hello"};
    const std::string cs{"const hello"};

    relay_bad(s); // mutable value
    relay_bad(std::string{"tmp"}); // mutable value, 丢失右值性

    relay(s); // mutable value
    relay(cs); // const lvalue
    relay(std::string{"tmp"}); // rvalue
    relay(std::move(s)); // rvalue
  }
#+end_src
这没有发生复制或移动，因为 ~consume~ 只接收引用。转发引用与 ~std::forward~ 所做的只是:

#+begin_quote
让重载决议看到调用者传入的是左值、 ~const~ 左值还是右值。
#+end_quote
是否真正发生复制或移动，要看下游函数使用了哪个构造函数或重载。
* ~std::move~ 和 ~std::forward~ 的区别
** ~std::move~
#+begin_src cpp
  std::move(value);
#+end_src

含义近似于:
#+begin_src cpp
  static_cast<std::remove_reference_t<decltype(value)&&>(value);
#+end_src
它无条件地把表达式转换为右值。

因此:
#+begin_src cpp
  template <typename T>
  void wrong(T &&value) {
    consume(std::move(value));
  }
#+end_src
虽然传入了左值， ~wrong~ 仍然会将它当作右值传给下游。可能导致 ~s~ 被移动。
** ~std::forward~
#+begin_src cpp
  std::forward<T>(value);
#+end_src
根据 ~T~ 中保存的信息，决定返回的是左值还是右值。

使用原则是:

- 已知是普通右值引用参数：使用 ~std::move~, 因为构造者明确允许从该对象移动
- 转发引用参数: 使用 ~std::forward<T>~
- 普通左值引用: 通常直接使用


例如构造函数中的参数不是转发引用:
#+begin_src cpp
  class Widget {
  public:
    Widget(Widget&& other) : name_{std::move(other.name_)}{}
  private:
    std::string name_;
  };
#+end_src
~other~ 的类型已经被固定为 ~Widget&&~, 因此它不是转发引用。而调用移动构造函数本身就说明调用者允许从该对象移动，所以使用 ~std::move~.

而泛型包装函数不知道实参原本是左值还是右值，因此使用 ~std::forward~
* 完美转发(perfect forwarding)

当一个函数使用转发引用接受参数，并使用 ~std::forward~ 将参数传递给另一个函数时，通常被称为 *perfect forwarding*.

其典型模式是:
#+begin_src cpp
  template <typename T, typename... Args>
  T make_object(Args&&... args) {
    return T(std::forward<Args>(args)...);
  }
#+end_src
这里的 ~Args&&~ 是一个转发引用参数包，对每个参数都执行 ~std::forward<Args>(args)...~.

例如:
#+begin_src cpp
  class Person {
  public:
    Person(std::name, int age) : name_{std::move(name)}, age_{std::move(age)} {}
  private:
    std::string name_;
    int age_;
  };

  auto p = make_object<Person>("Alice", 20);
#+end_src
~make_object~ 本身不决定 ~"Alice"~ 和 ~20~ 应该怎样构造 ~Person~, 而是把它们原样交给 ~Person~ 的构造函数。

一个带有C++20约束的版本可以写成:
#+begin_src cpp
  template <typename T, typename... Args>
    requires std::constructible_from<T, Args...>
      std::unique_ptr<T> make_owned(Args&&... args) {
      return std::make_unique<T>(std::forward<Args>(args));
    }
#+end_src
~requires~ 提前约束 ~T~ 必须能由 ~Args...~ 构造。
* 泛型 lambda 中的转发引用
泛型 lambda:

#+begin_src cpp
  auto relay = [](auto &&value) {
    consume(std::forward<decltype(value)>(value));
  };
#+end_src
这里没有显式写出模板参数 ~T~, 但是编译器生成的闭包类型大致类似:
#+begin_src cpp
  struct GeneratedClosure {
    template <typename T>
    void operator()(T&& value) const {
      consume(std::forward<T>(value));
    }
  };
#+end_src
所以 ~auto &&value~ 具有和 ~T&&~ 转发引用相同的推导行为。

由于 lambda 内部无法直接写出编译器生成的 ~T~, 因此会使用 ~decltype~:
#+begin_src cpp
  std::fowrard<decltype(value)>(value);
#+end_src
* C++20 中简写函数模板中的转发引用
现代C++可以写:
#+begin_src cpp
  void relay(auto&& value) {
    consume(std::forward<decltype(value)>(value));
  }
#+end_src
和前述使用 ~template~ 的写法大致等价。

也可以添加概念约束:
#+begin_src cpp
  void process(std::ranges::range auto&& range) {
    use_range(std::forward<decltype(range)>(range));
  }
#+end_src
或者直接写成完整模板形式:
#+begin_src cpp
  template <std::ranges::range R>
  void process(R&& range) {
    use_range(std::forward<R>(range));
  }
#+end_src
* 转发引用不应该作为默认参数写法
“万能引用” 这个旧名，容易让人误以为:
#+begin_src cpp
  template <typename T>
  void f(T&&) {}
#+end_src
应该到处使用。但实际上不应该如此。反对 “universal reference” 这一名称的一个重要原因，就是它可能暗示这种引用应该被“普遍使用”；委员会更希望名称反映它的主要用途：转发。

通常可以这样选择:

| 需求                       | 更合适的参数               |
|----------------------------+-----------------------------|
| 只读一个已知类型         | ~const T&~                  |
| 修改调用者对象           | ~T&~                        |
| 明确只接收可移动对象     | ~T&&~                       |
| 函数要保存一份对象       | 按值 ~T value~ 往往更简单 |
| 透明地传给另一个对象     | ~T&&~ 转发引用             |
| 工厂、包装器、 ~emplace~ | 转发引用参数包            |

例如:
#+begin_src cpp
  void print(const std::string& text);
#+end_src
没有必要写成:
#+begin_src cpp
  template <typename T>
  void print(T&& text);
#+end_src
后者会:
- 接收过多不相关类型
- 增加模板实例化
- 把实现暴露在头文件中
- 可能影响重载决议
- 产生更复杂的编译错误

转发引用主要是泛型基础设施，而不是所有函数的万能参数形式。  
* 危险问题: _转发构造函数_ 抢占 _复制构造函数_

考虑:
#+begin_src cpp
  class Person {
  public:
    template <typename T>
    explicit Person(T &&name) 
    : name_{std::forward<T>(name)} {}

  private:
    std::string name_;
  };
#+end_src
然后:
#+begin_src cpp
  Person p{"Alice"};
  Person q{p};
#+end_src
我们可能希望第二行调用复制构造函数: ~Person(const Person &)~, 但模板构造函数可能会被实例化为: ~Person(Person&)~.

对于非 ~const~ 左值 ~p~, ~Person&~ 比 ~const Person&~ 是更精确的匹配。所以模板构造函数可能会抢占复制构造函数，随后会尝试使用 ~Person~ 构造 ~std::string~, 产生复杂错误。

C++20 可以约束它:
#+begin_src cpp
  class Person {
  public:
    template <typename T>
      requires (!std::same_as<std::remove_cvref_t<T>, Person> && std::constructible_from<std::string, T>)
    explicit Person(T&& name) : name_{std::forward<T>(name)}{}
  private:
    std::string name_;
  };
#+end_src
这里排除了 ~std::remove_cvref_t<T> == Person~, 从而让真正的复制构造和移动构造处理 ~Person~ 对象。
* 生命周期不会被“完美转发”修复
转发只会保留类型和值类别，不负责对象生命周期。

下面的代码很危险:
#+begin_src cpp
  class StringRef {
  public:
    template<typename T>
    explicit StringRef(T &&value)
    : ptr_{&value} {}
    
  private:
    const std::string *ptr_;
  }
#+end_src
如果调用:
#+begin_src cpp
  StringRef ref{std::string{"temporary"}};
#+end_src
那么构造函数结束后，临时 ~std::string~ 会被销毁， ~ptr_~ 成为悬空指针。

必须记住:
#+begin_quote
~std::forward~ 不是所有权管理工具，也不会延长被转发对象的生命周期。
#+end_quote
* 不要对同一个参数反复转发
考虑:
#+begin_src cpp
  template <typename T>
  void use_twice(T &&value) {
    first(std::forward<T>(value));
    second(std::forward<T>(value));
  }
#+end_src
如果调用者传入右值:
#+begin_src cpp
  use_twice(std::string{"hello"});
#+end_src
第一次转发可能令 ~first~ 从字符串中移动，第二次转发时对象可能已经处于 *moved-from state* , 被移动后状态。

因此一般原则是:

#+begin_quote
把 ~std::forward~ 放在参数最后一次实际使用处。
#+end_quote
* 完美转发的失败情况
“perfect” 并不意味着任何C++表达式都能被无损转发。
** 花括号初始化器没有独立类型
#+begin_src cpp
  template <typename T>
  void relay(T&&);

  relay({1, 2, 3}); // 无法推导 T
#+end_src
~{1, 2, 3}~ 本身不是一个普通的有类型表达式，因此模板无法直接推导 ~T~.

可以明确类型:

#+begin_src cpp
  relay(std::initializer_list<int>{1, 2, 3});
#+end_src
** 重载函数名没有唯一类型
#+begin_src cpp
  void handle(int);
  void handle(double);

  relay(handle); // 不知道选择哪个重载
#+end_src
需要显式选择:
#+begin_src cpp
  using Handler = void (*)(int);

  relay(static_cast<Handler>(handle));
#+end_src
* C++23: ~std::forward_like~

C++23 增加了:
#+begin_src cpp
  std::forward_like<T>(value);
#+end_src
它的用途是:

#+begin_quote
希望让 ~value~ 采用 ~T~ 的 ~const~ 属性和值类别
#+end_quote
* 总结
** 定义
转发引用：位于类型推导语境中的、直接形如 ~T&&~ 的参数。

典型形式:
#+begin_src cpp
  template <typename T>
  void f(T&& value);
#+end_src
** 推导规则
- 传入 U 左值:
  - T 推导为 U&
  - T&& -> U& && -> U&
- 传入 const U 左值
  - T 推导为 const U& 左值
  - T&& -> const U& && -> const U&
- 传入 U 右值
  - T 推导为 U&&
  - T&& -> U&& -> U&& && -> const U&&
** 引用折叠:
- & + & -> &
- & + && -> &
- && + & -> &
- && + && -> &&
** 函数体内
~value~ 始终是左值表达式，因为它有名字。
** 正确转发
#+begin_src cpp
  template <typename T>
  void relay(T&& value) {
    target(std::forward<T>(value));
  }
#+end_src
** 泛型 lambda
#+begin_src cpp
  auto relay = [](auto&& value) {
    target(std::forward<decltype(value)>(value));
  };
#+end_src
** 与右值引用的区别
#+begin_src cpp
  void f(Widget&&); // 普通右值引用

  template <typename T>
  void f(T&&); // 转发引用

  template <typename T>
  void f(const T&&); // 普通右值引用

  template <typename T>
  void f(std::vector<T>&&); // 普通右值引用
#+end_src
** 与 ~std::move~ 的区别
- ~std::move(x)~ 无条件把 ~x~ 转换成右值
- ~std::forward<T>(x)~ 根据 ~T~ 恢复 ~x~ 原本的左值/右值属性
