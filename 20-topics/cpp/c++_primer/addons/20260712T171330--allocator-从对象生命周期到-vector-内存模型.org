#+Title: Allocator: 从对象生命周期到 vector 内存模型
#+date:       [2026-07-12 Sun 17:13]
#+identifier: 20260712T171330
#+author: yurikon

* 核心结论
~allocator~ 可以理解为:

#+begin_quote
一个向容器提供原始存储空间，并规定这块存储空间应如何分配、释放和使用和策略对象。
#+end_quote

allocator 是封装某种 *allocation model(分配模型)* 信息的类对象，其中包括指针类型、大小类型以及分配和释放存储空间的原语。

对于正在实现的 ~vector~, allocator 解决的核心问题是:
#+begin_quote
~vector~ 的 ~capacity~ 个槽位中，只有前 ~size~ 个槽位存在真正的 ~T~ 对象。
#+end_quote

#+begin_example
begin_                        end_                   capacity_end_
  │                            │                          │
  ▼                            ▼                          ▼
  [ T ][ T ][ T ][ T ][ raw ][ raw ][ raw ][ raw ]
        已构造对象                 尚未构造的存储空间
  <--------- size --------->
  <---------------- capacity ---------------------->
#+end_example
* 为什么 ~unique_ptr<T[]>~ 不足以实现真正的 ~vector~
我们过去利用智能独占指针和逻辑 ~size~ 、 ~capacity~ 保存动态数组:
#+begin_src cpp
  std::unique_ptr<T[]> data_;
  std::size_t size_;
  std::size_t capacity_;
#+end_src
并使用:
#+begin_src cpp
  data_ = std::make_unique<T[]>(capacity_);
#+end_src
这实际上会创建一个包含 ~capacity_~ 个 ~T~ 对象的数组。

也就是说，即便我们通过 ~size_~ 和 ~capacity_~ 从逻辑上限定了只能使用前 ~size_~ 个元素，但底层已经存在十个完成构造的 ~T~ 对象了。
#+begin_example
[ T ][ T ][ T ][ T ][ T ][ T ][ T ][ T ][ T ][ T ]
#+end_example
这会造成几个问题:
** ~T~ 必须能够默认构造
例如:
#+begin_src cpp
  class User {
  public:
    explicit User(std::string name) : name_{name}{}
    
  private:
    std::string name_;
  }
#+end_src
~User~没有默认构造函数, 所以:
#+begin_src cpp
  std::make_unique<User[]>(10); // 无法编译
#+end_src
而真正的 ~vector~ 应当完全合法:
#+begin_src cpp
  std::vector<User> users;
  users.reserve(10);
#+end_src
因为 ~reserve(10)~ 只申请10个空间，并不会构造10个 ~User~.
** ~capacity~ 区域不应该存在对象
标准 allocator 的 ~allocate(n)~ 为 ~n~ 个 ~T~ 提供存储空间，但不会构造这些数组元素。当前标准甚至明确区分了 “数组存储存在” 和 “数组元素对象尚未开始生命周期” 。

因此:
#+begin_src cpp
  allocator.allocate(10);
#+end_src
得到的概念是:
#+begin_example
[ raw ][ raw ][ raw ][ raw ][ raw ][ raw ][ raw ][ raw ][ raw ][ raw ]
#+end_example
而不是:
#+begin_example
[ T ][ T ][ T ][ T ][ T ][ T ][ T ][ T ][ T ][ T ]
#+end_example
随后容器可以只构造前三个:
#+begin_example
[ T ][ T ][ T ][ raw ][ raw ][ raw ][ raw ][ raw ][ raw ][ raw ]
#+end_example
** ~unique_ptr<T[]>~ 把对象数量和存储容量绑定到一起
~unique_ptr<T[]>~ 的析构行为是:
#+begin_src cpp
  delete[] pointer;
#+end_src
它认为整块区域中存在一个完整数组，数组中的所有元素都必须被析构。

而 ~vector~ 需要的是:
1. 只析构 ~[begin_, end_)~ 中的对象
2. 不处理 ~[end_, capacity_end_)~ 的未初始化空间
3. 最后释放整块存储空间


所以 allocator 模型的关键是:
#+begin_quote
允许容器把存储空间的生命周期与元素对象的生命周期分离。
#+end_quote
* C++ 内存管理的四个层次
** 第一层: 存储空间
存储空间只是一段满足大小和对齐要求的内存:
#+begin_example
地址 + 字节数量 + 对齐要求
#+end_example
里面不一定存在某个类型的对象。例如:
#+begin_src cpp
  void *raw = ::operator new(sizeof(std::string));
#+end_src
这里只提供了空间，尚不存在 ~std::string~ 对象。
** 对象生命周期
在存储空间中执行构造，才会开始对象生命周期。
#+begin_src cpp
  auto *p = static_cast<std::string*>(raw);
  std::construct_at(p, "hello");
#+end_src
此时才真正存在一个 ~std::string~.

结束对象生命周期:
#+begin_src cpp
  std::destroy_at(p);
#+end_src
但这只调用析构函数，并没有释放 ~raw~ 指向的内存。

最后才是:
#+begin_src cpp
  ::operator delete(raw);
#+end_src
所以完整流程是:
#+begin_example
取得存储
    ↓
在存储中构造对象
    ↓
使用对象
    ↓
销毁对象
    ↓
释放存储
#+end_example
** 第三层: 所有权
所有权回答: 谁最终负责清理这项资源。
例如:
#+begin_src cpp
  std::unique_ptr<T>
#+end_src
负责:
1. 记录指针
2. 在离开作用域时销毁对象
3. 释放内存


allocator 本身通常不拥有已分配对象。它更像一个提供服务的策略对象:
#+begin_src cpp
  T *p = traits::allocate(alloc, p);
#+end_src
此后调用者负责记录并最终释放 ~p~.
** 分配策略
分配策略回答:
- 从全局堆分配吗
- 从内存池分配吗
- 从栈上的缓冲区分配吗
- 从共享内存分配吗
- 是否记录分配次数
- 是否按某种对齐方式分配
- 不同 allocator 实例是否能互相释放内存


~std::allocator<T>~ 是默认策略，通常最终使用全局分配函数获得存储。标准规定它的存储通过 ~::operator new~ 获得，但保留了具体调用次数和方式的实现自由。
* allocator 的四个核心操作
对容器作者，最重要的是四个核心操作:
- ~allocate~
- ~construct~
- ~destroy~
- ~deallocate~


现代代码通常通过 ~std::allocator_traits~ 进行调用。
** ~allocate~: 取得未初始化存储
#+begin_src cpp
  T *p = Traists::allocate(alloc, n);
#+end_src
含义是: 取得一块足以容纳 ~n~ 个 ~T~ 的存储空间。这里的 ~n~ 是元素数量。allocator 会自行考虑 ~n * sizeof(T)~ ，调用成功后并不能直接使用 ~p[0]~, 因为元素对象尚未构造。
** ~construct~: 在某个槽位开始对象生命周期
#+begin_src cpp
  Traits::construct(alloc, p, args...);
#+end_src
例如:
#+begin_src cpp
  Traits::construct(alloc, p, "hello");
#+end_src
概念上相当于: ~std::construct_at(p, "hello");~ . 当前的 ~allocator_traits::construct~ 会:
1. 如果 allocator 提供了自己的 ~construct~, 调用它；
2. 否则调用 ~std::construct_at~


当前的 ~std::allocator<T>~ 本身只保留了 ~allocate~, ~allocate_at_least~ 和 ~deallocate~ 等核心接口，不再要求它提供 ~construct~ 和 ~destroy~
** ~destroy~: 结束对象生命周期
#+begin_src cpp
  Traits::destroy(alloc, p);
#+end_src
只析构对象，不释放所在的存储空间。调用后:
#+begin_example
之前：

[ T ]

之后：

[ raw ]
#+end_example
内存还在，但其中不再有一个或者的 ~T~ 对象。
** ~deallocate~: 释放存储空间
#+begin_src cpp
  Traits::deallocate(alloc, p, n);
#+end_src
调用之前必须确保其中的活对象已经全部销毁。

通常要求传回的 ~n~ 与当初传给 ~allocate~ 的数量一致。
* ~allocator_traits~ 是什么
~std::allocator_traits<Alloc>~ 是 allocator 的统一适配层。

标准将其描述为:
#+begin_quote
为各种 allocator 类型提供统一接口的类模板。
#+end_quote
容器不应该假定 allocator 一定具有某个完整接口，而应该通过 traits 查询:
#+begin_src cpp
  using traits_type = std::allocator_traits<allocator_type>;

  using pointer = typename traits_type::pointer;

  using size_type = typename traits_type::size_type;

  using difference_type = typename traits_type::difference_type;
#+end_src
并调用:
#+begin_src cpp
  traits_type::allocate(alloc_, n);
  traits_type::construct(alloc_, p, args...);
  traits_type::destroy(alloc_, p);
  traits_type::deallocate(alloc_, p, n);
#+end_src
** 为什么要多一层 traits
这是C++中的常见设计:
#+begin_example
具体策略类型 Alloc
          ↓
适配与默认行为 allocator_traits<Alloc>
          ↓
泛型容器 vector<T, Alloc>
#+end_example
这样 allocator 自身只需要提供最小接口:
#+begin_src cpp
  template<class T>
  class MyAllocator {
  public:
    using value_type = T;
    T* allocate(std::size_t n);
    void deallocate(T* p, std::size_t n) noexcept;
  };
#+end_src
其他类型别名和默认行为都可以由 ~allocator_traits~ 补齐。

标准目前提供的最小 allocator 示例也主要包括:
#+begin_example
value_type
跨类型构造函数
allocate
deallocate
operator==
#+end_example
* commit-or-rollback
这是我们的 ~simplevector~ 的关键设计。包括:
1. allocate new storage
2. construct new elements
3. 全部成功
4. destroy old elements
5. deallocate old storage
6. commit pointers


我们经常用到的一个设计就是，在完全分配成功之前，都不要对原始的指针等内部表示进行操作。而一旦出现异常，则只需要销毁目前已经构造的元素，不能试图销毁未构造的元素。
* ~construct~, 赋值和移动不是一回事
实现容器时必须区分两个区域。
** 已构造区域
~[begin_, end_)~

可以对这个区域执行:
#+begin_src cpp
  ,*p = value;
  ,*p = std::move(value);
#+end_src
因为对象已经存在。
** 未构造区域
~[end_, capacity_end_)~

不能赋值，只能通过构造开始生命周期:
#+begin_src cpp
  traits_type::construct(alloc_, end_, std::forward<Args>(args)...);
#+end_src
因此插入操作经常需要同时使用 move assignment 和 move construction.

例如，容量足够时向中间插入元素:
#+begin_example
[ A ][ B ][ C ][ raw ]
#+end_example
要向 ~B~ 前插入 ~X~, 大致需要:
1. 在尾部 raw 槽位中移动构造 ~C~
2. 把已有元素向后移动
3. 给目标位置赋值 ~X~


也就是， construct 到 raw 区域， assign 在 live 区域。
* allocator 如何影响 Rule of Five
当 allocator 有状态时，复制、移动和交换都会复杂很多。
** 复制构造
容器复制构造时，并不总是简单复制 allocator:
#+begin_src cpp
  Vector(const Vector &other)
    : alloc_{ traits_type::select_on_container_copy_construction(other.alloc_)}
  {}
#+end_src
~select_on_container_copy_construction~ 默认返回原 allocator, 但自定义 allocator 可以选择返回另一个 allocator.
** 复制赋值
allocator 是否随容器复制赋值，由:
#+begin_src cpp
  traits_type::propagate_on_container_copy_assignment
#+end_src
决定。通常默认是 ~std::false_type~ ，也就是说 ~a = b~ 通常复制元素，但保留 ~a~ 原本的 allocator.
** 移动赋值
由:
#+begin_src cpp
  traits_type::propagate_on_container_move_assignment
#+end_src
以及 allocator 是否相等共同决定。
*** allocator 可以传播
可以接管 allocator 和内存块
*** allocator 不传播，但二者相等
因为目标 allocator 可以释放源 allocator 分配的存储，所以通常也能直接接管缓冲区。
*** allocator 不传播，并且二者不相等
不能直接偷走指针。因为以后目标容器会用自己的 allocator 释放这块内存，但它可能没有资格这样做。

这时必须:
1. 使用目标容器自己的 allocator 分配
2. 逐元素移动
3. 由源容器自己的 allocator 释放源缓冲区
* 小结
** allocator 定义
Allocator(分配器) 是封装内存分配模型的策略对象。它向容器提供存储空间，但容器负责对象生命周期、所有权和异常安全。
** allocator 的核心意义
~storage lifetime != object lifetime~

allocator允许:
- capacity 个存储槽位
- size 个活对象
** 四步模型
#+begin_src cpp
  allocate; // 取得未初始化存储
  construct; // 在存储中开始对象生命周期
  destroy; // 结束对象生命周期
  deallocate; // 释放存储
#+end_src
** 现代扩展
- C++11  allocator_traits
- C++17  std::pmr
- C++20  construct_at
- C++23  allocate_at_least
** 最终理解
智能指针和 allocator 并不是互相替代的工具。

- 智能指针: 管理一个已存在的对象或对象数组的所有权
- allocator: 为容器提供存储或构造策略
- vector: 使用 allocator 管理存储，自己管理哪些槽位中存在对象
