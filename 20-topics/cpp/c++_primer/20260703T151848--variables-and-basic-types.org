#+begin_example

这一章的核心是理解 C++ 的基本哲学:
#+begin_quote
C++ 程序中的每个对象都有类型。类型决定对象的存储、取值范围、解释方式和允许的操作。
#+end_quote
比如承接我们第一章的例子:
#+begin_src cpp
  i = i + j;
#+end_src
如果 ~i~ 和 ~j~ 都是整数，那么 ~+~ 就是算术加法。如果它们是 ~Sales_item~ ，那么 ~+~ 就是合并销售记录。也就是说，同一个表达式的语义由类型决定。

这也是 C++ 和许多动态语言非常不同的地方。 C++ 在编译器会检查类型；如果某个类型不支持某个操作，编译器会直接拒绝生成可执行文件。

* Primitive Built-in Types: 内置基本类型
C++ 的内置基本类型分为两大类:
#+begin_quote
算术类型 arithmetic types
void
#+end_quote
算术类型又分为:
#+begin_quote
integral types 整型，包括 bool 、字符类型、整数类型
floating-point 浮点类型
#+end_quote
~void~ 没有值，不能定义 ~void~ 类型变量，最常见的用途是表示函数不返回值:
#+begin_src cpp
  void log_error();
#+end_src
** Arithmetic Types: 算术类型
C++ Primer 给出了下列基本算术类型:
| Type          | Meaning                           | Minimun Size          |
|---------------+-----------------------------------+-----------------------|
| ~bool~        | boolean                           | NA                    |
| ~char~        | character                         | 8 bits                |
| ~wchar_r~     | wide character                    | 16 bits               |
| ~char16_t~    | Unicode character                 | 16 bits               |
| ~char32_t~    | Unicode character                 | 32 bits               |
| ~short~       | short integer                     | 16 bits               |
| ~int~         | integer                           | 16 bits               |
| ~long~        | long integer                      | 32 bits               |
| ~long long~   | long integer                      | 64 bits               |
| ~float~       | single-precision floating-point   | 6 significant digits  |
| ~double~      | double-precisiion floating-point  | 10 significant digits |
| ~long double~ | extended-precision floating-point | 10 significant digits |

尤其强调，标准只保证最小尺寸，实际大小依赖实现。

这点必须重视。 C++ 的内置类型不是 Javan 那样的完全宽度模型。 C++ 标准为了兼容不同硬件，只规定一些最低要求和相对关系:
#+begin_quote
sizeof(char) <= sizeof(short) <= sizeof(int) <= sizeof(long) <= sizeof(long long)
#+end_quote
更精确地说， ~char~ 至少 8 bits ， ~short~ 至少 16 bits ， ~int~ 至少 16 bits ， ~long~ 至少 32 bits， ~long long~ 至少 64 bits。

在我现在的 x86-64 Linux 的环境下，常见结果大概是:
#+begin_src cpp
    sizeof(char)      == 1
    sizeof(short)     == 2
    sizeof(int)       == 4
    sizeof(long)      == 8
    sizeof(long long) == 8
    sizeof(float)     == 4
    sizeof(double)    == 8
#+end_src
但这不是语言层面的绝对保证。尤其是 ~long~: Linux x86-64 上通常是 64 位， Windows x64 上通常是 32 位。这就是为什么跨平台代码不能轻率假设 ~long~ 的宽度。
*** 类型是什么
类型不是 “数学集合”，而是“存储 + 解释 + 操作”。

计算机把数据存为 bit 序列；最小可寻址单位是 byte；同一串 bit 必须结合类型才有意义。比如同一段 32 位内存，如果类型是 ~float~ ，就按照浮点数解释；如果类型是 ~unsigned char~ ，某个字节可能表示字符。

#+begin_quote
类型决定一段内存占用多少 bit，以及这些 bit 如何解释。
#+end_quote
比如同样的 bit patter:
#+begin_example
01000001
#+end_example
按照 ~unsigned char~ 解释，可能是整数 ~65~ ；如果按照字符集解释，可能是字符 ~'A'~ 。

所以 C++ 的类型至少有三种含义:
1. 存储需求: 需要多少字节，如何对齐
2. 值域：可以表示那些值
3. 操作集合: 可以做哪些运算


这就是为什么C++类型系统和底层机器关系非常紧密。

-----
*** 整型: signed / unsigned

除了 ~bool~ 和扩展字符类型外，整数类型可以有 signed 和 unsigned 版本。 ~signed~ 能表示负数、0、正数； ~unsigned~ 只能表示非负数。

例如:
#+begin_src cpp
  int x = -1;
  unsigned y = 1;
#+end_src
~int~ 是有符号类型， ~unsigned~ 是 ~unsigned int~ 的缩写。
**** ~char~ 的特殊性
C++ 里有三个不同的 ~char~ 类型:
#+begin_example
char
signed char
unsigned char
#+end_example
注意: ~char~ 不是 ~unsigned char~ 或 ~signed char~ 的别名。它是第三种独立类型，只是底层表示会选择 signed 或 unsigned 中的一种。原书特别强调: 普通 ~char~ 到底表现为 signed 还是 unsigned ，取决于编译器。

所以  ~char c = 200;~ 在某些平台上可能表现为负数，在某些平台上可能表现为200附近的非负值。严肃代码里，如果想表达“小整数”，不要用普通 ~char~ ，而应该明确写:
#+begin_src cpp
  signed char x;
  unsigned char y;
#+end_src
但如果想表达字符，就用 ~char~ 。
**** C++20 后的补充: 有符号整数表示
C++ Primer 是 C++ 11 时代的书，因此它说标准不规定 signed 类型如何表示，只保证范围大致均分，现代机器常用 ~-128~ 到 ~127~ 这样的范围。

现代标准这里有变化: C++20 起，标准只允许有符号整数使用二进制补码表示；C++20 之前标准允许多种 signed integer representation ，但 C++20 之后二进制补码是唯一允许的表示。

这意味着在现代 C++ 的语境下，我们可以更放心地认为普通有符号整数的位级是二进制补码。但注意: *这不等于 signed overflow 变成定义良好* 。例如:
#+begin_src cpp
  int x = INT_MAX;
  ++x; // signed overflow, 仍然是 undefined behavior
#+end_src
unsigned 溢出是按照模运算定义的； signed 溢出不是。这一点对安全性、优化和可靠性非常重要。
**** unsigned 的设计: 模运算
~unsigned~ 类型的关键规则是:
#+begin_quote
超出范围时，结果按照模 2^N 回绕。
#+end_quote
比如我的编译器中 ~unsigned int~ 是32位，能表示 ~0~ 到 ~4294967295~ ，那么把 ~-1~ 赋值给它就会得到 ~4294967295~ 。底层逻辑是:
#+begin_quote
-1 mod 4294967296 = 4294967295
#+end_quote
但这并不表示 ~unsigned~ 是 “安全的非负整数”。它其实更像是固定宽度的模整数。
**** signed 和 unsigned 混用
这是 C++ 新手的高危点。
比如:
#+begin_src cpp
  #include <iostream>

  int main() {
    // unsigned int n = -1;
    // std::cout << n << std::endl;

    unsigned u = 10;
    int i = -42;
    std::cout << i + i << std::endl;
    std::cout << u + i << std::endl;
    return 0;
  }
#+end_src
结果是:
#+begin_quote
-84
4294967264
#+end_quote
第二个表达式中， ~i~ 会被转化成 ~unsigned~ ，然后再相加。原书明确警告：不要混用 ~signed~ 和 ~unsigned~ ，因为负的 ~signed~ 会被转换成 ~unsigned~ ，会产生令人意外的结果。

更常见的问题是循环：
#+begin_src cpp
  for (unsigned u = 10; u >= 0; --u)
    std::cout << u << '\n';
#+end_src
这个循环永远不会停止，因为 ~u >= 0~ 永远为真。当 ~u~ 从 0 再减 1，它会回绕到一个很大的数，根据我们前面对于 ~unsigned~ 是模运算的说明。

之后写现代 C++ 时尤其要警惕这个组合:
#+begin_src cpp
  std::vector<int> v
  for (int i = 0; i < v.size(); ++i) { ... }
#+end_src
~v.size()~ 返回的是一个无符号 ~size_type~ ，这会导致 ~int~ 和 ~unsigned~ 比较。

在现代代码中经常写:
#+begin_src cpp
  for (std::size_t i = 0; i < v.size(); ++i) {
    // ...
  }
#+end_src
或者更好:
#+begin_src cpp
  for (const auto& x : v) {
    // ...
  }
#+end_src

~auto~ 关键字会自动检测变量的类型，基于赋予的值。它能够帮助我们编写更清晰的代码，而不用重复类型，尤其是对于复杂类型。

具体可以参照: [[https://learn.microsoft.com/zh-cn/cpp/cpp/auto-cpp?view=msvc-170][Microsoft Visual Studio 2022 auto]]

如果确实需要下标，并且需要倒序，应该非常谨慎，避免写出 unsigned 下溢。
**** Effective Modern C++: ~auto~ 与 size_type
Effective Modern C++ 中特别强调，用 ~auto~ 可以避免一些手写类型造成的移植性问题。例如:
#+begin_src cpp
  std::vector<int> v;
  unsigned sz = v.size() // 不理想
#+end_src
~v.size()~ 返回的真实类型是 ~std::vector<int>::size_type~ ，在 64 位 Windows 上可能和 ~unsigned~ 宽度不同；用 ~auto~ 可以让编译器推导出正确类型:
#+begin_src cpp
  auto sz = v.size();
#+end_src
~auto~ 不只是省打字，还能避免显式声明变量类型错误导致的正确性、性能和移植性问题。

同时也不能滥用，比如 ~auto~ 会保留或丢弃 ~const~ 、引用等信息。这在我们后面的 ~auto~ 会再次学习。
*** 浮点类型
浮点类型默认优先 ~double~ 。C++ 有三种浮点类型:
#+begin_quote
float \\
double \\
long double
#+end_quote
浮点计算通常使用 ~double~ 。 ~float~ 精度通常不够，而 ~double~ 相比 ~float~ 的成本通常可以忽略，有些机器上 ~double~ 甚至更快； ~long double~ 的精度和成本都更依赖实现。

我们可以先形成这个实践判断:
1. 默认用 ~double~
2. 大量内存/带宽敏感的数值数组才考虑 ~float~
3. 确实需要更高精度并确认平台支持时才考虑 ~long double~


例如在算法中使用:
#+begin_src cpp
  double learning_rate = 0.001;
  double source = 0.0;
  double eps = 1e-9;
#+end_src
比盲目使用 ~float~ 更加稳妥。

** Type Conversions: 类型转换

C++ 的算术类型之间有大量隐式转换。赋值时的转换规则:
#+begin_src cpp
  bool b = 42; // true
  int i = b; // 1
  i = 3.14; // 3
  double pi = i; // 3.0
  unsigned char c = -1; // 若8位，则 255
  signed char c2 = 256; // C++ 11 时是 undefined
#+end_src
这里有几条规则:
1. 非 ~bool~ 算术值转 ~bool~ 时，0 为 ~false~ ，非 0 为 ~true~
2. ~bool~ 转其他算术类型时， ~false~ 为 0, ~true~ 为 1
3. 浮点数转整数会被截断
4. 整数转浮点数可能会丢精度
5. 超出 ~unsigned~ 范围按模回绕
6. 超出 ~signed~ 范围会导致未定义行为


未定义行为是标准不指定含义的行为，程序可能看起来正常、崩溃、产生垃圾值，更换编译器、版本、输入等都可能变化；实现定义行为则是由具体实现决定，例如 ~int~ 的大小。
*** 为什么C++保留 undefined behavior
C++ 的目标之一是:
#+begin_quote
不给不需要某项检查的程序强加运行时成本。
#+end_quote
如果每次整数加法都检查溢出，每次数组访问都检查边界，每次指针使用都检查有效性， C++ 就会失去大量底层控制和性能优势。

所以 C++ 选择让某些错误成为 undefined behavior 。这样编译器可以基于 “程序不会触发 UB” 的假设进行优化。例如它可以假设有符号整数不会溢出，从而重排或简化表达式。

这给程序员的要求是:
#+begin_quote
写 C++ 时不能只问“这在我的机器上是什么运行结果”，还要问“标准是否定义了这个行为”。
#+end_quote

** Literals: 字面值
字面值是代码中直接写出来的值，例如:
#+begin_src cpp
  42
  3.14
  'a'
  "hello"
  true
  nullptr
#+end_src
每个字面值都有类型，字面值的形式和值决定其类型。
*** 整型字面值
整型可以写成十进制、八进制、十六进制：
#+begin_src cpp
  20 // decimal
  024 // octal 等于十进制20
  0x14 // hexadecimal, 等于十进制 20
#+end_src
一个非常容易踩坑的例子:
#+begin_src cpp
  int month = 09;
#+end_src
这是非法的。因为以 ~0~ 开头的表示八进制，而八进制没有数字 ~9~ 。

现代 C++ 还支持二进制字面量:
#+begin_src cpp
  0b1010 // C++14 起，等于十进制 10
#+end_src
*** 浮点字面值
默认的浮点字面值是 ~double~:
#+begin_src cpp
  3.14 // double
  3.14f // float
  3.14L // long double
#+end_src
*** 字符和字符串字面值
#+begin_src cpp
  'a' // char
  "a" // const char[2]
#+end_src
注意，这里的 ~'a'~ 是一个字符，而 ~"a"~ 是字符串字面量，实际包含两个字符:
#+begin_quote
'a' \\
'\0'
#+end_quote
字符串字面值的类型是 “常量字符数组”，编译器会在末尾追加 null character ~'\0'~ 。

所以:
#+begin_src cpp
  sizeof('a') // 类型 char
  sizeof("a") // 数组中有 'a' 和 '\0'
#+end_src
** 内置基本类型小结
- 对象 = 一段有类型的内存区域
- 类型 type = 存储大小 + 对齐要求 + 值域 + 表示方式 + 可用操作
- 变量 variable = 带名字的对象，或者引用
- 表达式 expression = 由对象和值组成，产生一个值，并且有类型
- 类型转换 conversion = 在某些上下文中，编译器把一个类型的值变成另一个类型的值
- 未定义行为 UB = 标准不规定结果，不能依赖 “看起来能跑”


接下来我们后面会沿着这个模型继续展开：变量定义、初始化、声明和定义、作用域、引用、指针、 ~const~ 、 ~constexpr~ 、 ~auto~ 、 ~decltype~ 。这些不是孤立语法，而是共同服务一个核心问题:
#+begin_quote
如何精确控制对象的生命周期、可变性、访问方式和类型推导。
#+end_quote

* Variables
这一节讲“变量”。但实际上是在铺垫 C++ 的对象模型、初始化模型、链接模型和作用域模型。后面理解构造函数、 RAII、头文件、ODR、 ~extren~ 、 ~static~ 、 ~const~ 、 生命周期、未定义行为，都要回到这一节。

对于 Variables ， C++ Primer 给出的定义很简洁:
#+begin_quote
变量提供一块可被程序操作的具名存储。每个 C++ 变量都有类型，类型决定变量的内存大小、布局、可存储值范围，以及可施加的操作。
#+end_quote
此外，C++ 程序员经常把 variables 和 object 混用。

这一段需要拆开理解：
#+begin_quote
variable = name + object \\
object = typed region of memory \\
type = storage layout + value interpretation + legal operations
#+end_quote
所以， ~int x = 42~ 并不是单纯创建了一个名字x，而是:
1. 分配一块足以容纳 ~int~ 的存储区域
2. 这块区域的类型是 ~int~
3. 用 42 初始化这块区域
4. 把名字 x 绑定到这块区域
5. 之后在 x 的可见作用域内， x 代表这个对象


这和 Python 这类语言的名字绑定不同。在 Python 里，名字更多是引用某个对象；在 C++ 里，局部变量 ~int x~ 通常直接就是一个对象本身。这个区别在后面理解引用、指针、拷贝、移动、生命周期非常重要。

** Variable Definitions: 变量定义
一个简单变量定义由类型说明符、一个或多个变量名组成，变量名之间用逗号分隔，并以分号结束。定义可以选择性地提供初始值。

例如:
#+begin_src cpp
  int sum = 0, value, unit_sold = 0;
  Sales_item item;
  std::string book("0-201-78345-X");
#+end_src
这三行分别涉及三种情况

*** 一个定义可以定义多个变量
一个定义可以定义多个变量，但不一定都初始化。

对应第一行。这里:
#+begin_quote
sum 是 int, 初始化为 0 \\
value 是 int, 没有显式初始化 \\
units_sold 是 int, 初始化为 0
#+end_quote
这就是 C++ 的一个危险点: 同一个定义语句里，有些变量初始化了，有些没有初始化。

如果这行出现在函数内部，那么 ~value~ 就是为初始化的局部内置对象，读取它的值会导致为定义行为。函数体内定义的变量如果没有初始化，其值是 undefined ；访问这种值是错误。

所以实际上更推荐:
#+begin_src cpp
  int sum = 0;
  int value = 0;
  int units_sold = 0;
#+end_src
或至少保证每个变量都显式初始化。

从可靠性角度，更建议第一种。尤其是当类型、初始化表达式或含义不完全相同时。

*** 类类型对象的默认初始化由类自己决定
#+begin_src cpp
  Sales_item item;
  std::string empty;
#+end_src
对类类型来说，“没有显式初始化”不等于“里面是垃圾值”。类可以定义默认构造行为:
#+begin_src cpp
  std::string empty;
#+end_src
会得到空字符串。 ~string~ 类规定: 如果不提供初始化器，得到的是 empty string.

这和内置类型 ~int~ 等完全不同。比如:
#+begin_src cpp
  int local_int;
#+end_src
函数内部的 ~local_int~ 没有确定值；而 ~std::string local_str;~ 是一个合法的空字符串对象。

这体现了 C++ 的设计思想:
#+begin_quote
内置类型为了性能不自动初始化；类类型可以把初始化策略封装在构造函数里。
#+end_quote
也就是说， ~std::string~ 的作者替我们保证了对象一创建就处于有效位置。这也预示了 RAII 的相关内容: 资源和状态应在对象构造时就建立好。

*** 什么是 Object
对象的定义是:
#+begin_quote
最一般地说， object 是一块能够包含数据并且具有类型的内存区域。
#+end_quote
本书会采用这个广义用法，不管对象是内置类型还是类类型、有名或无名、可读写还是只读，都可以叫 object.

所以以下均可以被视为对象或涉及对象:
#+begin_src cpp
  int x = 1; // x 是具名对象
  std::string s = "hi"; // s 是类类型对象
  42 // 字面值，不是变量，但表达式产生值
  std::string("tmp") // 临时对象
#+end_src
C++ 后面大量术语都围绕 object 展开:
#+begin_quote
object lifetime 对象生命周期 \\
object storage 对象存储 \\
object representation 对象表示 \\
const object 常量对象 \\
temporary object 临时对象 \\
subobject 子对象 \\
#+end_quote
我们可以这样理解:
#+begin_quote
对象 = 某段生命周期内存在的、有类型的存储区域 \\
变量 = 有名字的对象，或者引用
#+end_quote

*** Initializers: 初始化器
对象被初始化，就是对象在创建的那一刻获得指定值。初始化变量的值可以是任意复杂的表达式:
#+begin_src cpp
  double price = 109.99;
  double discont = price * 0.16;
  double salePrice = applyDiscount(price, discont);
#+end_src
这体现了两点:

- 第一，同一条定义中，前面定义的名字可以被后面初始化器使用；
- 第二，初始化器不一定是字面值，还可以是函数调用。


所以初始化不是 “写一个常量进去”，而是 *用一个表达式的结果构造对象的初始状态* 。

*** 初始化不是赋值
:PROPERTIES:
:CUSTOM_ID: d4750c25-5414-469f-9bad-b8e1a4b4d91c
:END:
#+begin_quote
初始化不是赋值。初始化会在对象创建时给它一个初始值。赋值会将对象当前值抹掉，用新的值替换。
#+end_quote
比如:
#+begin_src cpp
  int x = 0; // 初始化
  x = 1; // 赋值
#+end_src
这对于内置类型 ~int~ 好像看起来差别不大，但对于类类型差别非常大:
#+begin_src cpp
  std::string s = "hello"; // 初始化：构造 string 对象
  s = "world"; // 赋值：调用 string 的赋值操作
#+end_src
更典型地:
#+begin_src cpp
  Sales_data data1; // 默认初始化
  Sales_data data2 = data1; // 拷贝初始化
  data1 = data2; // 赋值
#+end_src
这三行可能调用不同的函数:
- 默认构造函数
- 拷贝构造函数
- 拷贝赋值运算符


C++ 对象模型里，“创建对象”和“修改已有对象”是两件事。

*** C++ 的多种初始化方式

书中列出了四种把 ~int units_sold~ 初始化为 0 的写法:

#+begin_src cpp
  int units_sold = 0;
  int units_sold = {0};
  int units_sold{0};
  int units_sold(0);
#+end_src
这四种都能初始化一个 ~int~ ，但它们并不总是等价。尤其对类类型、 ~auto~ 、 ~initializer_list~ 、窄化转换而言。

C++ 初始语法之所以复杂，是历史演化的结果。
- C 继承来的 ~=~ 初始化
- C++ 构造函数引入的 ~()~ 初始化
- C++11 引入的 ~{}~ 列表初始化 / 花括号初始化


*** List initialization: 列表初始化
C++11 推广了 ~{}~ 初始化。花括号初始化可以在很多场景中使用，成为 list initialization；对内置类型来说，它有一个重要性质：如果初始化可能导致信息丢失，编译器不允许。

例如:
#+begin_src cpp
  long double id = 3.1415926;
  int a{id}; // 错误: narrowing conversion
  int b = {id}; // 错误: narrowing conversion

  int c(id); // 可以，但截断
  int d = id; // 可以，但截断
#+end_src
这里 ~a~ 和 ~b~ 被拒绝，因为 ~long double~ 到 ~int~ 会丢失小数部分，甚至可能超出 ~int~ 范围。

这就是 ~{}~ 初始化的重要安全价值:
#+begin_quote
它能在编译器阻止某些窄化转换。
#+end_quote
实际写现代 C++，我们更偏好:
#+begin_src cpp
  int count{0};
  double price{0.0};
  std::string name{"alice"};
#+end_src
但是需要注意，Effective Modern C++对此有一个重要补充：花括号初始化虽然统一，但会和 ~std::initializer_list~ 产生特殊交互，有时导致选择了你没想到的构造函数。此外，它还专门提醒要注意区分 ~()~ 和 ~{}~ 创建对象，尤其是在类有 ~initializer_list~ 构造函数时。

所以在实践上可以形成更细致的判断：
- 内置数据类型: ~{}~ 很合适，可以防止窄化
- 容器显式列元素: ~{}~ 很合适
- 类类型构造: 要知道该类是否有 ~initializer_list~ 构造函数
- ~auto~ 变量: 避免 ~auto x{...}~ 或 ~auto x = {...}~ 的误推导，后面会讲


*** Default Initialization: 默认初始化
如果定义变量时没有初始化器，变量会被 default initialized；默认值取决于变量类型，也可能取决于变量定义的位置。

**** 内置类型的默认初始化
#+begin_quote
函数体外定义的内置变量类型：初始化为 0 \\
函数体内定义的内置变量类型：不初始化，值未定义
#+end_quote
例如:
#+begin_src cpp
  int global_int;
  int main ()
   {
     int local_int;
   }
#+end_src
~global_int~ 是 0, ~local_int~ 是未初始化的，读取它是错误。

C++ 标准资料中， default-initialization 发生在没有初始化器声明对象等场景；对于非类类型，默认初始化通常不会执行初始化动作，而自动存储期对象的未初始化会带来 indeterminate value 相关问题。

最实用的规则是:
#+begin_src cpp
  int x; // 函数内部：危险，未初始化
  int x{}; // 安全，值初始化为0
  int x = 0; // 安全，初始化为0
#+end_src
如果写:
#+begin_src cpp
  int count;
  std::cin >> count;
#+end_src
这通常没问题，因为在读取前并没有使用 ~count~ 的值。但如果后续逻辑复杂，仍然推荐初始化为 0.

**** 为什么 C++ 不自动初始化局部 int
这和 C++ 的设计哲学直接相关:
#+begin_quote
不为未请求的操作付出成本。
#+end_quote
如果每个局部 ~int~ 都自动清零，那么某些性能敏感的代码会被迫支付额外成本。 C++ 选择把责任交给程序员：如果需要初值，就初始化；如果不需要，语言也不强迫付出清零成本。

但如果强调可靠性和安全性优先的话，实践建议通常是:
#+begin_src cpp
  int value{};
  double price{};
  bool ok{}; // false
#+end_src

**** 类类型的默认初始化
类类型由自己控制默认初始化。这意味着类可以保证自己的不变量。例如 ~std::string~ 默认构造后是一个合法字符串，长度为0，可以调用:
#+begin_src cpp
  s.size();
  s.empty();
  s += "hello";
#+end_src
这也是 C++ 类设计的核心目标之一:
#+begin_quote
构造完成的对象应该处于有效状态。
#+end_quote
以后写自己的类，也应该做到:
#+begin_quote
对象一旦构造完成，就要满足不变量；不需要用户额外调用 ~init()~ 才能使用。
#+end_quote

** Variable Declarations and Definitions: 声明与定义
这一节是以后理解头文件、分离编译、链接错误的关键。

为了让程序能被分成逻辑部分，C++ 支持 separate compilation ，也就是多个文件可以独立编译。一个文件可能需要另一个文件中定义的变量，所以C++区分 declaration 和 definition .

核心区别是:
- 声明 declaration: 让名字为程序所知
- 定义 definition: 创建实体，变量定义会分配存储


变量定义本身也是声明。

*** ~extern~: 只声明，不定义
#+begin_src cpp
  extern int i; // 声明 i,但是不定义 i
  int j; // 声明并定义 j
#+end_src
其中， ~extern int i~ 的意思是:
#+begin_quote
有一个 ~int~ 类型的变量 i, 它的定义在别处。当前翻译单元可以使用这个名字，但这里不分配存储。
#+end_quote
~int j~ 则会真正定义一个对象，分配存储。

也就是说，如果要获得一个不是定义的声明，需要加 ~extern~ ，并且不能提供初始化器。 *任何带初始化器的声明都是定义* ； ~extern double pi = 3.14159;~ 是定义，因为它提供了初始化器。

*** 一个变量只能定义一次，但可以声明多次
例如:
#+begin_src cpp
  // config.h
  extern int global_counter;

  // config.cc
  int global_counter = 0;

  // main.cc
  #include "config.h"
  void f() {
    ++global_counter;
  }
#+end_src
这里的 ~global_counter~ 只有在 ~config.cc~ 中的一个定义，但是却可以在多个文件里通过头文件声明 ~extern int global_counter~ 。但是如果把定义写进头文件:
#+begin_src cpp
  // bad_config.h
  int global_counter = 0;
#+end_src
然后多个 ~.cc~ 都 include 这个头文件，这就会导致多个翻译单元各自定义 ~global_counter~ ，链接时通常会报 multiple definition。这就是声明/定义区分的意义。

*** 分离编译的底层流程

以两个文件为例:
#+begin_src cpp
  // a.cpp
  int counter = 0;
#+end_src

#+begin_src cpp
  // b.cpp
  extern int counter;

  void inc()
  {
    ++counter;
  }
#+end_src
编译期大致发生:
#+begin_quote
a.cpp -> a.o \\
b.cpp -> b.o \\
linker 把 a.o 和 b.o 链接成可执行文件
#+end_quote
在编译 ~b.cpp~ 时，编译器只需要知道:
#+begin_quote
counter 是 int
#+end_quote
所以 ~extern int counter;~ 足够让它生成代码。

但 ~counter~ 的真实存储在哪里，需要链接器在 ~a.o~ 中找到定义:
#+begin_src cpp
  int counter = 0;
#+end_src
这就是为什么 C++ 需要声明和定义分开： *编译器处理但个翻译单元，链接器处理跨文件实体匹配* 。

~std::cout~ 和 ~std::cin~ 也是类似的机制。当我们在代码里写
#+begin_src cpp
  #inlcude <iostream>
  std::cout << "hello\n";
#+end_src
这里 ~std::cout~ 并不是我们定义的对象。它由标准库的某处定义，我们通过头文件获得声明，然后链接到标准库实现。


*** 声明、定义和 ODR
这里可以提前引入一个非常重要的概念： *ODR, One Definition Rule* 。

简化理解就是：一个实体在整个程序中通常只能有一个定义；但是声明可以出现多次，只要保持一致。

类定义、模板、inline函数等有更复杂的 ODR 规则，后面会逐步提到。现在先记住变量的基本规则:
#+begin_quote
头文件放声明，不要放普通全局变量定义。 \\
.cc/.cpp 文件放定义。
#+end_quote
C++17 引入了 ~inline variable~ ，可以让某些变量定义安全地放在头文件里，但这是现代扩展点。

** Identifiers: 标识符
标识符就是名字。 C++ 标识符可以由字母、数字、下划线组成，必须以字母或下划线开头，大小写敏感。

例如:
#+begin_src cpp
  int somename, someName, SomeName, SOMENAME;
#+end_src
这是四个不同变量。

*** 关键字不能做标识符

例如:
#+begin_src cpp
  int double = 3.14; // 错误，double 是关键字
#+end_src

*** 保留名字规则很重要
程序员自定义名字不能包含连续两个下划线，不能以下划线+大写字母开头；函数外定义的标识符不能以下划线开头。

也就是说，不要写:
#+begin_src cpp
  int __value;
  int _Value;
  int _global; // 如果在全局作用域，需要避免
#+end_src
这些名字需要留给编译器、标准库、系统头文件实现使用。当我们在工程里使用它们，可能和实现内部名字冲突，导致十分诡异的问题。

实践上建议:
#+begin_src cpp
  int value;
  int student_count;
  int max_buffer_size;
#+end_src
类名可以用大写开头:
#+begin_src cpp
  struct Sales_data {};
  class BookStore {};
#+end_src
普通变量用小写更清晰:
#+begin_src cpp
  int units_sold = 0;
  double total_revenue = 0.0;
#+end_src

** Scope of a Name: 作用域
scope 是程序的一部分，在这个部分中某个名字具有特定含义。C++ 中大多数作用域由花括号界定。名字从声明点开始可见，直到声明所在作用域结束。

例如:
#+begin_src cpp
  #include <iostream>

  int main()
  {
    int sum = 0;

    for (int val = 1; val <= 10; ++val)
      sum += val;

    std::cout << sum << std::endl;
  }
#+end_src
这里有几个名字:
- ~main~: 全局作用域
- ~sum~: ~main~ 函数体的块作用域
- ~val~: ~for~ 语句作用域
- ~std~: 命名空间名
- ~cout~ / ~endl~: ~std~ 命名空间里的名字


~val~ 在 ~for~ 外不可见。

*** 名字从声明点开始可见
比如:
#+begin_src cpp
  int x = 1;

  int main()
  {
    int y = x; // 使用的是全局 x
    int x = 2; // 从这里开始，局部 x 隐藏全局 x
  }
#+end_src
局部 ~x~ 的作用域不是从第一个花括号开始的，而是从它自己的声明点开始。

同理，如果我们在局部作用域里写:
#+begin_src cpp
  int x = x;
#+end_src
右边的 ~x~ 指的是正在声明的这个局部 ~x~ ，但它尚未初始化，读取它会出问题。不要写这种代码。

*** 嵌套作用域与隐藏
看下面这个例子:
#+begin_src cpp
  #include <iostream>

  int reused = 42;

  int main()
  {
    int unique = 0;

    std::cout << reused << " " << unique << std::endl;

    int reused = 0;

    std::cout << reused " " << unique << std::endl;
    std::cout << ::reused << " " << unique << std::endl;

    return 0;
  }
#+end_src
输出是:
#+begin_example
42 0
0 0
42 0
#+end_example
意思是，局部的 ~reused~ 会隐藏全局变量 ~reused~ 。如果要显式访问全局变量，需要使用空的作用域运算符:
#+begin_src cpp
  ::reused
#+end_src
在函数里定义和全局变量同名的局部变量，通常是坏风格。

*** 为什么作用域对 C++ 特别重要
因为 C++ 的名字查找、对象生命周期、析构时机都和作用域强相关。\\
例如:
#+begin_src cpp
  {
    std::string s = "hello";
  } // s 在这里析构
#+end_src
~std::string~ 的生命周期结束点由作用域决定。

这就是 RAII:
- 对象构造时获取资源
- 对象离开作用域时析构并释放资源


所以上述的作用域并不是简单的可见性规则，以后会变成 C++ 资源管理模型的基础。

** Variables 底层逻辑总结
这一节可以压缩成几个核心命题。

1. 变量是具名对象 \\
   #+begin_src cpp
     int x = 0;
   #+end_src
   不是“名字 x 指向某个值”，而是创建了一个 ~int~ 对象，并让 ~x~ 成为它的名字。
2. 初始化发生在对象创建时，赋值发生在对象已存在
   #+begin_src cpp
     T a = expr; // 初始化
     a = expr; // 赋值
   #+end_src
   这对类类型尤其重要。
3. 未初始化的局部内置类型对象是危险的
   #+begin_src cpp
     int x; // 函数内部危险
     int x{}; // 推荐这种方式，可以赋予默认值0
   #+end_src
   原书中反复提醒：未初始化变量导致运行时问题，访问未初始化值是未定义行为，编译器不一定能发现。
4. 声明让名字可见，定义创建实体
   #+begin_src cpp
     extern int x; // 声明
     int x = 0; // 定义
   #+end_src
   这是头文件和分离编译的基础
5. 作用域控制名字可见性，也暗含对象生命周期边界

* Compound Types
这一节的内容不单是 “引用和指针怎么写”，而是我们目前的学习中，第一次把对象 (object) - 地址 (address) - 类型 (type) - 表达式语义 (expression semantics) 串在一起。书中把 *复合类型(compound type)* 定义为 “由其他类型定义而来的类型”，本节先讲两种最基础、也最容易造成长期误解的复合类型: *引用 (reference)* 和 *指针(pointer)* 。

** Compound type: 类型不是孤立的
类型不是孤立的，而是可以被组合出来的。到目前为止，我们看到的声明大多是 ~int i = 0~, ~double d = 3.14~ , ~std::string s = "hello"~ 这种的，看起来像 “一个类型说明符 + 一个变量名”。但是从这一节开始， C++ 的真实声明模型要展开了：
#+begin_src cpp
  int i = 1024, *p = &i, &r = i;
#+end_src
这一个声明里， ~int~ 是 *base type* ，即基础类型；而 ~i~, ~*p~, ~&r~ 分别是 *declarator* ，即声明符。原书特别强调：一个声明不是简单的 “类型 + 名字列表”，而是 *base type + declarator list* 。每个 declarator 都会把名字声明称 “与 base type 有某种关系的类型”。例如， ~p~ 不是 ~int~ ，而是 “pointer to int”； ~r~ 不是普通 ~int~ ，而是 “reference to int” 。

这就是为什么下面这句很容易误读:
#+begin_src cpp
  int* p1, p2;
#+end_src
它并不是两个 ~int*~ 。它等价于:
#+begin_src cpp
  int *p1; // p1 is pointer to int
  int p2; // p2 is int
#+end_src
在 C++ 的声明语法里， ~*~ 和 ~&~ 更贴近 declarator， 而不是单纯贴近 base type 。所以从学习阶段开始，建议采用原书的风格:

#+begin_src cpp
  int *p1, *p2;
  int &r = i;
#+end_src
这样可以提醒自己: ~*p1~, ~*p2~, ~&r~ 是各自的声明符，不要以为 ~int*~ 会自动作用于后面的所有变量。

** Reference: 引用不是对象，而是已有对象的别名
引用是 C++ 新手第一次真正遇到的 “语法表面很像变量，但语义不是变量” 的东西。
#+begin_src cpp
  int ival = 1024;
  int &refVal = ival;
#+end_src
这里 ~refVal~ 是 ~ival~ 的引用。更确切地说， ~refVal~ 是 ~ival~ 的 *alias* ，即别名。原书说得很直接:
 *A reference is not an object. Instead, a reference is just another name for an alreay existing object.* 引用不是一个新的对象，而是绑定到一个已有对象上的名字。

我们可以这样理解:
#+begin_src cpp
  int i = 10;
  int &r = i;

  r = 20;
  std::cout << i << '\n'; // 20
#+end_src
~r = 20~ 不是 “让引用r指向一个新的值”，而是 “通过名字r操作它所绑定的对象i”。引用一旦初始化，就一直绑定到那个对象，没有“重新绑定”这个说法。

比如:
#+begin_src cpp
  int a = 1;
  int b = 2;
  int &r = a;

  r = b;
#+end_src
这句 ~r = b~ 的意思不是让 ~r~ 改为引用 ~b~ ，而是把 ~b~ 的值赋给 ~a~ 。执行后:
#+begin_src cpp
  a == 2
  b == 2
#+end_src
这里， ~r~ 仍然是 ~a~ 的别名。

** 引用必须初始化
引用必须初始化，因为它没有 “空绑定” 状态。

普通变量可以先定义、再赋值:
#+begin_src cpp
  int x;
  x = 42;
#+end_src
但引用不行。

原因不是语法洁癖，而是对象模型决定的。引用不是 *独立对象* ，它没有像指针那样 “保存地址的存储单元” 作为语法层面的对象身份。它必须在创建时绑定到一个已有对象，否则它就没有语义基础。

这也解释了为什么引用常被用来表达一种更强的约束： *这个名字一定代表某个有效对象* 。相较指针，引用没有 ~nullptr~ 这种显式空状态。虽然底层ABI或编译器实现中，引用参数常常会用地址传递，但是 C++ 语言语义不把引用看作 “可为空、可改指向的地址变量”。

这也是C++的一个重要设计哲学： *语言抽象和机器实现不总是一一对应* 。引用在机器上可能通过指针实现，但在语言层面不是指针。我们写程序时必须按照语言规则理解，而不是按照某个编译器的实现猜测它。

** 引用的初始化不是拷贝，而是绑定
看这两句:
#+begin_src cpp
  int i = 42;
  int j = i;
#+end_src
~j~ 是一个新对象，初始化时从 ~i~ *拷贝* 了值。之后 ~i~ 和 ~j~ 独立。

而:
#+begin_src cpp
  int i = 42;
  int &r = i;
#+end_src
~r~ 并不是从 ~i~ 拷贝到值，它只是 *绑定* 到 ~i~ 。所以 ~r~ 修改时，改变的是 ~i~ 。

这和我们在之前的 [[denote:20260703T151848::#d4750c25-5414-469f-9bad-b8e1a4b4d91c][初始化不是赋值]] 中的思想一致。对引用而言，初始化尤其特殊: 它不是给引用对象存入值，因为引用不是对象；它是建立名字和已有对象之间的绑定关系。

** 普通左值只能绑定到对象，且类型必须精确匹配
书中这里讲的是 *lvalue reference* ，即左值引用。C++11引入了 *rvalue reference* , 右值引用，形式是 ~T&&~ ，主要服务于移动语义、完美转发等高级机制。在本节中，如果单独说引用 reference ，那么默认是 *lvalue reference* 。

普通非 const 左值引用有两个限制:
#+begin_src cpp
  int &r1 = 10; // error
  double d = 3.14;
  int &r2 = d; //error
#+end_src
第一句错误，因为 ~10~ 是字面值，不是一个可被普通 ~int&~ 绑定的对象。第二句错误，因为 ~d~ 是 ~double~ 对象，而 ~r2~ 要求绑定到 ~int~ 对象。这里不能先做 ~double -> int~ 转换，然后让 ~int&~ 绑定到临时 ~int~ 。因为那会让我们以为自己能通过 ~r2~ 修改 ~d~ ，实际上修改的是临时对象。C++ 禁止这种误导性的非 const 引用绑定。

但是后面会讲到一个例外，在有关 ~const~

#+begin_src cpp
  const int &r = 10; // ok
  const int &r2 = 3.14 // ok, but binds to a temporary int
#+end_src
但这是 ~const reference~ 的特殊规则，不要提前混淆。当前阶段先记住： *普通 ~T&~ 要绑定到一个同类型的、真实存在的对象* 。

-----

** Pointer: 指针是对象，保存地址，可以改变
指针 (pointer) 也是复合类型，但它和引用的根本差异是： *指针本身是对象* .
#+begin_src cpp
  int i = 42;
  int *p = &i;
#+end_src
~p~ 是一个对象，它的值是 ~i~ 的地址。它占有自己的存储空间；你可以拷贝它、赋值给它、让它先指向 ~i~ ，再指向别的对象。
#+begin_src cpp
  int i = 1;
  int j = 2;

  int *p = &i;
  p = &j; // p now points to j
#+end_src
这和引用形成鲜明对比:
#+begin_src cpp
  int &r = i;
  r = j; // assigns j's value to j, does not rebind r
#+end_src
所以引用表达的是“别名关系”，指针表达的是“地址值关系”。

** ~&~ 和 ~*~ 有两套含义：声明上下文与表达式上下文
~&~ 和 ~*~ 在不同上下文中含义完全不同。

声明中:
#+begin_src cpp
  int &r = i; // & means reference declarator
  int *p = &i; // * means pointer declarator
#+end_src
表达式中:
#+begin_src cpp
  p = &i; // & means address-of operator
  *p = 10; // * means dereference operator
#+end_src
所以这一句:
#+begin_src cpp
  int &r2 = *p;
#+end_src
左边的 ~&~ 是声明符的一部分，表示 ~r2~ 是引用；右边的 ~*p~ 是解引用表达式，得到 ~p~ 所指向的那个 ~int~ 对象。


** 指针的值有几种状态: 有效不等于可解引用
书中把 pointer value 分成四类:
1. 指向某个对象
2. 指向某个对象之后的紧邻位置，也就是 one past the end
3. 空指针 (null pointer)
4. 无效指针 (invalid pointer)


重点是: *valid pointer 不一定可以 dereference* 。

比如:
#+begin_src cpp
  int *p = nullptr;
#+end_src
~p~ 是一个 *有效* 的空指针值，我们可以比较它:
#+begin_src cpp
  if (p == nullptr) {}
#+end_src
但不能解引用:
#+begin_src cpp
  *p = 42; // undefined behavior
#+end_src
再比如数组中常见的 one past the end pointer:
#+begin_src cpp
  int arr[3] = {1, 2, 3};
  int *end = arr + 3;
#+end_src
~end~ 是合法的“尾后指针”，可用于比较无效、迭代边界判断，但不能解引用:
#+begin_src cpp
  *end; // undefined behavior
#+end_src
这体现了 C++ 的内存模型：语言允许你持有某些“边界地址”用于算法表达，但不允许把它当作对象访问。

** 解引用：从地址回到对象
当指针确实指向一个对象的时候，可以使用解引用运算符 (dereference operator) 访问对象:
#+begin_src cpp
  int i = 42;
  int *p = &i;

  std::cout << *p << '\n'; // 42

  ,*p = 0;
  std::cout << *p << '\n'; // 0
#+end_src
~*p~ 不是 “指针里的值”，而是 “指针p指向的对象”。所以 ~*p = 0~ 修改的是 ~i~ 。

这有一个非常重要的类型系统含义：指针类型不仅保存地址，还告诉编译器 “这个地址应按照什么类型解释”。例如：
#+begin_src cpp
  double d = 3.14;
  double *pd = &d;
  int *pi = pd; // error
#+end_src
这里，为什么不能把 ~double *~ 随便赋值给 ~int *~ ？因为 ~int*~ 的解引用会告诉编译器：“请把这块地址上的比特解释为 int ，并允许 int 操作”。如果实际那里是 ~double~ 对象，访问语义就错了。C++ 的静态类型系统在这里保护了对象类型。

** ~nullptr~: 现代 C++ 中表示空指针的正确方式
C++11 引入了 ~nullptr~ ，它是 *pointer literal* ，即指针字面值。 cppreference 也说明: ~nullptr~ 是 ~std::nullptr_t~ 类型的纯右值 (prvalue) ，可以隐式转换为空的任意指针类型。

所以现代 C++ 应写:
#+begin_src cpp
  int *p = nullptr;
#+end_src
而不是:
#+begin_src cpp
  int *p = 0;
  int *p = NULL;
#+end_src
~0~ 的问题是它首先是一个 ~int~ 。只有在上下文需要指针时，它才被当作空指针常量使用。 ~NULL~ 通常也是某种整数常量宏。 Effective Modern C++ 中强调: ~0~ 和 ~NULL~ 在重载和模板类型推导中会造成错误直觉； ~nullptr~ 的实际类型是 ~std::nullptr_t~ ，可以转换到所有 raw pointer 类型，但不会被当作整数。

比如这个典型问题:
#+begin_src cpp
  void f(int);
  void f(void *);

  f(0); // calls f(int)
  f(nullptr); // calls f(void *)
#+end_src
如果想表示 “空指针”，就写 ~nullptr~ ，不要写 ~0~ 或 ~NULL~ 。这是类型系统上的问题。

** 指针可以用于条件判断，但前提是指针值有效
#+begin_src cpp
  int i = 1024;
  int *p1 = nullptr;
  int *p2 = &i;

  if (p1) {
    // false
  }

  if (p2) {
    // true
  }
#+end_src
空指针会在条件中被转换为 ~false~ ，非空指针会被转换为 ~true~ 。但注意， *参与条件判断的指针本身也必须是有效指针值* 。未初始化的指针不只是 “不知道指向哪里”，而是它的值是 indeterminate ，读取这个值本身就可能导致未定义行为。当指针用于条件或比较时，也必须是 valid pointer 。

比如合格错误示例:
#+begin_src cpp
  int *p; // uninitialized local pointer

  if (p) { // undefined behavior: reading invalid pointer value
    
  }
#+end_src
安全的写法是:
#+begin_src cpp
  int *p = nullptr;
  if (p) {
    // ...
  }
#+end_src
这就是为什么 “初始化所有指针” 比初始化所有普通整数变量还要重要。

** ~void *~: 只有地址，没有对象类型
~void *~ 是一种特殊指针类型，可以保存任意对象的地址:
#+begin_src cpp
  double obj = 3.14;
  double *pd = &obj;

  void *pv = &obj;
  pv = pd;
#+end_src
但是 ~void*~ 丢失了 “该地址处对象是什么类型” 的信息。原书说， ~void*~ 能做的事情很有限：比较、传参、返回、赋给另一个 ~void*~ 。不能通过 ~void*~ 直接操作它指向的对象，因为 *类型决定可执行的操作* ，而 ~void *~ 不知道对象类型。

例如:
#+begin_src cpp
  void *pv = &obj;
  *pv; // error: cannot deference void* as an object type
#+end_src
必须先恢复类型:
#+begin_src cpp
  double *pd2 = static_cast<double *>(pv);
  std::cout << *pd2 << '\n';
#+end_src
但这要求程序员真的知道 ~pv~ 原本保存的是 ~double~ 对象地址。如果错把它转成 ~int*~ 再解引用，就是未定义行为或严格别名相关问题的入口。

设计上， ~void*~ 是 C/C++ 低层接口的遗产：它允许把内存当作 “裸地址” 传递，但它绕开了类型信息。现代 C++ 中，普通业务代码应尽量少用 ~void*~ ；泛型用模板，所有权用智能指针，类型擦除用 ~std::any~, ~std::function~, 虚函数接口等更高层设施。

** 指向指针的指针: pointer to pointer
因为指针本身也是对象，所以也有地址。因此可以有指向指针的指针:
#+begin_src cpp
  int ival = 1024;
  int *pi = &ival;
  int **ppi = &pi;
#+end_src
这里， ~pi~ 是 ~int*~ ，指向 ~ival~ 。 ~ppi~ 是 ~int**~ ，指向 ~ival~ 。访问时:
#+begin_src cpp
    std::cout << ival << '\n';   // 1024
    std::cout << *pi << '\n';    // 1024
    std::cout << **ppi << '\n';  // 1024
#+end_src
~*ppi~ 得到的是 ~pi~ 这个指针对象； ~**ppi~ 才得到最终的 ~int~ 对象。

这类声明要围绕名字读:
#+begin_src cpp
  int **ppi;
#+end_src
~ppi~ is a pointer to pointer to int.

** 指向指针的引用: reference to pointer

引用不是对象，所以不存在 “指向引用的指针”。但指针是对象，所以就存在 “指向指针对象的引用”:
#+begin_src cpp
  int i = 42;
  int *p = &i;
  int *&r = p;
#+end_src
对于 ~*&r~ 的定义我们这样念: ~r~ 是一个引用(~&r~)，引用到 ~int*~ 这个指针。所以 ~r~ 是指向 ~int~ 的指针的引用。

验证:
#+begin_src cpp
  int i = 42;
  int j = 100;

  int *p = &i;
  int *&r = p;

  ,*r = 0;   // modifies i, i becomes 0

  r = &j;   // modifies p itself, p now points to j

  ,*r = 7;   // modifies j, j becomes 7
#+end_src
这里要区分:
#+begin_src cpp
  *r = 0;
#+end_src
~r~ 是 ~p~ 的别名。所以 ~*r~ 等价于 ~*p~ ，修改 ~p~ 指向的对象 ~i~ 。

而:
#+begin_src cpp
  r = &j;
#+end_src
这是给 ~p~ 赋新地址，因为 ~r~ 是 ~p~ 的别名，执行后 ~p~ 改为指向 ~j~ 。

这说明引用并不总是 “引用普通对象”；它还可以引用一个指针对象。后面函数参数中会经常看到这种模式，用于让函数修改调用者传入的指针:
#+begin_src cpp
  void reset(int *&p) {
    p = nullptr;
  }
#+end_src
调用后，实参函数本身会被修改成空指针。

** 引用和指针核心差异总结
不要只记语法，从对象模型理解:
| 维度                   | 引用 ~T&~                                | 指针 ~T*~                                    |
|------------------------+------------------------------------------+----------------------------------------------|
| 是否是对象            | 语言层面不是对象，是别名                | 是对象，保存地址值                          |
| 是否必须初始化        | 必须                                     | 不必须，但强烈建议初始化                    |
| 是否可重新绑定/改指向 | 不可以                                   | 可以                                         |
| 是否可为空            | 普通引用没有空状态                      | 可以说 ~nullptr~                             |
| 使用方式               | 自动访问被绑定对象                      | 需要 ~*p~ 解引用                            |
| 表达语义               | “这个名字就是那个对象”                  | “这个对象保存另一个对象的地址”             |
| 常见用途               | 参数传递、别名、避免拷贝、表达非空对象 | 可选函数、动态对象、数组遍历、底层内存操作 |

现代 C++ 的倾向是: \\
能用引用表达的，不要用指针；需要空状态、重绑定、动态所有权或C接口时，再考虑指针。

现代C++不鼓励随意使用 raw pointer 表达所有权。 Effective Modern C++ 中明确把内置指针称为 raw pointer ，并把 smart pointer 作为现代资源挂你的重要替代；例如 ~std::unique_ptr~ 表达独占所有权， ~std::shared_ptr~ 表达共享所有权。

也就是说，裸指针 ~T*~ 更适合表达:

#+begin_quote
  我访问/观察一个对象，但是不拥有它。
#+end_quote
而不是：我负责释放它。

所有权问题要等到后面 ~new/delete~, RAII, 智能指针时系统展开。


** C++ 为什么同时拥有指针和引用

从语言设计上来看，引用和指针解决的是不同层次的问题。

指针来自C的系统编程传统，它暴露地址，允许你接近机器的内存模型：对象在内存中有位置，指针保存位置，解引用通过位置访问对象。这给了 C++ 高性能、底层控制、与硬件和 C ABI 交互的能力。但代价是安全性：空指针、悬垂指针、野指针、越界指针都可能产生 undefined behavior 。

引用则更像是 C++ 为类型系统和抽象机制增加的“安全别名”。它让你可以避免拷贝，有不必把 “地址值” 暴露给使用者。例如函数参数:
#+begin_src cpp
  void increment(int &x) {
    ++x;
  }
#+end_src
调用者写:
#+begin_src cpp
  increment(i);
#+end_src
语义上就是 “把对象i交给函数，让函数处理它”。不需要写:
#+begin_src cpp
  increment(&i);
#+end_src
函数内部也不需要写:
#+begin_src cpp
  ++(*p);
#+end_src
引用让接口更接近“对象语义”，指针让接口更接近“地址语义”。

C++ 的复杂性就在这里：它同时保留底层机器模型，又提供高层抽象设施。你必须知道什么时候自己正在写“对象层面的代码”，什么时候正在写“地址层面的代码”。
* Const Qualifier

这一节是在前面 *object - type - reference - pointer* 的基础上，引入 C++ 类型系统中第一个真正重要的“权限约束”： *通过某个名字、引用或指针，是否允许修改对象* 。

~const~ 的核心不是 “这个内存永远都不会变”，而是：
#+begin_quote
在某个类型视角下，这个对象或被指向对象不允许被修改。
#+end_quote

同时还会学习C++的一个基础设计原则:
#+begin_quote
const correctness = 用类型系统表达 “不可变约束”
#+end_quote
我们分为三个层次来讲:
1. const 的语言语义(C++ 标准层面)
2. 指针/引用中的 const 组合规则(类型系统核心)
3. 现在C++的设计扩展(C++11 ~ C++20)

-----

** const qualifier: 把 “不能修改”写进类型系统
*const qualifier(const 限定符)* 用来限定一个对象的类型，使该对象在初始化后不能再被赋新值。比如缓冲区大小：我们希望它有名字，方便维护；又希望它不会被误改，所以写成 ~const int bufSize = 512~ 。书中明确指出：因为 ~const~ 对象创建后不能改变，所以必须初始化。

比如:
#+begin_src cpp
  const int bufferSize = 512; // ok
  bufSize = 1024; // error: cannot assign to const object
  const int i = get_size(); // ok: 运行期初始化也可以
  const int j = 42; // ok: 编译器常量初始化
  const int k; // error: const 对象必须初始化
#+end_src
这里需要区分三个层次:
#+begin_src cpp
  int x = 42;
  const int cx = 42;
  constexpr int cex = 42;
#+end_src
- ~x~ 是普通对象，可以修改
- ~cx~ 是 *const object(常量对象)* ，初始化之后不能通过 ~cx~ 修改
- ~cex~ 是 *constexpr object(常量表达式对象)* ，不仅不能修改，而且其初始化必须能在编译期求值。 \\
  当前 C++ 标准草案也规定: ~constexpr~ 用在对象声明上会使对象成为 ~const~ ，并且对象必须是 literal type 且被初始化。 \\
  所以，就会有：
  #+begin_src cpp
    int f();

    const int a = f(); // ok, 但 a 不是 constant expression
    constexpr int b = f(); // error, 除非 f 是 constexpr function
  #+end_src
这就是本节最后的 ~constexpr~ 的伏笔: *const 管能不能改， constexpr 管能不能作为编译期值* 。


** const 对象的初始化、拷贝与类型约束

~const~ 对象虽然不能被赋值，但可以用来初始化另一个对象:
#+begin_src cpp
  const int ci = 42;
  int i = ci; // ok, 拷贝 ci 的值
#+end_src
  
这并不矛盾。因为拷贝 ~ci~ 并没有改变 ~ci~ 本身。 ~ci~ 的不可修改性，保护的是 ~ci~ 这个对象，而不是它的值42不能被赋值。

更底层地说，C++对象模型是：对象是一块具有类型的存储区域。 ~const int ci~ 说明这块存储区域通过 ~ci~ 这个名字不能被修改；但读取它的值、用它初始化另一个 ~int~ 对象，是允许的。
#+begin_src cpp
  const int ci = 42;
  int j = ci; // j 是一个新的 int 对象
  j = 100; // ok, j 不是 const
#+end_src
这里就出现一个关键问题: ~const~ 修饰的到底是谁？这会在指针和引用中变得复杂。

** 默认情况下，文件作用域 const 具有内部链接
#+begin_src cpp
  // constants.h
  const int bufSize = 512;
#+end_src
如果这个头文件被多个 ~.cpp~ 文件包含，在普通变量的规则下会导致多重定义。但 C++ 对 namespace scope 的非 ~extern const~ 做了特殊处理：它默认具有 *internal linkage(内部链接)* 。也就是说每个翻译单元各有一份自己的 ~bufSize~ 。C++ Primer 也解释了：为了避免多重定义， ~const~ 变量默认局部于文件；如果要跨文件共享同一个 ~const~ 对象，需要在定义和声明都使用 ~extern~ 。 cppreference 对现代规则的表述也是：非局部、非 volatile 、非 extern 的 const 变量默认给出 internal linkage 。C++17 起还需要考虑 inline 变量例外。

经典写法是:
#+begin_src cpp
  // file_1.cpp
  extern const int buffSize = get_size(); // definition

  // file_1.h
  extern const int bufSize; // declaration
#+end_src

现代 C++17之后，更常见的是:
#+begin_src cpp
  // constants.h
  inline constexpr int bufSize = 512;
#+end_src
*inline variable(内联变量)* 允许同一个变量定义出现在多个翻译单元中，只要定义一致，并且它在整个程序中仍然是一个实体、具有同一个地址。

所以在现代实践中:
#+begin_src cpp
  // C++17 +
  inline constexpr std::size_t buffer_size = 4096;
#+end_src
通常要优于:
#+begin_src cpp
  #define BUFFER_SIZE 4096
#+end_src
因为前者有类型、有作用域、参与类型检查；后者只是预处理器文本替换。


** reference to const: 引用到 const
本节的第一个容易误解的概念是 *reference to const* ，对 const 的引用。
#+begin_src cpp
  const int ci = 1024;
  const int &r1 = ci; // ok
  r1 = 42; // error;
  int &r2 = ci; // error
#+end_src
所谓的 “const reference” ，只是口语缩写。严格说应该叫 *reference to const* ，因为引用不是对象，引用本身不能再绑定到别的对象。所以不存在 “const reference” 这种对象层面的东西。 ~const int&~ 的意思是 “这个引用把被引用对象当作 const int 来看”。

也就是说， ~const int &r = i;~ 不是说这个 ~r~ 引用本身 const, 因为引用天然不能重复绑定。它说的是:
#+begin_quote
通过 r 不能修改 i 。
#+end_quote


** reference to const 可以绑定到非 const 对象
#+begin_src cpp
  int i = 42;
  int &r1 = i;
  const int &r2 = i;

  r1 = 0; // ok, i 变成 0
  r2 = 0; // error, 不能通过 r2 修改 i
#+end_src
~r2~ 不能修改 ~i~ ，但 ~i~ 本身可以被修改。 reference to const 限制的只是“通过该引用能做什么”，并不一定说明底层的对象本身一定是 const 。

这也是: ~const~ 很多时候都不是物理不可变性，而是 *access path immutability (访问路径上的不可修改性)* 。

可以把它理解成:
#+begin_src cpp
  int i = 42;

  const int &view  = i; // 只读视图
#+end_src
~view~ 本身只是一扇只读窗口，但房子本身不一定不可变。

** reference to const 可以绑定到字面值、表达式和临时对象
普通左值引用 ~int&~ 要求绑定到一个真实、可修改的 ~int~ 左值:
#+begin_src cpp
  int &r  = 42; // error
  int &r2 = i + 1; // error
#+end_src
但是 ~const int&~ 可以:
#+begin_src cpp
  const int &r1 = 42; // OK
  const int &e2 = i + 1; //OK
#+end_src
这里发生了 *temporary materialization (临时对象实质化)* 与 *lifetime extension (生命周期延长)* 。可以粗略理解为编译器生成了一个临时 ~const int~ 对象，然后让引用绑定到它:
#+begin_src cpp
  const int temp = 42;
  const int &r1 = temp;
#+end_src
更值得注意的是类型转换:
#+begin_src cpp
  double dval = 3.14;
  // int &r1 = dval; // error
  const int &r2 = dval; // OK, 但 r2 绑定到的不是 dval ，而是临时的 int(3)
#+end_src
这不是让 ~ri~ 成为 ~dval~ 的别名，它大致等价于:
#+begin_src cpp
  const int temp = dval; // 截断为 3
  const int &ri = temp;
#+end_src
所以:
#+begin_src cpp
  double dval = 3.14;
  const int &ri = dval;
  dval = 4.99;
  // ri 仍然是3 ，不会变成4
#+end_src
而为什么普通的 ~int&~ 不允许这种绑定呢？因为如果允许:
#+begin_src cpp
  int &ri = dval; // 假设允许
  ri = 10;
#+end_src
用户很可能以为 ~dval~ 被修改为了10,但实际上引用可能绑定到转换产生的临时对象。这种语义太误导，因此语言禁止非 const 引用绑定到需要转换产生的临时对象。


** pointer to const: 指向 const 的指针
引用和指针的 const 规则比较相似，但指针更复杂，因为指针本身是对象。

先看 *pointer to const*:
#+begin_src cpp
  const double pi = 3.14;
  double *ptr = &pi; // error
  const double *cptr = &pi; // OK

  *cptr = 42; // error
#+end_src
~const duble *cptr~ 的意思是:
#+begin_quote
cptr 是一个指针，指向一个被视为 const double 的对象。
#+end_quote
注意， ~cptr~ 本身可以改:
#+begin_src cpp
  const double pi = 3.14;
  const double e = 2.718;
  const double *p = &pi;

  p = &e; // OK, p 可以改指向
  ,*p = 0.0; // error 不能通过 p 修改对象
#+end_src
pointer to const 也可以指向非 const 对象:
#+begin_src cpp
  double d = 3.14;
  const double *p = &d; // OK
  ,*p = 2.0; // error
  d = 2.0; // OK
#+end_src
这和 ~const int&~ 指向非 ~const~ 对象的语义一样: 限制的是 “通过这个指针不能修改”，不是对象本身不能修改。 point / reference to const 可以理解为 “它认为自己指向/引用的是const”，因此该 pointer/reference 不允许通过它自己修改。但如果指向的并不是一个 const, 仍然可以通过别的方式修改。


** const pointer: 常量指针
因为指针是对象，因此指针本身也可以是 const 。这叫 *const pointer* ，常量指针。
#+begin_src cpp
  int errNumb = 0;
  int *const curErr = &errNumb;
#+end_src
从右往左读:

~curErr~ 先和 ~const~ 结合，所以 ~curErr~ 本身是一个 const；再看 ~*~ 说明它是一个指针；最后基础类型是 ~int~ 。所以:
#+begin_quote
curErr 是一个 const pointer to int.
#+end_quote
常量指针不能换指向:
#+begin_src cpp
  int a = 1;
  int b = 2;
  int *const p = &a;
  p = &b; // error, p 本身不能改
  *p = 0; // ok, a 变成 0
#+end_src
当然也可以两边都是用 ~const~:
#+begin_src cpp
  const double pi = 3.14159;
  const double *const pip = &pi;
#+end_src
~pip~ 是:
#+begin_quote
const pointer to const double.
#+end_quote
所以，这个指针指向的对象不能通过它修改；这个指针的指向本身也不能修改。也就是说:
#+begin_src cpp
  ,*pip = 2.72; // error, pointer to const
  pip = nullptr; // error, const pointer
#+end_src
对于 ~const pointer~ 和 ~pointer to const~ ，这是两个不同的维度。我们使用从右往左读的方法判断其类型。

** top-level const 与 low-level const
:PROPERTIES:
:CUSTOM_ID: 95b1563a-0899-4768-85c1-9a387ef79697
:END:
*top-level const*: 顶层const, 对象本身是 const
*low-level const*: 底层 const, 复合类型所指向、引用、间接访问的对象是 const .
#+begin_src cpp
  int i = 0;

  int *const p1 = &i; // top-level const: p1 本身不可改
  const int ci = 42; // top-level const: ci 本身不可改

  const int *p2 = &ci; // low-level const: p2 指向 const int
  const int *const p3 = p2; // 左边 const 是 low-level, 右边 const 是 top-level

  const int &r = ci; // 引用中的 const 总是 low-level
#+end_src

top-level const 表示对象本身是 const; low-level const 出现在指针、引用等复合类型的基础类型部分。指针可以同时拥有 top-level 和 low-level const. 

*** 拷贝时， top-level const 会被忽略
#+begin_src cpp
  const int ci = 42;
  int i = ci; // OK
#+end_src
这里复制的是值。 ~ci~ 不可改的这个事实，不影响它把值复制到普通 ~int~ 。

指针也一样:
#+begin_src cpp
  int i = 0;
  const int *p2 = &i;
  const int *const p3 = p2;

  p2 = p3; // OK: p3 本身是 const 不会被复制
#+end_src
~p3~ 是 const pointer, 但拷贝它的值只是拷贝里面存的地址，不会修改 ~p3~ 。

*** 拷贝时， low-level const 不能随便丢弃
原因很简单:
#+begin_src cpp
  const int ci = 42;
  const int *p2 = &ci;

  int *p = p2; // error
#+end_src
因为如果允许，就可以通过 ~p~ 修改 ~ci~ 了，就会出现很诡异的情况:
#+begin_src cpp
  *p = 100; // 通过 int* 修改 const int?
#+end_src
这会破坏 const 约束。

但是，从非 const 到 const 是允许的:
#+begin_src cpp
  int i = 0;
  int *p = &i;

  const int *cp = p; // OK
#+end_src
因为增加只读限制是安全的；减少只读限制是不安全的。 C++ Primer 对此的总结是：复制对象时， top-level const 可以忽略， low-level const 不可以忽略；通常可以从 noconst 复制到 const ，不能反过来。


** const 与 auto: 先提前建立规则
严格来说 ~auto~ 是2.5节的内容，但是我们可以先提前打通联系。

#+begin_src cpp
  const int ci = 42;
  const int &cr = ci;

  auto a = ci; // int, top-level const 被丢弃
  auto b = cr; // int, 引用被看作其绑定对象, top-level const 被丢弃

  auto c = &ci; // const int*, low-level const 保留
#+end_src
如果希望保留顶层 const:
#+begin_src cpp
  const auto x = ci; // const int
#+end_src
如果希望引用:
#+begin_src cpp
  auto &r1 = ci; // const int&
  const auto &r2 = 42; // OK
#+end_src
C++ Primer 在下一节会正式讲： ~auto~ 通常忽略 top-level const, 但保留 pointer-to-const 这种 low-level const. Effective Modern C++ 也把这一类规则放到类型推导的核心位置：按值推导时会忽略引用性以及顶层 const / volatile；引用或指针推导时则会保留相应的 const 限定。

这条规则后面会反复出现:
#+begin_src cpp
  const std::string s = "hello";

  auto x = s; // std::string 复制一份. x 可改
  const auto y = s; // const std::string
  auto &z = s; // const std::string&
#+end_src


** constexpr and constant expressions: 编译期值
*constexpr expression* （常量表达式）是值不会改变、并且能在编译期求值的表达式。
#+begin_src cpp
  const int max_files = 20; // constant expression
  const int limit = max_files + 1; // constant expression

  int staff_size = 27; // not constant expression
  const int sz = get_size(); // not constant expression
#+end_src
为什么 ~staff_size~ 不是：因为它不是 const

为什么 ~sz~ 不是: 因为 ~get_size()~ 的结果通常运行期才能知道。

*** constexpr variale: 要求编译器验证
#+begin_src cpp
  constexpr int mf = 20;
  constexpr int limit = mf + 1;
  constexpr int sz = size(); // 只有 size 是 constexpr function 才 ok
#+end_src
~constexpr~ 的好处不是 “让东西更 const”，而是把你的意图交给编译器检查。
#+begin_src cpp
  const int n = get_size(); // 运行期 OK
  constexpr int n = get_size(); // 编译期检查: get_size() 必须可编译期求值
#+end_src
所以 C++ Primer 的建议是：如果打算把变量用作 constant expression, 通常应该用 ~constexpr~ 。

Effective Modern C++ 更进一步: ~constexpr~ 不只是 “常量”，而是让部分原本运行期做的工作迁移到编译期；如果构造函数、成员函数、非成员函数都满足 ~constexpr~ 条件，一个对象甚至可以在编译期就完成计算并放入只读内存。

** literal type: 能参与 constexpr 的类型
*literal type (字面值类型)* 是足够简单、可以拥有编译期字面值的类型。

在C++11的语境里，算术类型、引用、指针是 literal type； ~Sales_item~ 、IO类型、 ~std::string~ 这类库类型当时不属于本节语境下可以 ~constexpr~ 的类型。
#+begin_src cpp
  constexpr int i = 42; // OK
  constexpr double d = 3.14; // OK
  constexpr int *p = nullptr; // OK

  std::string s = "hello"; // OK
  constexpr std::string cs = "hi"; // C++ 下不行
#+end_src
~constexpr~ 要求类型和初始化过程都能被编译器在常量求值语境中处理。
立

** constexpr pointer: constexpr 修饰的是指针本身
#+begin_src cpp
  const int *p = nullptr;
  constexpr int *q = nullptr;
#+end_src
二者完全不同。 ~const int *p~ 表示 p 是 pointer to const int, p 可以改指向，但不能通过 p 修改 int. ~constexpr int *q~ 表示 q 是 ~constexpr object~ ，因此 q 本身是 ~const pointer to int~ 。也就是说:
#+begin_src cpp
  constexpr int *q = nullptr;
  int *const q = nullptr;
#+end_src
在等价方向上二者接近。在 ~constexpr~ 指针声明中， ~constexpr~ 作用于指针本身，而不是指针所指的类型； ~constexpr~ 会给它定义的对象施加 top-level const. 

所以:
#+begin_src cpp
  constexpr int *q = nullptr; // q 是 const pointer to int
  constexpr const int *p = &i; // p 是 const pointer to const int
#+end_src
再注意: ~constexpr~ 指针只能初始化为 ~nullptr~ 、 ~0~ ，或指向有固定地址的对象。局部自动变量通常不能作为 ~constexpr~ 指针的目标；全局对象、静态局部对象有固定地址，可以。

也就是说:
#+begin_src cpp
  int gloabl = 0;
  constexpr int *p = &global; // OK, global 有固定地址

  int main() {
    int local = 0;
    // constexpr int *q = &local; // error. local 地址不是常量表达式
  }

#+end_src

** C++20 之后: const, constexpr, consteval, constinit 的分工
现代 C++ 又引入了两个相关关键词。

*** consteval: 必须编译期求值的函数
*consteval (立即函数)* 用于函数，要求其调用在需要的语境中产生 constant expression. immediate function 是 constexpr function , 并且 consteval 也隐含 inline；潜在求值的 immediate invocation 必须产生 constant expression.
#+begin_src cpp
  consteval int square(int x) {
    return x * x;
  }
  int a = square(3); // OK, 编译期求值
#+end_src
和 ~constexpr~ 的区别可以记为:
#+begin_src cpp
  constexpr int f(int x) { return x * x; } // 可以编译期，也可以运行期
  consteval int g(int x) { return x * x; } // 必须编译期
#+end_src

*** constinit: 保证静态初始化，但不保证不可修改
*constinit* 是 C++20 引入的，作用于 static 或 thread storage duration 的变量。它要求变量不能进行 dynamic initialization；但它不像 ~constexpr~ 那样自动使对象 const-qualified. ~constinit~ 变量若发生动态初始化则程序不良构， ~constinit~ 不能和 ~constexpr~ 一起使用；对象场景下 ~constexpr~ 会让对象 const, 而 ~constinit~ 不会。

#+begin_src cpp
  constexpr int square(int x) { return x * x; }

  constinit int global = square(10); // OK, 静态初始化
  global = 5; // OK, constinit 不等于 const
#+end_src
所以四者关系是:

#+begin_quote
const: 不能通过该对象修改；可能运行期初始化 \\
constexpr: 必须可常量求值；对象隐含 const \\
consteval: 函数必须编译期求值 \\
constinit: 静态/线程变量必须静态初始化；不代表不可修改
#+end_quote

** const 的设计哲学: 接口契约
C++ 的 ~const~ 很强，因为它深入类型系统:
#+begin_src cpp
  void print(const std::string &s);
#+end_src
这个函数的接口承诺是:
#+begin_quote
我不会修改传入的字符串
#+end_quote
调用者可以传入普通对象:
#+begin_src cpp
  std::string s = "hello";
  print(s);
#+end_src
也可以传入 const 对象:
#+begin_src cpp
  const std::string cs = "world";
  print(cs);
#+end_src
这就是 const-correctness 的价值：它扩大了函数可接受的参数范围，同时让编译器帮助检查 “不该改的东西是否改了” 。

但要注意， ~const~ 不是并发安全、不是深度不可变、也不是魔法防御。

例如类里可能有缓存:
#+begin_src cpp
  class Widget {
  public:
    int value() const {
      if (!cache_valid_) {
        cache_ = compute();
        cache_valid_ = true;
      }
      return cache_;
    }

  private:
    mutable int cache_ = 0;
    mutable bool cache_valid_ = false;
  };
#+end_src
这里， ~value~ 是 const member function, 但是它修改了 ~mutable~ 成员。这叫做 *logical constness(逻辑常量性)*: 从用户可观察语义看对象不变，但内部缓存可以变。 Effective Modern C++ 在这个方面提醒: 如果 const member function 可能被多个线程并发调用，就必须保证线程安全；一个变量可用 atomic, 多个变量作为整体更新时应该使用 mutex.

这说明 ~const~ 是接口语义的一部分，但不是完整的并发模型。

** 本节核心规则压缩
#+begin_src cpp
  const int x = 42;
#+end_src
~x~ 是 const object, 必须初始化，不能被赋值修改。
#+begin_src cpp
  const int &r = x;
#+end_src
~r~ 是 reference to const, 不是 “const reference” 。不能通过 ~r~ 修改对象。
#+begin_src cpp
  const int *p = &x;
#+end_src
~p~ 是 pointer to const. ~p~ 可以换指向，但不能通过 ~p~ 修改对象。
#+begin_src cpp
  int *const p = &x;
#+end_src
~p~ 是 const pointer. ~p~ 不能换指向，但可以通过 ~p~ 修改 ~i~ 。
#+begin_src cpp
  const int *const p = &x;
#+end_src
~p~ 是 const pointer to const. 指针本身和所指对象都不能通过这个表达式修改。
#+begin_src cpp
  constexpr int n = 42;
#+end_src
~n~ 是 compile-time constant expression, 可用于数组大小、模板实参等要求编译期求值的语境。
#+begin_src cpp
  constexpr int *p = nullptr;
#+end_src
~constexpr~ 修饰的是对象本身，所以 ~p~ 是 const pointer, 而不是 pointer to const.

** 一些例子
#+begin_src cpp
  int i = 0;
  const int ci = 42;

  int &ri = ci; // error, 不能用普通引用绑定到 const int
  const int &r2 = i; // OK, 只读视图
  const int &r3 = 42; // OK, 绑定临时对象并延长生命周期

  int *p1 = &ci; // error, 不能用 int* 指向 const int
  const int *p2 = &ci; // OK, 只读试图
  const int *p3 = &i; // OK, 通过 p3 不能修改 i

  int *const p4 = &i; // OK
  p4 = nullptr; // error, p4 是 const pointer, 不能修改指向
  ,*p4 = 10; // OK, p4 指向的是 nonconst int

  const int *const p5 = &ci; // OK
  p5 = &i; // error, p5 是 const pointer to const int, 不能修改指向
  ,*p5 = 10; // error

  const int n = get_size(); // 不是 constant expression, 除非 get_size() 可编译期求值且语义允许
  constexpr int m = 42; // 是 constant expression
#+end_src
下一节会进入 ~typedef~, ~using~, ~auto~, ~decltype~, 其中 ~auto~ 的推导规则直接依赖这一节的 top-level const / low-level const

* Dealing with Types

这一节表面上讲三个语法设施: *type alias (类型别名)* , ~auto~, ~decltype~ 。但是它真正处理的是 C++ 类型系统里的一个核心矛盾:
#+begin_quote
C++ 要求编译期知道每个名字的精确类型；但真实工程里的类型经常又长、又嵌套、又依赖上下文，甚至只有编译器才知道。
#+end_quote
C++ Primer 在 2.5 开头说得很准确：随着程序复杂化，类型也会复杂化；困难主要来自两个方面，一是类型难写，二是有时很难确定我们到底需要什么精确类型。于是本节给出三类工具：给复杂类型起名字、让编译器从初始化器推导类型、让编译器从表达式推导类型。

-----

** 主线: 类型表达能力与可读性的平衡

C++ 是 *static typed languaged (静态类型语言)* 。编译器必须在编译期知道每个表达式的类型，才能决定:
#+begin_src cpp
  i = i + j;
#+end_src
到底是整数加法、浮点加法、字符串拼接，还是某个类重载的 ~operator+~ 。 C++ Primer 在 Part I 开头也强调：C++ 中对象类型决定能执行什么操作，类型检查在编译期完成，因此编译器必须知道程序中每个名字的类型。

但是类型一旦进入真实工程，就会变得非常啰嗦:
#+begin_src cpp
  std::unordered_map<std::string, std::vector<std::unique_ptr<Node>>>::const_iterator
#+end_src
或者:
#+begin_src cpp
  typename std::iterator_traits<It>::value_type
#+end_src
或者 lambda 的闭包类型根本写不出来:
#+begin_src cpp
  auto pred = [](const auto &x) { return x.valid(); };
#+end_src
所以 2.5 不是偷懒语法，而是 C++ 现代化的入口： *你要学会什么时候显式写类型，什么时候抽象类型，什么时候让编译器推导类型* 。

这对应现代工具的取舍。 [[https:google.github.io/styleguide/cppguide.html][Google C++ Style Guide]] 的目标不是追求某种语法洁癖，而是管理 C++ 的复杂度，让代码在大规模代码库中可读、可维护；它明确强调“为读者优化，而不是为写作者优化”。 [[https:llvm.org/docs/CodingStandards.html][LLVM Coding Standards]] 也类似：大型代码库尤其需要统一风格，目标是是提高公共源码库的可读性和可维护性。

** Type Alias: 类型别名
类型别名不是新类型，而是已有类型的另一个名字。 *type alias* 是某个已有类型的同义名，它不创造新类型，不改变 ABI,不改变对象布局，不增加运行期开销。它只是让编译器在语义上把一个名字当作另一个类型来用。

C++ Primer 给出两种定义类型别名的方法。传统的 C/C++ 写法是 ~typedef~:
#+begin_src cpp
  typedef double wages; // wages 是 double 的同义名
  typedef wages base, *p; // base 是 double, p 是 double*
#+end_src
C++11 引入了 *alias declaration (别名声明)*:
#+begin_src cpp
  using SI = Sales_item; // SI 是 Sales_item 的同义名
#+end_src
书中明确说， ~using~ 左边的是别名名，右边是被命名的类型；类型别名可以出现在任何类型名可以出现的地方。也就是说:
#+begin_src cpp
  wages hourly, weekly;
  // 等价于
  double hourly, weekly;

  SI item;
  // 等价于
  Sales_item item;
#+end_src

*** 类型别名的真正用途: 表达意图
例如:
#+begin_src cpp
  using Price = double;
  using Quantity = std::size_t;
  using CustomerId = std::uint64_t;
#+end_src
这样能提高可读性:
#+begin_src cpp
  Price total_price(Quantity n);
#+end_src
更接近领域语言。

但是需要警惕， *type alias 不提供类型安全* 。比如:
#+begin_src cpp
  using UserId = int;
  using OrderId = int;

  void cancel_order(OrderId id);

  UserId u = 42;

  cancel_order(u); // 合法，因为 UserId 和 OrderId 本质上都是 int
#+end_src
如果希望真正区分 ~UserId~ 和 ~OrderId~ ，应该创建新类型:
#+begin_src cpp
  struct UserId {
    int value;
  };

  struct OrderId {
    int value;
  };

  void cancel_order(OrderId id);

  UserId u{42};
  // cancel_order(u); // error
#+end_src
这是C++设计里的一个关键分层： *alias* 是命名工具，不是抽象边界； *class/struct* 才能创造新类型。

** typedef 的语法陷阱: 它遵循声明符系统
C++ 的声明语法来自C. 它不是简单的 “左边类型，右边名字”，而是 *declarator* （声明符） 与 *base type* （基本类型部分）组合。
#+begin_src cpp
  typedef wages base, *p;
#+end_src
这里 ~wages~ 是基本类型， ~base~ 是一个声明符， ~*p~ 是另一个声明符。所以:
#+begin_src cpp
  base x; // double x;
  p ptr; // double *ptr;
#+end_src
这也是为什么 ~typedef~ 在复杂类型上难读:
#+begin_src cpp
  typedef void (*Handler)(int, const std::string&);
#+end_src
需要按照 C 声明语法读:
#+begin_quote
Handler 是一个指针，指向函数；该函数接受 ~int~ 和 ~const std::string&~ ，返回 ~void~ 。
#+end_quote
如果按照 ~using~ 写就会清晰很多:
#+begin_src cpp
  using Handler = void (*)(int, const std::string&);
#+end_src
就会更容易阅读:
#+begin_quote
Handler 是右边这个类型的别名。
#+end_quote
Effective Modern C++ 中也专门建议应优先使用 alias declaration, 而不是 ~typedef~ ，其中一个理由正是函数指针别名更容易读；更重要的理由是 alias declaration 可以写成 *alias template (别名模板)* ，而 ~typedef~ 不能。libc++ 的公开编码指南里也明确写道：优先使用 ~using~ alias 而不是 ~typedef~ ，因为 ~using~ 更易读且支持模板；历史代码里仍有 ~typedef~ 多半是历史原因。

** alias template
假设想给一个使用自定义分配器的 ~std::list~ 起别名。

如果使用 C++11 的 ~using~ 写法:
#+begin_src cpp
  template <typename T>
  using MyAllocList = std::list<T, MyAlloc<T>>;
  MyAllocList<Widget> widgets;
#+end_src
如果使用 C++98 的风格 ~typedef~ 的话，必须绕一层模板结构体:
#+begin_src cpp
  template <typename T>
  struct MyAllocList {
    typedef std::list<T, MyAlloc<T>> type;
  };

  MyAllocList<Widget> widgets;
#+end_src
它减少了模板元变成中的 “类型萃取样板代码”。现代标准库也大量使用这种模式:
#+begin_src cpp
  template <bool B, class T = void>
  using enable_if_t = typename enable_if<B, T>::type;

  template <class T>
  using remove_reference_t = typename remove_reference<T>::type;

  template <class T>
  using decay_t = typename decay<T>::type;
#+end_src

上面的意思是，早期的C++的类型计算经常产出一个 ~::type~ ，C++14之后大量提供 ~_t~ 后缀别名，把:
#+begin_src cpp
  typename std::remove_reference<T>::type
#+end_src
简化为:
#+begin_src cpp
  std::remove_reference_t<T>
#+end_src
libc++ 编码指南也进一步建议，在只有一个 alias 成员的类型萃取场景中，能用 alias template 的就优先用 alias template ，因为它比 class template 更轻量。不过它也提醒 alias template 会更早求值，在少数 SFINAE 场景可能更受影响。

*** 插叙: 关于 template 以及 typename 的大致介绍
以下面这段为例:
#+begin_src cpp
  template <class T>
  using remove_reference_t = typename remove_reference<T>::type;
#+end_src
可以粗略理解为:
#+begin_quote
输入一个类型 ~T~ ，输出另一个类型。
#+end_quote
这是 C++ type traits 的常见形式。C++14 的 ~_t~ 别名模板就是为了避免反复写 ~typename ...::type~ ，让类型转换更简洁。

**** ~template~ 是什么
~template~ 的意思是：接下来我要定义一个 *模板(template)* ，它不是一个具体东西，而是一族东西的生成规则。

比如普通函数：
#+begin_src cpp
  int add(int a, int b) {
    return a + b;
  }
#+end_src
它只能处理 ~int~ 。但是如果写成函数模板:
#+begin_src cpp
  template <class T>
  T add(T a, T b) {
    return a + b;
  }
#+end_src
它就表示一族函数:
#+begin_src cpp
  add<int>
  add<double>
  add<std::string>
  ...
#+end_src
当调用 ~add(1, 2)~ 时，编译器会推导出 ~T = int~ ，于是生成类似:
#+begin_src cpp
  int add(int a, int b);
#+end_src
当调用 ~add(1.4, 2.6)~ 时，编译器会推导出 ~T = double~ ，于是生成类似:
#+begin_src cpp
  double add(double a, double b)
#+end_src
所以 ~template~ 的核心作用就是:
#+begin_quote
把 “具体类型” 变成参数，让编译器根据类型生成代码。
#+end_quote

**** ~template <class T>~ 里的 ~class T~
这里的 ~class~ 不表示 “必须传一个 class 类型”，它的意思是：
#+begin_quote
T 是一个类型参数。
#+end_quote
所以下面两者基本等价:
#+begin_src cpp
  template <class T>

  template <typename T>
#+end_src
比如:
#+begin_src cpp
  template <class T>
  struct Box {
    T value;
  };
#+end_src
可以这样用:
#+begin_src cpp
  Box<int> b1;
  Box<double> b2;
  Box<std::string> b3;
#+end_src
此时， ~Box<int>~ 是一个具体类型。 ~Box<double>~ 是另一个具体类型。而 ~Box<T>~ 本身是模板，不是一个完整类型。只有当提供模板实参之后，比如 ~Box<int>~ 它才能成为具体类型。

**** ~template <bool B, class T = void>~
来看这一句:
#+begin_src cpp
  template <bool B, class T = void>
  using enable_if_t = typename enable_if<B, T>::type;
#+end_src
模板参数有两个:
#+begin_src cpp
  bool B
#+end_src
这是一个 *非类型模板参数 (non-type template parameter)* 。它不是类型，而是编译期布尔值。

例如:
#+begin_src cpp
  enable_if_t<true, int>
  enable_if_t<false, int>
#+end_src
第二个:
#+begin_src cpp
  class T = void
#+end_src
这是一个类型参数，并且默认值是 ~void~ .
所以， ~enable_if_t<true>~ 等价于 ~enable_if_t<true, void>~ ，也就是说哦，如果不提供第二个模板参数，默认使用 ~void~ .

**** ~using xxx = ...~
普通类型别名是这样:
#+begin_src cpp
  using Int = int;
#+end_src
而模板类型别名是这样的:
#+begin_src cpp
  template <class T>
  using Ptr = T*;
#+end_src
于是， ~Ptr<int>~ 等价于 ~int*~ . ~Ptr<std::string>~ 等价于 ~std::string*~ 。所以:
#+begin_src cpp
  template <class T>
  using remove_reference_t = typename remove_reference<T>::type;
#+end_src
意思是定义一个别名模板 ~remove_reference_t<T>~ ，它等价于 ~typename remove_reference<T>::type~ 。


**** ~::type~
~::~ 是作用域解析运算符 (scope resolution operator) 。例如:
#+begin_src cpp
  struct x {
    using type = int;
  };
#+end_src
那么 ~x::type~ 就是 ~int~ 。这里的 ~type~ 没有魔法，就是一个嵌套在 ~x~ 里的类型别名。

再看一个例子:
#+begin_src cpp
  template <class T>
  struct Identity {
    using type = T;
  };
#+end_src
那么 ~Identity<int>::type~ 就是 ~int~ , ~Identity<double>::type~ 就是 ~double~ 。

所以， ~remove_reference<T>::type~ 的意思是：
#+begin_quote
先用 ~T~ 实例化 ~remove_reference<T>~ 这个模板，然后取出它内部名叫 ~type~ 的类型。
#+end_quote

**** ~remove_reference<T>::type~ 的大致结构
标准库里的实现会更复杂，但核心思想类似这样:
#+begin_src cpp
  template <class T>
  struct remove_reference {
    using type = T;
  };

  template <class T>
  struct remove_reference<T&> {
    using type = T;
  }

  template <class T>
  struct remove_reference<T&&> {
    using type = T;
  }
#+end_src
所以，
#+begin_src cpp
  template <class T>
  using remove_reference_t = typename remove_reference<T>::type;
#+end_src
只是把后面那一串从作用域中提取 ~type~ 类型的代码，包装成更短的 ~remove_reference_t<T>~ 。比如说， ~remove_reference_t<int&>~ 等价于 ~typename remove_reference<int&>~ ，其结果是 ~int~ 。

**** 为什么前面要写 ~typename~
后半部分的 ~typename remove_reference_t<T>::type~ 可能会让人感到困惑，这里的 ~typename~ 的意思是，告诉编译器:
#+begin_quote
将 ~remove_reference<T>::type~ 视为一个类型。
#+end_quote
做这个提醒，是因为 ~remove_reference<T>::type~ 依赖于模板类型 ~T~ 。在模板定义阶段，编译器还不知道 ~T~ 未来会是什么，也就不能确定 ~remove_reference<T>::type~ 到底是一个类型，还是一个静态类型成员，或是别的名字。比如:

#+begin_src cpp
  template <class T>
  struct Weird {
    static int type;
  };
#+end_src
这里，如果我们取 ~Weird<T>::type~ 的话，就不是一个类型，而是一个变量。

所以C++要求：凡是这种依赖于模板参数的嵌套类型名，通常必须写 ~typename~ . 也就是:
#+begin_src cpp
  typename Trait<T>::type
#+end_src
而不是:
#+begin_src cpp
  Trait<T>::type
#+end_src

**** ~enable_if_t~ 如何理解
我们先看它依赖的 ~enbable_if~ 大概怎么实现:
#+begin_src cpp
  template <bool B, class T = void>
  struct enable_if {
    // B 为 false 时，没有 type
  }

  template <class T>
  struct enable_if<true, T> {
    using type = T;
  }
#+end_src
然后:
#+begin_src cpp
  template <bool B, class T = void>
  using enable_if_t = typename enable_if<B, T>::type
#+end_src
因为 ~B = true~ ，所以 ~enable_if<true, int>~ 里面有:
#+begin_src cpp
  using type = int;
#+end_src
所以结果是 ~int~ 。

但是如果 ~enable_if_t<false, int>~ 展开成: ~typename enable_if<false, int>::type~ ，而这里面没有 ~type~ 。所以这个类型不存在。

这就是 ~enable_if~ 的核心: *条件为真时产生一个类型，条件为假时不产生类型* 。

常用于让某个模板函数 “只在某些条件下存在”。

例如:
#+begin_src cpp
  #include <typ_traits>
  #include <iostream>

  template <class T>
  std::enable_if_t<std::is_integral_v<T>, void> print(T x) {
    std::cout << "integer: " << x << std::endl;
  }
#+end_src
当 ~T = int~ 时， ~std::is_integral_v<int>~ 的结果为 ~true~ ，所以 ~std::enable_if_t<true, void>~ 的结果为 ~void~ ，函数有效。当 ~T = double~ 时， ~std::is_integral_v<double>~ 结果为 ~false~ ，于是 ~std::enable_if_t<false, void>~ 没有类型，模板函数替换失败。

这背后就是之后会遇到的 SFINAE: *Substitution Failure Is Not An Error* 。模板替换失败不一定立刻报错，而是把这个候选模板从重载集合中移除。

** 类型别名与 ~const: pstring~
#+begin_src cpp
  typedef char *pstring;

  const pstring cstr = 0;
  const pstring *ps; 
#+end_src
这里的 ~const pstring cstr~ 并不是 ~const char *cstr~ 。 ~pstring~ 本身就是 pointer to char, 所以 ~const pstring~ 的意思是 “const pointer to char”，也即是:
#+begin_src cpp
  char *const cstr = 0;
#+end_src
这才是正确的理解。 ~const~ 修饰的是整个别名代表的类型，而不是把 ~char*~ 文本展开后再肉眼进行解析。 ~pstring~ 的类型是 pointer to char, 那么显然 ~const pstring~ 的类型就是 const pointer to char, 也就是 ~char *const~ ，而不是 pointer to const char (~const char*~) .

而对于 ~const pstring *ps~ ，我们可以翻译成 ps 是一个指针，指向的是 const pointer to char .也即是说可以写成:
#+begin_src cpp
  char *const *ps;
#+end_src
这里， ~ps~ 的指向可以改变，因为它是普通的 pointer, ~*ps~ 的指向不能改变，因为它是 ps 指向的 const pointer, ~**ps~ 的值可以改变, 因为 ~*ps~ 是 const pointer, 而不是 const pointer to const. 

如果使用 ~using~:
#+begin_src cpp
  using pstring = char*;
  const pstring cstr = nullptr; // 仍然是 char *const
#+end_src
~using~ 的可读性更好一些，但是语义完全一样。

这个例子背后是 C++ 声明系统里的根规则:
#+begin_src cpp
  const T x;
#+end_src
其中 ~const~ 修饰的是 ~T~ 这个整体类型。如果 ~T~ 是 ~int~, 那么就是 ~const int~ ，如果 ~T~ 是 ~char*~ ，那么就是 ~char *const~.

为了避免理解误差，最好不要使用 ~using pstring = char*~ 这种带有指针的别名。更好的做法是在使用时才声明指向关系，或者直接使用高级抽象:
#+begin_src cpp
  char *p;
  const char *cp;

  std::string s;
  std::string_view sv;
#+end_src

#+begin_quote
别名适合表达稳定的概念类型，不适合隐藏裸指针的可见性。
#+end_quote

** ~auto~: 编译期类型推导，不是动态类型

auto type specifier (auto 类型说明符) 告诉编译器: 变量类型从初始化器中推导。

~auto~ 不像 ~double~ 那样命名一个具体类型，而是让编译器从 Initializer 推导类型；因此使用 ~auto~ 声明变量必须有初始化器。

注意， ~auto~ 不是 Python 的动态类型。它只是让编译器在编译期替你写类型:
#+begin_src cpp
  auto x = 42; // 编译后 x 的类型固定为 int
  x = 3.14; // 合法，但是 3.14 转成 int,  x 变成 3
#+end_src
它更接近 “编译期局部类型推导”。


** ~auto~ 必须初始化 
#+begin_src cpp
  auto x = 0; // OK
  auto y; // error
#+end_src
这可以避免一类未初始化局部变量问题:
#+begin_src cpp
  int x1; // 可能未初始化
  auto x2; // error
  auto x3 = 0; // OK
#+end_src

** 一个声明中的多个 ~auto~: 必须推导出同一个基础类型
比如:
#+begin_src cpp
  auto i = 0, *pi = &i; // OK
  auto sz = 0, pi = 3.14; // error
#+end_src
原因是同一个声明只有一个 base type. 第一个声明里 ~auto~ 推导为 ~int~:
#+begin_src cpp
  int i = 0, *p = &i;
#+end_src
第二个声明里， ~sz~ 想让 ~auto~ 是 ~int~ ， ~pi~ 想让 ~auto~ 是 ~double~ ，冲突，所以非法。

现在 C++ Core Guideliness 有一条很实用的建议， *一个声明只声明一个名字，用auto避免重复冗长类型名* 。所以项目中更推荐:
#+begin_src cpp
  auto i = 0;
  auto *p = &i;

  auto sz = 0;
  auto pi = 3.14;
#+end_src
不要把多个 ~auto~ 声明放在一起，它节省不了多少行，却会显著增加理解成本。

** auto 与 reference: 初始化器是引用时，推导的是被引用对象类型

对于下面的类型:
#+begin_src cpp
  int i = 0;
  int &r = i;

  auto a = r;
#+end_src
这里 ~a~ 的类型就是 ~int~, 而不是 ~int&~ 。因为在表达式中使用引用，通常就是使用它所绑定的对象。 C++ Primer 明确说，当引用作为初始化器时，初始化器其实是对应对象，编译器用该对象的类型进行 ~auto~ 推导。

所以:
#+begin_src cpp
  a = 42;
#+end_src
只会修改 ~a~ ，不会修改到 ~i~ 。也就是说， ~auto a = r~ 本质上是给 ~a~ 的类型推导为 ~int~, 并将 ~r~ 的值复制给它。

如果想让 ~a~ 成为引用，必须显式写:
#+begin_src cpp
  auto &a = r; // int&
  a = 42; // 修改 i
#+end_src
这条规则非常重要： *auto 默认按值推导；引用性默认丢失，除非显式写 ~auto&~ 或 ~auto&&~* 。

** auto 与 const: 丢弃top-level const, 保留 low-level const

比如:
#+begin_src cpp
  int i = 0;
  const int ci = i;
  const int &cr = ci;

  auto b = ci; // int
  auto c = cr; // int
  auto d = &i; // int*
  auto e = &cr; // const int*
#+end_src
~auto~ 通常忽略 *top-level const*, 但保留 *low-level const* 。例如 pointer to const 中的 const 会被保留。

逐个解释:
#+begin_src cpp
  auto b = ci;
#+end_src
这里 ~ci~ 是 ~const int~, 但这里是按值复制。复制出来的新对象 ~b~ 没有必要继承 ~ci~ 的不可修改性，所以 ~b~ 是 ~int~ 。
#+begin_src cpp
  auto c = cr;
#+end_src
~cr~ 是 ~const int&~ ，但使用引用时视为使用其绑定对象；而绑定对象的 const 在按值复制时是顶层 const, 所以被丢弃。 ~c~ 也是 ~int~ 。
#+begin_src cpp
  auto d = &i;
#+end_src
~&i~ 的类型是 ~int*~ ，所以 ~d~ 是 ~int*~ 。
#+begin_src cpp
  auto e = &ci;
#+end_src
~&ci~ 的类型是 ~const int*~, 这里的 const 是底层const，表示指向 const int. 不能丢。否则就会允许通过 ~int*~ 修改 ~ci~ ，所以 ~e~ 是 ~const int*~ 。

如果要保留顶层 const, 必须写出来:
#+begin_src cpp
  auto &g = ci; // const int&
  auto &h = 42; // error
  const auto &h = 42; // const int&
#+end_src
书中明确说，当我们要求 ~auto~ 推导出引用时，初始化器中的顶层 const 不会被忽略；因为绑定引用时， const 不再是 “复制源对象的顶层 const”，而是引用所绑定对象类型的一部分。


** ~auto*~, ~auto&~, ~const auto&~ 的选择

*** 本地复制: ~auto~
#+begin_src cpp
  auto value = compute();
#+end_src
表示你要一个新对象。它可能发生拷贝，也可能发生移动，也可能被优化掉。语义上它拥有自己的值。

*** 只读引用: ~const auto&~
#+begin_src cpp
  const auto& item = container.front();
#+end_src
表示不复制、且不修改。遍历容器时非常常见:
#+begin_src cpp
  for (const auto &x : xs) {
    use(x);
  }
#+end_src

*** 可修改引用: ~auto&~
#+begin_src cpp
  for (auto &x : xs) {
    normalize(x);
  }
#+end_src

*** 指针: ~auto*~
#+begin_src cpp
  auto *p = get_ptr();
#+end_src
~auto*~ 的优势是把“这是指针”明确留在使用点。这比 ~auto p = get_ptr()~ 更清楚，因为后者可能让读者一眼看不出 ~p~ 是指针。

** auto 取舍: 不是越多越现代
Effective Modern C++ 主张: Prefer auto to explicit type declarations. 因为 ~auto~ 能避免未初始化变量、冗长类型、闭包类型无法书写、以及错误类型捷径。比如：
#+begin_src cpp
  std::vector<int> v;
  unsigned sz = v.size(); // 可能出现错误
#+end_src
~v.size()~ 的真实类型是 ~std::vector<int>::size_type~, 不一定等于 ~unsigned~. 32 位和 64 位平台上这种“看起来差不多”的类型可能导致移植问题，用 ~auto~ 可以让 ~sz~ 精确成为 ~v.size()~ 的返回类型。

但 Google/Abseil 的实践更加克制。Abseil 引用 Google Style Guide: 只有当类型推导当代码对不熟悉项目的读者更清楚，或者让代码更安全时，才使用类型推导；不要仅仅因为不想写显示类型就是用 ~auto~.

这两个观点并不矛盾。可以这样折中:
#+begin_src cpp
  auto it = v.begin(); // 好，迭代器类型冗长且上下文明显
  auto size = v.size(); // 好，避免手写错误 size_type
  const auto &[key, value] = *it; // 好，结构绑定表达局部结构
  auto ptr = std::make_unique<Node>(); // 好，右侧已写 Node
#+end_src
但下面就可能不清楚:
#+begin_src cpp
  auto result = service.query(request);
#+end_src
读者不知道 ~result~ 是状态码、对象、指针、optional、expected，还是某个异步句柄。此时用显式类型可能更好:
#+begin_src cpp
  QueryResult result = service.query(request);
#+end_src
或者改函数名/接口设计，让返回类型更清楚。

** map 遍历中的 auto
有一个比较常见的问题。关联容器的元素并不是:
#+begin_src cpp
  std::pair<Key, Value>
#+end_src
而是:
#+begin_src cpp
  std::pair<const Key, Value>
#+end_src
因为 Key 不能被修改。

错误写法:
#+begin_src cpp
  std::unordered_map<std::string, int> m;

  for (const std::pair<std::string, int> &p : m) {
    // ...
  }
#+end_src
这里，我们会以为 ~p~ 引用的是内部元素，但其实没有。因为 map 的内部元素是:
#+begin_src cpp
  std::pair<const std::string, int>
#+end_src
键是 const 的。和我们写的类型不同。编译器会构造一个临时的 ~std::pair<std::string, int>~ ，再让 ~const&~ 绑定到临时对象。每轮循环都可能发生不必要拷贝。因此建议使用 ~const auto&~ 或结构化绑定来避免错误类型。正确写法应该是:
#+begin_src cpp
  for (const auto &p : m) {
    // p 的真实类型是 const std::pair<const std::string, int>&
  }
#+end_src
C++17 后更好:
#+begin_src cpp
  for (const auto &[key, value] : m) {
    // key: const std::string&
    // value: const int& 或按 const pair 引用推得的元素访问
  }
#+end_src
这就是 ~auto~ 的工程价值：能够避免“我以为我写对了类型，其实写错了”的问题。


** auto 与 ~{}~ 初始化
在 C++11/14 中:
#+begin_src cpp
  auto x1 = 27; // int
  auto x2(27); // int
  auto x3 = {27}; // std::initializer_list<int>
  auto x4{27}; // C++14/17 中也是 std::initializer_list<int>
#+end_src
~auto~ 遇到花括号初始化时有特殊规则，可能推导成 ~std::initializer_list~ ，这是经典问题。 cppreference 也说明， brace-enclosed-initializer 本身没有类型，因此模板类型推导不能直接从 ~{1, 2, 3}~ 推导 ~T~, 但 ~auto~ 有特殊例外，在 copy-list-initialization 中会被推导为 ~std::initializer_list~ 。

C++17 修改了 ~auto x{27}~ 的规则，现在:
#+begin_src cpp
  auto x1 = {27}; // std::initializer_list<int>
  auto x2{27}; // int, C++17 起
  auto x3{1, 2}; // error, 初始化列表不能多个元素推导一个auto
#+end_src
建议上很简单:
#+begin_src cpp
  auto x = 27; // 普通标量
  auto xs = {1, 2, 3}; // 明确想要 initializer_list 时才这样写
#+end_src
不要为了统一花括号而强行写 ~auto x{27}~, 它会造成跨版本认知负担。类型推导应该提升清晰性或安全性，而不是机械追求统一或少写。

** decltype: 从表达式获得类型，但不求值
:PROPERTIES:
:CUSTOM_ID: 1a07c3d9-cebe-427a-8b1b-27490f1b7827
:END:
*decltype type specifier (decltype 类型是说明符)* 用来从一个表达式获得类型。

有时我们想让编译器从某个表达式推导变量类型，但不想用这个表达式初始化变量，于是引入 ~decltype~ ；编译器分析表达式以确定类型，但不计算表达式。

比如:
#+begin_src cpp
  decltype(f()) sum = x;
#+end_src
这里 ~f()~ 不会被调用。编译器只会问:
#+begin_quote
如果调用 ~f()~ ，返回类型是什么？
#+end_quote
然后把 ~sum~ 声明成那个类型。

比如:
#+begin_src cpp
  int f();

  decltype(f()) x = 0; // int x = 0;
#+end_src
再如:
#+begin_src cpp
  std::vector<int> v;

  decltype(v.size()) n = 0;
  // n 的类型是 std::vector<int>::size_type
#+end_src
这里不需要真的调用 ~v.size()~ 来初始化 ~n~ ，只需要借用它的返回类型。

** decltype 与 auto 的核心区别
~auto~ 看初始化规则，通常会调整类型:
#+begin_src cpp
  const int ci = 0;
  const int &cr = ci;

  auto a = ci; // int
  auto b = cr; // int
#+end_src
~decltype~ 更像“问这个名字或表达式的精确类型是什么”，因此:
#+begin_src cpp
  decltype(ci) x = 0; // const int
  decltype(cr) y = x; // const int&
#+end_src
~decltype~ 处理 top-level 和 reference 的方式与 ~auto~ 不同；当作用于变量时， *它返回该变量的类型，包括顶层引用 const 和引用* 。

所以从语义方面我们可以这样理解:
#+begin_src cpp
  const int ci = 42;
  const int &cr = ci;

  auto a = cr; // int
  decltype(cr) b = ci; // const int&
#+end_src
这里 ~auto~ 问的是:
#+begin_quote
用 ~cr~ 初始化一个新对象，应该是什么类型
#+end_quote
而 ~decltype(cr)~ 问的很简单:
#+begin_quote
~cr~ 这个名字被声明成了什么类型
#+end_quote
这两个问题不是同一层面的。

** decltype 的现代完整规则
如果 ~decltype~ 作用于变量名，返回变量声明类型；如果作用于更一般表达式，可能得到引用类型。现代 C++ 可以更精确地说:
#+begin_src cpp
  decltype(e)
#+end_src
有两大规则:

第一，如果 ~e~ 是未加括号的 id-expression 或成员访问表达式， ~decltype(e)~ 得到该实体的声明类型。
#+begin_src cpp
  int i = 0;
  const int ci = 0;
  int &r = i;

  decltype(i) a = 0; // int
  decltype(ci) b = 0; // const int
  decltype(r) c = i; // int&
#+end_src
第二，如果 ~e~ 是其他表达式，结果取决于 *value catagory(值类型)* :
- 若 ~e~ 是 lvalue, ~decltype(e)~ 是 ~T&~
- 若 ~e~ 是 xvalue, ~decltype(e)~ 是 ~T&&~
- 若 ~e~ 是 pvalue, ~decltype(e)~ 是 ~T~


现在只需要先掌握 lvalue 版本，因为我们还没正式展开右值引用:
#+begin_src cpp
  int i = 42;
  int *p = &i;

  decltype(i) a; // int
  decltype((i)) b; // int&, error: 引用必须初始化
  decltype(*p) c; // int&, error: 引用必须初始化
#+end_src
这里，为什么 ~decltype(*p)~ 是 ~int&~ 。因为 ~*p~ 表达式表示被指向的对象，它可以出现在赋值左边:
#+begin_src cpp
  *p = 10;
#+end_src
所以 ~*p~ 是 lval expression. 对于 lvalue expression, ~decltype~ 给出 ~T&~ 。解引用得到的是指针所指的对象，并且可以给该对象赋值，因此 ~decltype(*p)~ 是 ~int&~ ，不是 ~int~ 。

** ~decltype((i))~ 的语义
这是最经典的问题:
#+begin_src cpp
  int i = 0;

  decltype(i) a; // int
  decltype((i)) b; // int&, error
#+end_src
因为 ~i~ 是一个未加括号的变量，套用第一条规则。但 ~(i)~ 不再是 “未加括号的 id-expression”，而是一个普通表达式。变量表达式是 lvalue，所以:
#+begin_src cpp
  decltype((i)) // int&
#+end_src
~decltype((variable))~ 永远都是引用类型，而 ~decltype(variable)~ 只有当 variable 本身被声明为引用时才是引用。 Effective Modern C++ 也强调，这个差异可能在 C++14 的 ~decltype(auto)~ 的返回类型推导中可能导致严重的问题。

例如:
#+begin_src cpp
  decltype(auto) f1() {
    int x = 0;
    return x; // decltype(x) 是 int, 所以返回 int
  }

  decltype(auto) f2() {
    int x = 0;
    return (x); // decltype((x)) 是 int&, 所以返回局部变量引用， UB
  }
#+end_src
~f2~ 返回的是局部变量引用，函数返回后 ~x~ 已经销毁，后续使用是 ~undefinend behavior (未定义行为)~ 。这就是为什么 ~decltype(auto)~ 很强，但不能随便使用。

** ~decltype~ 的典型用途
典型用途是表达“与某个表达式同类型”。

基础阶段最常见用途:
#+begin_src cpp
  decltype(v.size()) index = 0;
#+end_src
比写:
#+begin_src cpp
  std::vector<int>::size_type index = 0;
#+end_src
更短，但同时更依赖上下文。

另一个典型用途是泛型代码中的返回类型:
#+begin_src cpp
  template <typename Container, typename Index>
  auto access(Container &c, Index i) -> decltype(c[i]) {
    return c[i];
  }
#+end_src
这里，为什么不直接用:
#+begin_src cpp
  auto acces(Container &c, Index i) { ... }
#+end_src
的形式呢？因为 C++14 之后函数返回类型可以用 ~auto~ 推导，但普通 ~auto~ 推导会像类型模板一样丢掉引用性。 Effective Modern C++ 的例子说明，如果 ~c[i]~ 返回 ~T&~ ，普通 ~auto~ 返回类型可能被推导为 ~T~ ，导致不能返回可赋值引用；这是需要 ~decltype(auto)~ 或 ~trailing return.

但同时，我们之前强调过，下面的写法比较危险:
#+begin_src cpp
  decltype(auto) access(Container &c, Index i) { ... }
#+end_src
这虽然会保留 ~c[i]~ 的真实返回类型，如果是引用就返回引用，如果是值就返回类型；但是它对表达式形式非常敏感，所以不要当成普通 ~auto~ 的高级替代品。它适合写泛型库、转发函数、适配器；普通业务代码里用得越少越好。

** 源码视角：为什么标准库到处都是类型别民
一个简化版的源码式结构大概是:
#+begin_src cpp
  template <class T, class Allocator = std::allocator<T>>
  class vector {
  public:
    using value_type = T;
    using allocator_type =  Allocator;
    using size_type = std::size_type;
    using difference_type = std::ptrdiff_t;

    using reference = value_type&;
    using const_reference = const value_type&;

    using pointer = typename std::allocator_traits<Allocator>::pointer;
    using const_pointer = typename std::allocator_traits<Allocator>::const_pointer;

    using iterator = /* implementation-defined */;
    using const_iterator = /* implementation-defined */;
  };
#+end_src
这些别名的意义是为了给泛型代码一个统一接口:
#+begin_src cpp
  templat <typename Container>
  void print_size(const Container &c) {
    typename Container::size_type n = c.size();
  }
#+end_src
或者 C++11后，
#+begin_src cpp
  templat <typename Container>
  void print_size(const Container &c) {
    auto n = c.size();
  }
#+end_src
这也是C++ “库优先” 设计哲学的重要部分：语言不需要内建所有高级类型，只需要提供模板、别名、迭代器、运算符重载、 RAII 等机制，标准库和用户库就能构造出接近内建类型体验的抽象。 LLVM 编码标准也体现了类似的思路：优先使用标准库设施或 LLVM support libraries, 而不是重复构造数据结构；在 LLVM 中， ~DenseMap~, ~SmallVector~ 等支持库类型提供了与标准库相似的接口，但针对编译器场景做了性能取舍。


** ~decltype~ 与 ~auto~ 的对照总结
看这一组:
#+begin_src cpp
  int i = 0;
  const int ci = 42;
  const int &cr = ci;
  int *p = &i;

  auto a = ci; // int
  decltype(ci) b = 0; // const int
#+end_src
- ~auto~: 创建一个新对象，从 ~ci~ 拷贝值。顶层 const 丢掉
- ~decltype(ci)~: 获取 ~ci~ 这个名字的声明类型。保留 const


#+begin_src cpp
  auto c = cr; // int
  decltype(cr) d = 0; // const int&
#+end_src
- ~auto~: 引用退化为被引用对象，再按值复制
- ~decltype(cr)~: ~cr~ 被声明为 ~const int&~, 所以就是 ~const int&~


#+begin_src cpp
  auto e = *p; // int
  decltype(*p) f = i; // int&
#+end_src
- ~auto~: 用 ~*p~ 初始化新对象，复制一个 int
- ~decltype(*p)~: ~*p~ 是 lvalue expression, 所以得到 ~int&~


#+begin_src cpp
  decltype(i) g; // int
  decltype((i)) h = i; // int&
#+end_src
~i~ 是未加括号变量名，得到声明类型； ~(i)~ 是 lvalue expression ，得到引用。

** 本节的取舍

*** 优先用 ~using~, 少用 ~typedef~
新代码中:
#+begin_src cpp
  using Callback = void (*)(int);
#+end_src
模板别名必须用 ~using~:
#+begin_src cpp
  template <typename T>
  using Vec = std::vector<T>;
#+end_src

*** 不要用 alias 假装创建强类型
比如:
#+begin_src cpp
  using Meter = double;
  using Second = double;

  Meter m = 10;
  Second s = m; // 合法
#+end_src
这里语义上 ~Second~ 和 ~Meter~ 应该是两个完全不同的类型，但是从语法上却可以赋值。需要类型安全时，使用 ~struct~ 包装。

*** 局部变量可适度使用 ~auto~
适合:
#+begin_src cpp
  auto it = container.begin();
  auto ptr = std::make_unique<Node>();
  auto n = v.size();

  for (const auto &x : xs) {}
  for (auto &[k, v] : map) {}
#+end_src
谨慎:
#+begin_src cpp
  auto result = run();
  auto data = client.fetch();
  auto status = parse(x);
#+end_src
因为读者可能不知道返回类型。 ~auto~ 应该让代码更加清晰或者更加安全，而不是为了避免书写显式类型。

*** ~decltype~ 多用于泛型库和类型适配
普通业务代码里:
#+begin_src cpp
  decltype(expr) x = ...;
#+end_src
出现频率不会太高。它更适合:
#+begin_src cpp
  decltype(container.size()) n = 0;
#+end_src
或者:
#+begin_src cpp
  template <typename F, typename Arg>
  using result_t = decltype(std::declval<F>()(std::declval<Arg>()));
#+end_src
这类类型计算场景。

*** ~decltype(auto)~ 要慎用
它适合完美保留返回表达式类型:
#+begin_src cpp
  template <typename Container>
  decltype(auto) front(Container &c) {
    return c.front();
  }
#+end_src
但是下面这种非常危险:
#+begin_src cpp
  decltype(auto) f() {
    int x = 0;
    return (x); // int&, 悬垂引用
  }
#+end_src

** 本节压缩
#+begin_src cpp
  using T = ...
#+end_src
给类型起别名，但是不创建新类型。
#+begin_src cpp
  typedef ...
#+end_src
旧式类型别名。语法受C声明符影响；新代码优先使用 ~using~ .
#+begin_src cpp
  auto x = expr;
#+end_src
从初始化器推导变量类型，默认按值，引用性与顶层 const 通常丢失，底层 const 保留。
#+begin_src cpp
  auto &x = expr;
#+end_src
显式要求引用；这是 const 规则按照引用绑定处理。
#+begin_src cpp
  const auto &x = expr;
#+end_src
只读引用。尤其适合遍历和避免拷贝。
#+begin_src cpp
  decltype(name)
#+end_src
若 ~name~ 是未加括号的名字，得到声名类型。
#+begin_src cpp
  decltype(expr)
#+end_src
若是一般表达式，则根据值类别推导； lvalue 得到 ~T&~ 。
#+begin_src cpp
  decltype((x))
#+end_src
几乎总是引用，因为 ~(x)~ 是 lvalue expression 。
* Define Out Own Data Structures
** 2.6 的位置: 从“使用类型”到“定义类型”
*data structure* 不只是“几个字段放在一起”，而是“相关数据元素的组合，以及使用这些数据的策略”。书中使用 ~Sales_item~ 作为对照: ~Sales_item~ 不仅保存 ISBN、销量、收入，还提供 ~isbn()~, ~>>~, ~<<~, ~+~, ~+=~ 等操作；而本节的 ~Sales_data~ 只保存数据，不提供操作。所以使用者必须自己写读入、输出、合并逻辑。

这体现了C++核心设计目标: *用户自定义类型应该尽量像内置类型一样自然可用* 。标准草案也直接说: ~class~ 是一种类型； ~class-key~ 可以是 ~class~, ~struct~, ~union~ 。也就是说，在 C++ 里， ~struct~ 并不是“低级的C风格结构体”，而是定义 class type 的一种语法形式。

本节先使用 ~struct~, 因为它适合表达一种“透明的数据聚合体”：数据公开，使用者可以直接访问。等学到第七章，我们将会学到成员函数、构造函数、访问控制、封装；到第十四章再学习运算符重载，才能写出真正接近 ~Sales_item~ 那样的类型。
** 定义 ~Sales_data~: 最小的用户自定义类型
我们这样定义：
#+begin_src cpp
  #include <string>
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };
#+end_src
这段代码定义了一个新的类型，名字叫 ~Sales_data~ 。它的三个 data members 分别是:
#+begin_src cpp
  std::string bookNo; // ISBN
  unsigned units_sold = 0; // 销量
  double revenue = 0.0; // 总收入
#+end_src
C++ 标准说，一个 class definition 会引入一个新类型；例如 ~struct X { int a; };~ 和 ~struct Y { int a; }~ 即便成员完全一样， ~X~ 和 ~Y~ 也是两个不同类型，不能互相赋值。这非常关键: C++ 的类型不是“形状兼容即可”，而是 *名义类型系统* 倾向更强。 ~Sales_data~ 不是“三元组”，也不是“随便三个字段”，而是一个具有独立语义的类型。
** class body 后面必须有分号
这里，是因为 C++ 的声明系统允许你在定义类型的同时定义对象:
#+begin_src cpp
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  } accum, trans, *salesptr;
#+end_src
它等价于更清晰的写法:
#+begin_src cpp
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  } accum, trans, *salesptr;

  Sales_data accum, trans, *salesptr;
#+end_src
所以 ~}~ 后面的分号是在结束整个 declaration. C++ Primer 也强调，虽然可以把类型定义和对象定义写在一起，但这会把 “定义类型” 和 “定义变量” 混在一个语句中，通常不推荐。

如果漏掉这个分号，编译器会继续试图把后面的内容也当作这个声明的一部分来解析，错误信息可能看起来很绕。
** 数据成员的对象模型: 每个对象都有自己的成员副本
定义:
#+begin_src cpp
  Sales_data a;
  Sales_data b;
#+end_src
不是创建了一个共享的 ~bookNo~, 一个共享的 ~units_sold~, 一个共享的 ~revenue~ ，而是每个 class type 对象都有一个对应于每个 direct non-static data member 的唯一 member subobject. 换句话说， ~a.units_sold~ 和 ~b.units_sold~ 对应的是两个不同的子对象。

这和前面学过的“对象是具有类型的一块内存区域”是连在一起的。 ~Sales_data~ 对象是一块复合内容，其中嵌入了多个 member subobject.

但不要把它想象成简单的C二进制布局。因为 ~std::string~ 是一个类对象，它内部可能含有指针、长度、容量、小字符串优化等实现细节。这个对象的 ~sizeof(Sales_data)~ 不一定等于 ~sizeof(std::string) + sizeof(unsigned) + sizeof(double)~ , 中间可能还有 padding (填充) 以满足 alignment(对齐)。因此不要对这种类型做原始二进制读写:
#+begin_src cpp
  // 不推荐: Sales_data 含有 std::string, 不是适合裸二进制持久化的类型
  std::ofstream out("data.bin", std::ios::binary);
  out.write(reinterpret_cast<const char*>(&data), sizeof data);
#+end_src
真正可靠的序列化应该按照字段写出，例如写出 ISBN, 销量, 收入, 而不是把整个对象的内存块直接倾倒出去。
** In-class initializer: 把默认值放在成员声明处
这两个成员有默认成员初始化器:
#+begin_src cpp
  unsigned units_sold = 0;
  double revenue = 0.0;
#+end_src
C++11 起可以为数据成员提供 in-class initializer; 创建对象时，这些初始化器会用于初始化成员；没有初始化器的成员会被 default initialized 。 ~units_sold~ 和 ~revenue~ 会被初始化为0, ~bookNo~ 由 ~std::string~ 自己默认初始化为空字符串。

对内置类型成员尽量给默认成员初始化器。如果我们写:
#+begin_src cpp
  struct Bad {
    std::string name;
    unsigned count;
    double value;
  };
#+end_src
那么 ~Bad b;~ 里面的 ~count~ 和 ~value~ 在很多默认初始化场景下可能没有确定值。局部内置类型对象未初始化会产生 indeterminate value, 使用它们可能导致 undefined behavior 。成员也是同一套对象模型的延伸。
** ~struct~ 和 ~class~ 的真正区别
在 C++ 中:
#+begin_src cpp
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };
#+end_src
和
#+begin_src cpp
  class Sales_data {
  public:
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };
#+end_src
在这个例子里几乎等价。核心区别是默认访问权限:
#+begin_src cpp
  struct X {
    int a; // 默认 public
  };

  class Y {
    int a; // 默认 private
  };
#+end_src
所以本章节选择 ~struct~ 的设计意味是: *这是一个透明的数据聚合体，外部代码可以直接访问它的成员* 。

但是这个设计有取舍。 ~Sales_data~ 没有封装 invariant. 所谓 invariant ，就是对象在任何对外可见状态下都应该满足的约束，例如:
#+begin_example
units_sold >= 0
revenue >= 0
bookNo 不为空
平均单价 = revenue / units_sold
#+end_example
当前的 ~Sales_data~ 不保护这些约束。它只是一个“数据袋子”。这不是C++的最终设计风格：先理解 class type, member, header, 编译模型，再逐步把操作和约束封装进去。

实践上可以这样区分:
- ~struct~:
  - 适合简单、透明、没有复杂不变式的数据载体
  - 例如配置项、坐标、简单记录、 DTO
- ~class~:
  - 适合有资源管理、生命周期管理、状态不变式、并发约束的对象
  - 例如文件句柄、网络连接、缓存、业务实体
** ~Sales_data~ 是 aggregate, 可以用聚合初始化
因为当前 ~Sales_data~ 没有用户声明构造函数、没有 private/protected 数据成员、没有虚函数等，它是一个 aggregate (聚合). 标准草案对 aggregate 的定义包括: class aggregate 没有用户声明或继承的构造函数，没有 private/protected direct non-static data members, 没有 virtual functions 等。

所以可以写:
#+begin_src cpp
  Sales_data empty;

  Sales_data item1{"0-201-78345-X", 3, 60.0};
  Sales_data item1{"0-201-78345-X", 3}; // revenue 没有显示给出，会使用默认成员初始化器 0.0
#+end_src

C++20 之后还可以使用 designated initializer:
#+begin_src cpp
  Sales_data item3{
    .bookNo = "0-201-78345-X",
    .units_sold = 3,
    .revenue = 60.0
  };
#+end_src
指定初始化器对这种简单 ~struct~ 很清晰。但要注意C++的 designated initializer 比 C 更受限制，成员指定顺序要遵循声明顺序；不要把它当作任意字段乱序赋值机制。

这同时也说明了一个API设计问题: 如果你把一个类型公开为 aggregate, 外部用户可能大量依赖:
#+begin_src cpp
  Sales_data s{"isbn", 3, 60.0};
#+end_src
这样的代码。将来如果一旦添加构造函数，把成员改成 private 、增加不变式，很多调用代码都会失效。所以 aggregate 很适合内部简单数据结构，但如果是长期稳定的库接口，需要谨慎。
** 使用 ~Sales_data~: 手动读入、计算、合并
本节的逻辑是，读入两条交易记录，如果 IBSN 相同，就合并销量和收入，输出平均价格；否则报错。 C++ Primer 强调，因为 ~Sales_data~ 不提供操作，所以读入、输出、加法都要用户自己写。

我们可以写一个比较健壮的版本:
#+begin_src cpp
  #include <iostream>
  #include "Sales_data.hpp"

  int main() {
    Sales_data data1, data2;

    double price1 = 0.0;
    double price2 = 0.0;

    if (!(std::cin >> data1.bookNo >> data1.units_sold >> price1)) {
      std::cerr << "fali to read first transaction\n";
      return 1;
    }

    data1.revenue = data1.units_sold * price1;

    if (!(std::cin >> data2.bookNo >> data2.units_sold >> price2)) {
      std::cerr << "fali to read first transaction\n";
      return 1;
    }

    data2.revenue = data2.units_sold * price2;


    // std::cout << data1.bookNo << data2.bookNo << std::endl;
    if (data1.bookNo == data2.bookNo) {
      unsigned totalCnt = data1.units_sold + data2.units_sold;
      double totalRevenue = data1.revenue + data2.revenue;

      std::cout << data1.bookNo << ' ' << totalCnt << ' ' << totalRevenue << ' ';

      if (totalCnt != 0) {
        std::cout << totalRevenue / totalCnt << '\n';
      } else {
        std::cout << "(no sales)\n";
      }
      return 0;
    }
    std::cerr << "Data must refer to the same ISBN\n";
    return 1;
  }
#+end_src
这里有一个设计细节：输入记录里有“单价”，但是 ~Sales_data~ 存的是“总收入”:
#+begin_src cpp
  data1.revenue = data1.units_sold * price1;
#+end_src
这是一种存储策略选择，优点是合并交易很方便：
#+begin_src cpp
  totalRevenue = data1.revenue + data2.revenue;
#+end_src
平均价格可以之后计算:
#+begin_src cpp
  average = totalRevenue / totalCnt;
#+end_src
缺点是如果需要追踪每笔交易的单价分布， ~revenue~ + ~units_sold~ 就不够了。也就是说，数据结构不是中性的；它反映了你打算如何使用数据。

另一个补充: 严肃金融场景中一般不建议使用 ~double~ 表示金额，因为二进制浮点数不能精确表示许多十进制小数。教学阶段用 ~double~ 是为了专注类型和结构；真实业务中常用“分”为单位的整数，或者专门的 ~decimal~/~money~ 类型。
** 头文件: 为什么 ~Sales_data~ 应该放进 ~Sales_data.hpp~
如果一个源文件要定义对象:
#+begin_src cpp
  Sales_data data;
#+end_src
编译器必须知道 ~Sales_data~ 的完整定义，因为它要知道对象大小、成员布局、如何初始化成员。只有这样它才能为对象分配存储并生成成员访问代码。

这就是为什么类定义通常放在头文件里:
#+begin_src cpp
  // Sales_data.hpp
  #ifndef SALES_DATA_H
  #define SALES_DATA_H

  #include <string>

  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };

  #endif
#+end_src
一个好的头文件应该是 self-contained 的：只要别人写
#+begin_src cpp
  #include "Sales_data.hpp"
#+end_src
就能够使用 ~Sales_data~ 这个数据结构，而不需要提前猜测它内部用了什么头文件。因为 ~Sales_data~ 的成员里用力 ~std::string~ ，所以 ~Sales_data.hpp~ 自己必须 ~include <string>~ 。不要依赖 “包含者刚好已经 ~include <string>~ ”。

标准对 ~#include~ 的机制描述得很直接: ~#include~ 预处理指令会被它所识别的头文件或源文件的全部内容替换。 ~<...>~ 形式走实现定义的 header search； ~"..."~ 形式先按照源文件搜索规则寻找，失败时再转到 header search 。所以:
#+begin_src cpp
  #include <string> // 标准库里头文件
  #include "Sales_data.h" // 自己项目里的头文件
#+end_src
这是常见而合理的约定。
** header guard: 解决 “同一翻译单元内重复包含”
头文件可能被多次包含。例如:
#+begin_src cpp
  // a.h
  #include "Sales_data.h"

  // main.cpp
  #include "Sales_data.h"
  #include "a.h"
#+end_src
预处理后， ~Sales_data.h~ 的文本可能会进入同一个翻译单元两次。如果没有保护，就会得到重复定义，进而发生错误。

标准的 One-definition rule 说， class type, 函数, 变量等都是 definable item; 同一个 translation unit 不能包含同一个 definable item 的多个定义。所以需要 header guard:
#+begin_src cpp
  #ifndef SALES_DATA_H
  #define SALES_DATA_H

  #include <string>
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };

  #endif
#+end_src

执行过程是:
- 第一次 ~include~:
  - ~SALES_DARA_H~ 未定义
  - 进入 ~#ifndef~ 区域
  - ~#define SALES_DATA_H~
  - 复制 ~struct~ 定义
- 第二次 ~include~:
  - ~Sales_DATA_H~ 已定义
  - ~#ifndef~ 条件为假
  - 跳过 ~struct~ 定义


C++ Primer 也强调，预处理变量不遵循C++作用域规则，所以 guard 名字要在整个程序里尽量唯一，通常用全大写、基于头文件名或项目名前缀。

实践中也常见:
#+begin_src cpp
  #pragma once
#+end_src
它更简洁，但不是 C++ 标准的一部分；多数主流编译器支持。目前我们建议先掌握标准 header guard, 因为它揭示了预处理器的 ODR 的基本机制。
** header guard 不等于完整解决 ODR
这里要分清两层问题。

- 第一层：同一个 ~.cpp~ 预处理后，不要出现两次同一个类定义。 header guard 解决的是这个。
- 第二层：多个 ~.cpp~ 都可以包含同一个类定义，但这些定义必须一致。标准允许某些 definable item 在多个翻译单元中出现定义，但要求满足严格条件，例如对应定义应由相同 token 序列组成、名字查找应指向同一实体等。


如果手动在两个 ~.cpp~ 写两份“看起来差不多”的定义:
#+begin_src cpp
  // file1.cpp
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };

  // file2.cpp
  struct Sales_data {
    std::string bookNo;
    double revenue = 0.0;
    unsigned units_sold = 0;
  };
#+end_src
这就是灾难。两个翻译单元对同一个类型的布局理解不同，程序可能 ill-formed, 甚至在某些情况下问题不会被链接器友好地诊断出来。

这就是头文件的根本价值： *用一个源文本维护跨翻译单元一致的类型定义* 。
** 为什么类定义必须放头文件
我们可以只向前声明:
#+begin_src cpp
  struct Sales_data;
#+end_src
这会告诉编译器：有一个类型叫 ~Sales_data~ 。但此时它是 incomplete type (不完整类型)。

我们可以做:
#+begin_src cpp
  Sales_data *p = nullptr; // OK: 指针大小不依赖 Sales_data 完整布局
#+end_src
但不能做:
#+begin_src cpp
  Sales_data data; // error: 编译器不知道对象大小
#+end_src
也不能访问成员:
#+begin_src cpp
  p->bookNo; // error: 不知道里面有没有 bookNo
#+end_src
标准说，当定义一个 ~T~ 类型对象、声明一个 ~T~ 类型的非静态数据成员、对 ~T~ 做成员访问、 ~sizeof(T)~ 等操作时，需要完整类型。

这也解释了 C++ 的分离编译模型:
- 函数:
  - 调用者通常只需要函数声明
  - 函数体可以放在另一个 ~.cpp~ ，链接时再合并
- 类:
  - 如果要定义对象或访问成员变量，编译器必须看到完整类定义。所以类定义通常放在头文件中。
** 从编译器视角理解
我们可以用预处理初始看 ~#include~ 的效果:
#+begin_src bash
  g++ -E bookstore.cpp > bookstore.ii
#+end_src
~bookstore.ii~ 里会看到 ~Sales_data.hpp~ 已经被替换为了头文件内容。 header guard 会让第二次包含时内容被跳过。

也可以用 Clang AST 看编译器如何理解这个类型:
#+begin_src bash
  clang++ -Xclang -ast-dump -fsyntax-only bookstore.cpp
#+end_src
会看到类似概念上的结构:
#+begin_example
CXXRecordDecl struct Sales_data
  FieldDecl bookNo 'std::string'
  FieldDecl units_sold 'unsigned int'
  FieldDecl revenue 'double'
#+end_example
这有助于我们把源码和编译器内部模型对应起来: ~struct Sales_data~ 不是运行时动态创建的东西，而是在编译期建立了一个类型描述；每次定义 ~Sales_data data;~ ，编译器都依据这个类型描述生成对象初始化和成员访问代码。
** 设计取舍: 为什么现在先暴露数据，之后再封装
当前我们的版本:
#+begin_src cpp
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };
#+end_src
优点:
- 简单
- 聚合初始化方便
- 成员访问直观
- 适合作为教学中的数据模型
- 没有额外抽象成本
  
缺点:
- 无法保护不变式
- 所有用户都要重复读入、输出、合并逻辑
- 错误状态容易产生
- 一旦字段变化，所有使用者都要改


未来的成熟版本会像这样演化:
#+begin_src cpp
  class Sales_data {
  public:
    std::string isbn() const { return bookNo; }
    Sales_data &combine(const Sales_data &rhs) {
      units_sold += rhs.units_sold;
      revenue += rhs.revenue;
      return *this;
    }
    double avg_price() const {
      return units_sold ? revenue / units_sold : 0;
    }

  private:
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };
#+end_src
这不是说 ~class~ 比 ~struct~ 高级，而是说：当对象有不变式和行为时，应把行为放进类型内部。 C++ 的设计哲学不是 “只用类包装数据”，而是 “让类型表达语义约束”。简单透明的数据可以是 ~struct~; 有规则、有生命周期、有资源管理的东西应该封装成 ~class~ 。
* Variables and Basic Types 章末总结
第二章的核心是建立C++最基础的对象模型和类型模型。C++ Primer 在章末明确说: *types are fundamental to all programming in C++*; 每个类型都定义对象的存储需求，以及可以在该对象上执行的操作。内置类型与机器硬件表示紧密相关，而类机制则让我们可以定义自己的类型，标准库的IO, ~string~ 等高级抽象也正是用 class 机制建立起来的。
** 类型是 C++ 的解释框架
C++ 中，一段数据本身并不自动具有意义。意义来自类型。

同样一串 bit, 如果解释为 ~int~, 就是整数；如果解释为 ~char~, 可能是字符；解释为 ~float~, 就是浮点数。类型至少决定三件事:
1. 对象需要多少存储空间
2. 这段存储中 bit 如何被解释
3. 这个对象允许参与哪些操作


所以:
#+begin_src cpp
  i = i + j;
#+end_src
这个表达式的含义取决于 ~i~ 和 ~j~ 的类型。如果它们是整数， ~+~ 是算术加法；如果它们是 ~Sales_item~ ， ~+~ 可以表示销售记录的合并。第二章开头就用这个例子说明，表达式的合法性和语义由类型决定。

这也是C++静态类型系统的基础：编译器在编译期检查每个名字的类型，并根据类型决定哪些操作合法。
** 内置类型: 接近机器，但不等于机器
C++提供一组 primitive built-in types, 包括整数、字符、布尔、浮点数和 ~void~ 。这些类型非常接近硬件，但标准通常只规定最低要求，而不是规定大小。例如 ~int~ 至少16位， ~long long~ 至少 64 位；实际大小依赖平台和 ABI 。 C++ Primer 也特别强调：内置算术类型的大小会随着机器变化。标准只保证最小尺寸。

因此不能轻易假设:
#+begin_src cpp
  sizeof(int) == 4;
  sizeof(long) == 8;
#+end_src
这在 Linux x86-64 环境下可能成立，但在其他平台上未必成立。现在实践中，如果需要明确宽度，应该使用 ~<sctdint>~ 里的类型:
#+begin_src cpp
  std::int32_t
  std::uint64_t
  std::size_t
#+end_src
同时，本章最容易踩坑的是 ~signed~ 和 ~unsigned~ 的混用。 ~unsigned~ 不是 “安全的非负整数”，而是 *模整数* 。负数参与 unsigned 运算时会转化为 unsigned, 产生回绕结果。因此:
#+begin_src cpp
  unsigned u = 10;
  int i = -42;

  std::cout << u + i << '\n';
#+end_src
可能输出一个很大的数。
** 字面值也有类型
字面值不是“无类型的值”。 ~42~, ~42u~, ~42L~, ~3.14~, ~3.14f~, ~'a'~, ~"a"~ 都有类型。

特别需要区分:
#+begin_example
'a' // char
"a" // const char[2], 包含末尾 '\0' 
#+end_example
还有:
#+begin_example
10 // 十进制整数
010 // 八进制整数，值是8
0x10 // 十六进制整数，值是16
#+end_example
以 ~0~ 开头的整数字面值会按八进制解释。

字面值会影响重载、初始化、类型推导和转换。以后遇到模板、 ~auto~, 函数重载时，这些细节会重新出现。
** 变量与对象：变量是有名字的对象
C++ Primer 对 object 使用宽泛定义: *object 是一块具有类型的内存区域* 。变量则是我们给对象取的名字。对象是否有名字、是否是内置类型、是否是类类型、是否可修改，都不改变“对象是是一块带类型存储”的基本事实。

因此:
#+begin_src cpp
  int i = 0;
  std::string s = "hello";
#+end_src
都定义了对象。 ~i~ 是一个 ~int~ 对象， ~s~ 是一个 ~std::string~ 类类型对象。

本章反复强调的关键区别是:
- 初始化 initialization: 对象创建时获取初始值。
- 赋值 assignment: 对象已经存在，后来用新值覆盖旧值。

#+begin_src cpp
  int x = 10; // 初始化
  x = 20; // 赋值
#+end_src  
对内置类型来说，这个区别并不明显。但对类类型，初始化可能调用构造函数，赋值可能调用运算符，它们是不同操作。
** 默认初始化: C++ 把责任交给程序员
局部内置类型对象如果没有显式初始化，值是不确定的:
#+begin_src cpp
  int x; // 局部变量，未初始化
  std::cout << x; // 错误：使用未定义值
#+end_src
这不是 “随机值” 那么简单，而是可能导致 undefined behavior 。 C++ 这样设计，是为了保留零开销原则: 不强制为每个局部对象自动清零，让程序员在需要时显式初始化。

现代实践中，除非有非常明确的理由，否则应该初始化对象:
#+begin_src cpp
  int count = 0;
  double price = 0.0;
  std::string name;
#+end_src
对类类型对象，默认初始化由类自己决定。例如 ~std::string s~ 会得到空字符串，因为 ~std::string~ 定义了自己的默认构造行为。
** 声明、定义与分离编译
:PROPERTIES:
:CUSTOM_ID: f55e22b4-3292-48ec-9af4-14e9f60ceed4
:END:
C++ 区分 declaration 和 definition:
#+begin_src cpp
  extern int x; // 声明，不定义
  int x; // 定义
#+end_src
声明让名字可见；定义真正创建实体。变量可以声明多次，但只能定义一次。

这和 C++ 的分离编译模型密切相关。一个 ~.cpp~ 文件可以使用另一个 ~.cpp~ 文件中定义的对象或函数，但它必须先看到声明。链接器最后再把不同翻译单元中的定义连接起来。

本章虽然只初步介绍，但它已经埋下后面头文件、连接、ODR、inline、模板编译模型的基础。
** 作用域: 名字只在一定区域内有效
作用域决定一个名字在程序中哪里可见。名字从声明点开始可见，到所处作用域结束为止。
#+begin_src cpp
  int reused = 42;

  int main() {
    int reused = 0;
    std::cout << reused; // 使用局部 reused
    std::cout << ::reused; // 使用全局 reused
  }
#+end_src
局部名字会隐藏外层名字。C++允许这种隐藏，但实践上要谨慎，因为它会降低可读性，甚至制造非常隐蔽的bug.

好的习惯是: *在尽可能小的作用域中定义变量，并尽量靠近首次使用的位置定义* 。
** 引用: 别名，不是普通对象
引用是已有对象的另一个名字，它不是对象。
#+begin_src cpp
  int i = 42;
  int &r = i;
#+end_src
此后 ~r~ 和 ~i~ 指向同一个对象。
#+begin_src cpp
  r = 10; // 修改的是 i
#+end_src
引用必须初始化，并且一旦绑定到某个对象，就不能重新绑定到另一个对象。

理解引用的关键是:
#+begin_quote
引用不是“保存地址的变量”； \\
引用在语义上是对象的别名。
#+end_quote
当然，编译器实现引用时可能用地址，但语言层面应该把它理解为 alias. 这个理解以后对函数参数、返回值、范围 for 、模板推导、移动语义都非常重要。
** 指针: 保存地址的对象
指针和引用都能间接访问对象，但指针本身也是对象:
#+begin_src cpp
  int i = 42;
  int *p = &i;
#+end_src
指针可以保存地址，可以被赋值、拷贝、改变指向，也可以为空:
#+begin_src cpp
  p = nullptr;
#+end_src
现代C++应优先使用 ~nullptr~, 而不是 ~0~ 或者 ~NULL~ 。 ~nullptr~ 有专门的指针空值类型，能避免整型和指针重载时的起义； Effective Modern C++ 中也把 "prefer nullptr to 0 and NULL" 列为现代C++迁移时的重要建议。

指针最重要的风险是: *有效指针不一定可解引用* 。比如空指针、尾后指针都可能是有效指针，但不能通过 ~*p~ 访问对象。
#+begin_src cpp
  int *p = nullptr;
  ,*p = 10; // undefined behavior
#+end_src
因此，指针使用的底线是：初始化、检查、明确所有权和生命周期。
** ~const~: 把不可修改性写进类型系统
~const~ 让对象初始化后不可修改。 ~const~ 对象必须初始化，因为之后不能再赋值。

本章最重要的是理解两类 const:
- top-level const: 对象本身是 const
- low-level const: 通过指针、引用等间接访问到的对象是 const.


例如:
#+begin_src cpp
  int i = 0;
  int *const p1 = &i; // top-level const: p1 本身不能改指向
  const int *p2 = &i; // low-level const: 不能通过 p2 修改 i
  const int *const p3 = &i; // 两者都有
#+end_src
这个区分会影响拷贝、赋值、指针转换、 ~auto~ 推导。尤其是 ~auto~ 会忽略 top-level const, 但会保留 low-level const.
** ~constexpr~: 要求编译期可求值
~const~ 表示不能修改，但不一定表示编译期常量。

~constexpr~ 则要求表达式能在编译期求值:
#+begin_src cpp
  constexpr int size = 512;
#+end_src
所以可以用于数组大小、模板实参等需要编译期常量的场景。

现代 C++ 中， ~const~, ~constexpr~, ~consteval~, ~constinit~ 的分工越来越细:
- ~const~: 不可被修改
- ~constexpr~: 可用于常量表达式，通常要求编译期可求值
- ~consteval~: 函数必须在编译期求值
- ~constinit~: 保证静态初始化，但不表示对象不可修改


第二章主要掌握 ~const~ 和 ~constexpr~ 即可。
** 类型别名: 给复杂类型命名
C++ 支持用 ~typedef~ 或 ~using~ 定义类型别名:
#+begin_src cpp
  typedef double wages;
  using SI = Sales_item;
#+end_src
现代C++更推荐使用 ~using~ 。创建类型别名不是创建新类型，而是给已有类型另起一个名字。类型别名的主要价值是表达意图、隐藏复杂生命、辅助模板编程。
** ~auto~: 让编译器从初始化器推导类型
~auto~ 是编译期类型推导，不是动态类型。使用 ~auto~ 的变量必须初始化:
#+begin_src cpp
  auto x = 42; // int
  auto d = 3.14; // double
  auto s = "hello"; // const char*
#+end_src
~auto~ 能避免显式类型写错导致的正确性、性能和移植性问题。例如: ~std::vector<int>::size_type~ 不一定等同于 ~unsigned~, 用 ~auto sz = v.size()~ 可以让编译器保留真实返回类型。

但 ~auto~ 不是越多越好。需要掌握它的规则:
#+begin_src cpp
  const int ci = 42;

  auto a = ci; // int, 忽略 top-level const
  const auto b = ci; // const int;
  auto &c = ci; // const int&
#+end_src
实践上可以先记住:
#+begin_src cpp
  auto x = expr; // 只需要一个本地副本
  const auto &x = expr; // 只读访问，避免拷贝
  auto &x = expr; // 需要修改原对象
  auto *p = expr; // 明确表达这是指针
#+end_src
另外， ~auto~ 和初始化 ~{}~ 结合时可能推导出 ~std::initializer_list~, 这是现代C++的一个经典坑。
** ~decltype~: 从表达式获得类型
~decltype~ 根据表达式获得类型，但不求值。和 ~auto~ 的核心区别就是:
- ~auto~: 根据初始化器推导变量类型，通常会丢弃引用和 top-level const
- ~decltype~: 尽量精确地保留表达式的类型和值类别信息


所以会出现:
#+begin_src cpp
  int i = 0;
  int &r = i;

  auto a = r; // int
  decltype(r) b = i; // int&
#+end_src
~decltype~ 在业务代码中出现得少，但是在泛型库、返回类型推导、类型适配中非常重要。
** ~struct~ 和 ~class~: 定义自己的类型
第二章收束到自定义类型。数据结构不只是数据元素的集合，也包含使用这些数据的策略； C++通过定义 class 来定义自己的数据类型，标准库的 ~string~, ~istream~, ~ostream~ 都是 class 类型。

本章的 ~Sales_data~ 是一个最小自定义类型:
#+begin_src cpp
  struct Sales_data {
    std::string bookNo;
    unsigned units_sold = 0;
    double revenue = 0.0;
  };
#+end_src
它只包含数据成员，不提供操作。 class type 是内置类型机制的扩展：对象仍然有类型、存储、初始化、作用域、成员访问和生命周期，只是这个类型由程序员定义。
** 头文件与 header guard
类定义通常放在头文件中，因为编译器要定义对象或访问成员时，必须知道类的完整定义。

~Sales_data~ 通常放在 ~Sales_data.hpp~:
#+begin_src cpp
  #ifndef SALES_DATA_H
  #define SALES_DATA_H

  #include <string>

  struct Sales_data {
    std::string bookNo;
    unsigned unit_sold = 0;
    double revenue = 0.0;
  };

  #endif
#+end_src
头文件可能被多次包含，所以需要 header guard. C++ Primer 解释， ~#include~ 是预处理器功能，预处理器看到 ~#include~ 后会用指定头文件的内容替换这条指令； header guard 依赖预处理变量的“已定义/未定义”状态来避免重复包含。

实践规则是:
1. 每个头文件都写 header guard
2. guard 名字全大写
3. guard 名字尽量唯一
4. 头文件应 self-contained, 需要什么自己就 include 什么
** 本章的最终主线
第二章建立了C++最重要的一组基础概念:
- 类型决定意义
- 对象是带类型的存储区域
- 变量是带名字的对象
- 初始化和赋值不同
- 声明让名字可见，定义创建实体
- 作用域决定名字在哪里有效
- 引用提供别名语义
- 指针提供地址语义
- const 把不可修改性纳入类型系统
- constexpr 把编译期求值纳入类型系统
- auto 和 decltype 让编译器参与类型书写
- struct/class 让程序员定义自己的类型


更浓缩地说:
#+begin_quote
C++程序不是“变量+语句”的简单组合，而是有一组有类型的对象，以及一组受类型约束的操作。
#+end_quote
