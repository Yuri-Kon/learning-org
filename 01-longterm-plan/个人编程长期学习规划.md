# 个人编程长期学习规划

能力基线 总体路线与近期两阶段安排

版本 2.0　｜　更新日期 2026 年 11 月 9 日　｜　用途 个人执行与 ChatGPT 项目背景

当前主线是 Python 并发与工程实践，完成 Task Runner 后进入操作系统。长期目标是独立完成有实际用途的程序，能解释关键机制、验证边界与处理失败，并逐步把这些能力迁移到新的语言和项目中。

## 当前能力基线

以下判断承接此前的问答和项目讨论，属于初步画像。尚未验证的能力保留不确定性，后续用作品和独立任务更新。

| 领域 | 已有依据与当前判断 | 下一步需要的证据 |
| --- | --- | --- |
| Python 语言 | 能分析可变对象别名与共享引用，语义相对扎实 | 在项目中正确管理共享数据与接口边界 |
| 并发 | 正在建立 Event、Lock 与线程的理解 | 独立处理取消、完成、关闭之间的竞态 |
| 测试与调试 | 能解释错误、提出修复，完整验证证据不足 | 可重复触发问题，断言结果并防止回归 |
| GUI 与工程设计 | 能提出后台线程和取消检查点方案 | 完整实现线程通信、对象生命周期和安全退出 |
| C 语言 | 有基础，能分析对象生命周期 | 独立编写带错误处理的系统编程实验 |
| 算法与复杂度 | 初始判断出现偏差，反馈后变式表现改善 | 在新问题中独立选择数据结构并说明复杂度 |
| 操作系统 | 自述缺少系统理解，系统能力尚待评估 | 用 Linux 实验解释进程、内存和文件行为 |

## 选择这条路线的理由

Python 与 PySide2 接近工作和已有项目，适合集中补齐并发、测试及维护能力。Gentoo、Portage、C 与内核源码兴趣则为操作系统学习提供持续的问题来源。

学习以项目驱动，采用“预测行为—最小实验—解释机制”，配合少量定向阅读。算法和复杂度先随项目复习；Portage、raylib 保留为兴趣入口，暂不另开多条正式主线。

## 目标与安排的边界

已确定的方向是先完成 Python 主线，再学习操作系统。后续阶段、实验规模和时间预算均可调整。本文不预设职业等级，也不以通读教材或阅读源码数量评价能力。

本版本没有新增完成证明。Task Runner 的实际进展与操作系统启动日期待确认；后文均为计划和验收要求。

# 总体阶段与能力更新方法

## 总体阶段

前两阶段按当前方向执行，第三、四阶段为暂定安排，在第二阶段结束后重新排序或替换。

| 阶段 | 主任务与代表产出 | 完成后重点更新的能力 |
| --- | --- | --- |
| 一 Python 并发与工程实践 | 可取消 Task Runner、真实任务接入、最小 GUI 与测试 | 并发、验证、模块边界、Qt 生命周期 |
| 二 操作系统与 C 系统编程 | 进程、同步、内存、文件实验及局部内核导读 | C、系统机制、实验与源码阅读 |
| 三 算法与数据结构巩固 | 结合项目练习队列、哈希、堆、查找与复杂度分析 | 独立建模、边界推理与结构选择 |
| 四 综合项目与方向深化 | 根据复评，在 Linux 工具、Portage 或 GUI 应用中选一个可交付项目 | 需求拆分、集成、维护与跨领域迁移 |

第三阶段是否需要集中补课，由复评决定；若算法能力已在前两阶段得到充分验证，可缩短并转向更明显的缺口。第四阶段的具体项目在进入时确定。

## 每次学习的基本做法

先写问题和预测，再实现最小代码；用断言、日志或跟踪检验，读对应文档解释机制，最后做一个变式。每次只增加一个关键难点。阅读应回答当前问题，避免积累与实验脱节的材料。

## 每阶段结束如何更新画像

1. 提交成果：代码版本或文件、运行与测试命令、关键实验记录、已知限制，以及哪些部分得到过提示或使用了 AI 生成。
2. 进行复评：解释一处设计取舍，修复或分析一个边界问题，再完成一个未见过的小变式。允许查官方手册，先保留独立预测和尝试。
3. 更新记录：逐项写“旧判断—新证据—新判断—仍有缺口”，再决定进入下一阶段、补一个最小练习，或删减扩展范围。

能力使用“未评估、需提示完成、可独立完成并解释、可迁移到新问题”描述。一次成功先作为单条证据，经变式验证后再提高判断的把握；项目能运行不自动代表所有相关能力已掌握。

复评后保留三项资料：更新的能力画像、阶段总结、后续两阶段计划。只细化接下来两阶段，远期保持概述。每条评估记录注明日期、任务、证据位置和辅助程度。

# 第一阶段 Python 并发与工程实践

目标是完成一个可解释、可验证、可维护的后台任务执行器。沿用原计划的 Python 3.9 与 PySide2 约束，开始时确认实际环境。以下四个里程碑原拟约四周推进，按验收调整，不以周数强制切换。

## 一 单任务与协作式取消

使用 Thread、Event、Lock，实现启动、取消请求、状态查询、结果与异常记录。先画状态转换图，明确谁能修改状态、何时进入终态，以及重复取消的语义。任务在检查点响应取消，阻塞操作需要超时或其他可结束设计。

产出单任务核心和正常完成、取消、异常三类测试。验收时能说明“请求取消”和“任务已取消”的区别，终态不会被并发路径反复覆盖。

## 二 多任务与可重复的竞态验证

引入 queue.Queue 与少量 Worker，约定任务领取、结果快照和关闭协议。通过 Event、屏障或可注入检查点，安排取消与完成同时发生、重复取消、关闭时仍有任务等交错，检查是否丢任务或永久等待。

产出共享字段与锁的对应说明、关键交错测试和退出测试。测试应能稳定触发目标场景，并在超时时失败；不能只凭 sleep 或多跑几次判断正确，也不能依赖 GIL 保证复合业务状态安全。

## 三 接入真实任务与失败恢复

将执行器用于配置或订阅更新任务，可承接 Mihomo 工具已有代码。把网络、校验和文件替换分开，用可控响应模拟超时、失败和取消。先验证候选配置，再提交替换，并明确提交前后收到取消的处理规则。

产出可运行的任务适配与失败测试。验收时失败路径符合“保留有效配置”的约定，错误能被调用方观察到。已有业务实现可用于重构，无需重复造项目。

## 四 PySide2 界面与生命周期

为核心添加进度、取消和状态展示，明确 Python Worker 与 Qt 对象的边界，通过信号在 GUI 线程更新界面。学习 QObject 与 QThread 的线程归属、退出和清理；已有 Python 执行器与 Qt 适配应有清晰分工。

产出最小 GUI 与自动化验证，使用与环境兼容的 pytest-qt 等工具。验收覆盖连续启动、取消与任务运行中关闭窗口，界面可响应，退出后无遗留工作线程。

## 阶段验收与第一课

提交源码、测试、使用说明和一页以内的设计总结。独立解释一条竞态，完成“排队任务取消”等新变式。重点更新并发、测试、工程设计与 Qt 画像；核心仍有缺口时先补齐，业务或 GUI 缩减项须明确登记后再转入操作系统。

第一课先回答：cancel() 与任务完成同时发生时，谁决定最终状态？什么时刻决定？怎样构造可重复测试？从状态图和单任务原型开始。

# 第二阶段 操作系统与 C 系统编程

Python 阶段验收后启动，以 Gentoo Linux、C 和 OSTEP 为主线。进入前确认基本 C 编译、指针和资源释放能力，记录内核、架构、libc 与编译器版本。普通实验使用临时目录和用户权限。

以下五个单元依次建立概念，原规划的“五阶段”在总纲中统一作为本阶段的五个单元。每个单元都留下预测、程序、复现命令、观察与机制解释。

## 单元一 进程与系统调用

掌握进程、用户态与内核态、fork、exec、waitpid 和文件描述符继承。先比较 fork 前后普通变量的值与地址，再用 fork、execvp 和 waitpid 实现最小 Shell，处理成功、命令不存在和非零退出。

产出进程实验、Shell 和 strace -f 片段。完成标准是能解释父子返回值、exec 替换映像、子进程回收，以及普通内存副本与继承描述符的区别。首版 Shell 只需简单参数、cd、exit 与 EOF。

阅读 OSTEP 进程与 Process API 部分；查 fork(2)、execve(2)、exec(3)、waitpid(2)、open(2)。库函数与实际系统调用名称可能不同。

## 单元二 线程与同步

掌握共享地址空间、临界区、不变量、mutex、条件变量与死锁。用 pthread 实现有界生产者消费者队列：队列为空且未关闭时在 while 中等待，唤醒后重新检查条件；约定关闭时排空还是丢弃任务。

产出队列、关闭协议与关键交错测试。完成标准是能解释每个共享字段由谁保护、等待的谓词是什么，以及如何唤醒并回收 Worker；将其与 Python Event、Lock 的使用经验比较。

阅读 OSTEP 线程、锁、条件变量与并发错误部分；查 pthread_create(3)、pthread_join(3)、pthread_cond_wait(3)。普通 C 变量的数据竞争属于未定义行为，volatile 不能替代同步。

## 单元三 虚拟内存

掌握虚拟地址、页表、TLB、缺页、写时复制与 mmap。打印代码、栈、堆对象地址，对照 /proc/PID/maps；分配有限大小的匿名映射，比较映射后与逐页写入后的 RSS、缺页统计，再比较私有和共享映射。

产出地址空间图和映射对照记录。完成标准是能区分虚拟大小、驻留内存与缺页，解释相同虚拟地址为何不表示共享可写对象，并说明变量输出不足以单独证明物理页共享。

阅读 OSTEP 地址空间、地址翻译、分页与 TLB 部分；查 mmap(2)、getrusage(2) 及 proc 相关手册。不强求统计与理论页数精确对应。

# 操作系统后续单元与阶段复评

## 单元四 文件系统

掌握路径、inode、打开文件描述、链接、页缓存、原子替换与持久化。先保持文件打开再 unlink，观察描述符仍可读取；编写处理短写、EINTR 和错误返回的文件复制程序。

把 Python 配置更新问题改写成 C 实验：同目录创建临时文件，写入并校验，fsync 文件，rename 替换，再 fsync 父目录，检查每步错误。用 findmnt 确认实际文件系统，ext4 机制结合官方文档理解。

产出文件生命周期图、复制与替换原型、调用跟踪。完成标准是能区分名称、inode 和描述符，解释可见性、原子性与持久性的差异。正常运行或终止进程的实验不构成断电持久性证明；破坏性验证只在可丢弃环境进行。

阅读 OSTEP 文件与目录、文件系统实现、日志部分；查 read(2)、write(2)、unlink(2)、rename(2)、fsync(2)，再查 VFS 与 ext4 官方文档。

## 单元五 Linux 内核局部源码

从已有实验中选一个问题，如 fork 创建任务或 open/read 进入 VFS。固定源码 tag 或 commit，记录运行内核、Gentoo 补丁和架构；确认 /usr/src/linux 与运行版本是否一致。

从 strace 的实际调用出发，用源码搜索定位约 3 至 5 个关键函数，画调用图，说明核心对象、返回值与一条错误路径，再回到 C 实验核对。引用同时保留函数名、文件路径和版本。

产出一份简短源码导读。完成标准是能从用户程序讲到选定内核路径，再回到可观察行为；未读分支明确标为未知。不要求通读内核、编写模块或提交补丁。

## 进入下一总体阶段的条件

- 五个单元各有可复现的最小产出，能解释关键结果和实验不能证明什么。
- 独立完成跨单元新变式，例如“fork 后的文件偏移与普通变量为什么表现不同”，并指出需要查证的接口语义。
- 重新分析 Python Task Runner 中一次等待、一次资源释放或一次文件替换，用系统机制修正原解释。

复评重点更新 C 系统编程、操作系统、实验设计、调试与源码阅读能力，不因完成这些实验推定已精通 C 或 Linux。随后用一道新算法问题检查结构选择与复杂度，决定第三阶段的优先内容。

建议每个单元投入 2 至 3 个有效学习周，源码单元可放宽到 2 至 4 周，总体约 10 至 16 周。该范围不含准备、补课和中断，仅用于估算。

第一课问题：fork 前 x = 10，子进程改为 20，父进程 waitpid 后读到什么？&x 相同说明什么？先预测，再实验，并排除标准输出缓冲干扰。

# 执行节奏与参考资料

## 每周执行与调整

可先试行每周 3 次、每次 45 至 90 分钟，另留 15 分钟复盘，实际投入按工作负荷调整。大部分时间用于代码与实验；每周复盘只写本周证据、解释变化和下次最小任务。

连续两次主要卡在语言基础时，补一至两次最小练习；连续两周难以维持节奏时，降为每周一次并暂停扩展。工具配置长期占用时间时，先用可用环境；实验结果不稳定时，先缩减变量和检查错误，避免不断扩大项目。

阶段结束由验收决定。若范围过大，保留关键能力验证并登记缩减项；若独立变式未通过，补对应问题后再复评。兴趣支线只做小实验，是否升级为主线由复盘决定。

## 能力记录与文档维护

每条更新使用同一格式：日期与任务；原判断；代码和测试等证据；独立程度；新判断；尚未掌握的问题；下一步。能力画像保存结论，实验记录保存过程，本总纲保存方向与近期任务。

向后续学习对话提供最新总纲、最近一次能力画像和当前任务的代码或实验记录。请求先检查进展，再安排下一课；每次复评后更新版本并保留变更理由，旧状态不自动沿用为已完成。

开始执行时先核对已有 Task Runner 做到了哪个里程碑，验证已有成果后从首个缺口继续。当前不急于重写已有代码，也不提前并行启动操作系统大型项目。
